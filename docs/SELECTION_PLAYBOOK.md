# 选案例手册（双轴）

> 这份文档把「一批新线索进来，怎么判断」从**一次性推理**变成**可复用的判据**。
> 起因很具体：2026-10-26 从 howtomakemi.com 的 47 条官方披露里筛出 45 条，
> 当时的「小团队 / SaaS 可复制」四道筛子只活在一份临时报告和一次对话里。
> 下一批再来 100 条，那套判据要么重新推一遍、要么推出不一样的结论——
> 同一类形态在两批里一个判「可抄」一个判「不建议」，库就失去可比性了。
>
> 建立日期：2026-10-26 ｜ 配套数据：`data/anti_cases.json`（33 条反向样本）

---

## 0. 两条轴，一次说清

选案例是两件事，混在一起会互相污染：

| 轴 | 问的问题 | 输出 | 落到哪张表 |
|---|---|---|---|
| **A 能不能抄** | 一个或几个人，照着做，能不能活？ | T1 / T2 / T3 | `data/cases.json`（T1、T2） |
| **B 值不值得写** | 这个故事值不值得给读者看，怎么写？ | 正面样本 / 反面案例（三类） | `cases.json` 或 `anti_cases.json` |

**「不建议做」不等于「不值得写」。** 被轴 A 判 T3 的案例，恰恰常常是轴 B 的好材料——
因为它的排除理由都是可验证的结构事实，而不是「我觉得难」。

⚠ 反过来也成立：轴 A 判 T1 的案例不一定好写（很多是「他做到了，你也可以」的腔调），
轴 B 判好写的案例不一定能做（反面案例绝大多数你做不了）。

## 1. 轴 A：能不能抄 —— 四道筛子

逐条读页面的 `what / money / traffic / founder` 四段（或等价信息），过四道：

| # | 筛子 | 怎么问 | 否 = 什么 |
|---|---|---|---|
| ① | **自助订阅** | 注册即用，还是必须销售介入？ | 需要 SDR / 演示 / 报价 = 不是产品生意 |
| ② | **交付轻** | 有没有实施、集成、真人兜底？ | 有实施环节 = 人力随客户线性涨 |
| ③ | **护城河在产品之外** | 壁垒是资本 / 算力 / 牌照 / 数据资产 / 创始人履历 / 平台关系？ | 命中任一项 = 产品形态可抄，生意抄不了 |
| ④ | **国内有无强势同类** | 国内是否已被占住，且占位者不是「产品差」而是「渠道强」？ | 有 = 需求真但位置没了 |

四道全过 → **T1 形态可抄**；①②过、③或④命中但可换形 → **T2 有条件**；
③命中在资本/算力/牌照/规模上 → **T3 不建议**。

### 1.1 口径列是硬性要求，不是可选项

`money` 段那个数字**必须先定口径再谈大小**。允许的取值：

```
arr       年化经常性收入（含「run-rate」「年化收入」）
annual    年营收 / 年收入（含「2025 年营收」）
mrr       真·月收入（页面明说「月收入」且没有别的口径混进来）
funding   融资额（含「累计融资」「X 轮」）
valuation 估值
gmv       平台流水 / 累计处理金额 / 付给第三方的钱
price     定价档位（「¥665 起」）
lifetime  累计收入（不是当期）
unknown   页面没说清年还是月
invalid   上面都不成立的混用（例如融资口径混乱、数字与任何原文都对不上）
```

**没有 caliber 列的 backlog 表是废纸。** 2026-10-26 实测：47 条里 7 条的「月收入」栏
装的是 GMV / 融资额 / 定价，另有 3 条年/月不明。聚合站的「💰 月收入」是个**自由文本框**，
它什么都能装。

### 1.2 一个反直觉的统计（33 条实测）

把 33 条 T3 的「💰 月收入」卡片逐条对回页面自己的「数据口径」段：

| 标签值的真实口径 | 条数 | 说明 |
|---|---|---|
| `arr` 年化收入 | 20 | 按标签读成月收入 → **放大 12 倍** |
| `annual` 年营收 | 3 | 同上，放大 12 倍 |
| `mrr` 真月收入 | **1** | 只有 `picturethis` 一条名副其实 |
| `funding` 融资额 | 4 | 那个数跟收入无关 |
| `invalid` 口径对不上 | 2 | 取错曲线端点 / 来源不明 |
| `unknown` 年/月不明 | 1 | |
| `gmv` 平台流水 | 1 | 付给招聘官的钱 |
| `price` 定价 | 1 | Pro 档 ¥665/月 |

（2026-10-26 建表时是 arr 19 / annual 4；上站时发现 `lovable` 的 `caliber_note`
原文写着「¥13.44亿 ARR」却记成 `annual`，已改正为 `arr`。上站后卡片会把口径标签
和这句说明**并排**显示，两者不一致就是当场自相矛盾。）

**33 条里只有 1 条标签没写错。** 这个比例本身就是一条内容——
`docs/` 里所有引用聚合站收入的地方，都要先看这一节。

⚠ 同时说明一件事：**旧口径表自己也会错。** 这轮复核发现
`data/htm_backlog_caliber.json` 有 5 条与页面原文不符（`rox`、`crustdata`、`tjm-labs`、
`bland-ai`、`sanas`），已在 `anti_cases.json` 的 `caliber_conflict` 字段留痕，
**没有偷偷改旧表**——旧表是历史判断，改它等于伪造当时的结论。

## 2. 轴 B：值不值得写 —— 正面一个，反面三类

### 2.1 正面样本

用轴 A 的 T1/T2。写法是既有的「它真正卖的是 ___」结构（`verdict` 字段），
落点必须是**可迁移的那一句话**，不是成功学。

### 2.2 反面案例分三类，混着写会产出 33 篇一样的东西

| 类 | `role` | 判据 | 文章落点 | 典型陷阱 |
|---|---|---|---|---|
| **结构不可复制** | `structural` | 护城河是钱 / 算力 / 人力规模 / 数据资产 / 关系资产 | 门槛的**具体数额**是多少，多少人才跨得过去 | 写成「他们有钱所以你不行」，读者学不到任何东西 |
| **资格门槛** | `license` | 不是能不能做，是**有没有资格**做 | 缺的是哪一张证；国内对应的是哪一张 | 国外牌照名不能照搬，国内是另一套（医疗 / 支付 / 安全） |
| **数字不成立** | `caliber` | 页面那个数**根本不是收入** | 一个数字的三种读法，会得出三种结论 | ⚠ 见第 3 节，这一类最容易写成造谣 |

一条同时命中多类时：`roles` 记全部，`role` 记**主因**（写文章按主因落笔）。

### 2.3 三类各自的写法要点

**structural**：必须给出「跨不过去」的具体量。不是「他们融资很多」，
而是「累计融资 ¥36.96亿，其中 ¥22.18亿 是 B 轮，估值 ¥443.52亿」。
数字要能让人自己算出「我差几个数量级」。

**license**：必须把「能力」和「资格」分开讲。读者常以为自己做不了是因为技术不够，
实际是缺执照。这一段的价值在于**换赛道建议**：
医疗→做医疗机构的工具而不是医疗本身；支付→做商户的软件而不是支付。

**caliber**：必须同时给「正确读法」和「错误读法的后果」。
只骂聚合站没意义，要给出「你自己怎么在两分钟内识破」。

### 2.4 33 条怎么合并成 7 篇（按「门槛类型」，2026-10-26 定）

`role` 只有三个值，但 `structural` 有 21 条。21 条塞一篇 = 一万五千字，
读者看完只记得「他们都很有钱」——那正是 §2.2 点名的陷阱。
所以 structural 必须再按**跨不过去的东西是什么**切一刀。

| # | 篇（`volume`） | 条数 | 判据（这一篇在比什么） | 落点 |
|---|---|---|---|---|
| Ⅰ | 账单 · 用钱买来的规模 | 6 | 边际成本随用量线性涨，规模是融资垫出来的 | 钱具体花在哪一格：推理账单 / 垫算力 / 买公司 / 买下载量 |
| Ⅱ | 人头 · 人力就是交付能力 | 4 | 交付要有人接电话、复核、上门，产能不由代码决定 | 敢不敢承诺响应时间 = 背后有没有一排工位 |
| Ⅲ | 苦力 · 每个系统都要重做一遍 | 5 | 覆盖面靠逐个适配（连接器 / 国别 / 毫秒），只能拿时间换 | 没有技巧只有数量：400 个连接器、每国重写规则 |
| Ⅳ | 社区 · 买不到、只能攒的分发 | 3 | 星数 / 粉丝 / 月活是时间攒出来的关系资产 | 「零融资」的人手里握着钱买不到的东西 |
| Ⅴ | 关系 · 首单靠上一家公司 | 3 | 客户信任与数据资产来自履历和长期采购 | 让客户签字的不是技术，是「他上一家叫什么」 |
| Ⅵ | 资格 · 缺的不是能力，是那张证 | 7 | 门槛是牌照 / 执业资质 / 专业责任兜底 | 缺哪一张证，国内对应哪一张 |
| Ⅶ | 数字 · 那个数根本不是收入 | 5 | 页面那个数是融资 / GMV / 定价 | 一个数字的三种读法（⚠ 见 §3） |

合计 33 条。其中 3 条已单独成文（`lovable` / `medvi` / `crowdreply`，各 `role` 一条试点，
在 `out/articles/`），成稿时引用即可，不用重写。所以要写的其实是 **30 条 / 7 篇**。

落地方式：`scripts/build_anti_cases.py` 的 `VOLUMES` + `VOLUME_OF` 两张表。
**每条必须归篇、每篇条数必须与 `VOLUME_COUNTS` 一致**，否则脚本直接退出
——不做「没归篇就跳过」，那正是 `score_china_fit` 那个坑。

⚠ `volume` 与 `series_tag` 是**两个轴**，不是重复字段：
`series_tag` = 栏目身份（三个：结构 / 资格 / 数字），用于公众号栏目标签；
`volume` = 这一批写成几篇、每篇叫什么，用于成稿排期与站点分组。

## 3. ⚠ C 类专用警戒：不许把活得很好的公司写成失败案例

这是三类里唯一会**产生事实错误**的一类，单独用一节锁住。

`caliber` 类的案例**大多活得很好**。`crowdreply` 的 ¥665 是 Pro 定价，
不代表它月入 665 元；`paraform` 的 ¥3.36亿是付给招聘官的钱，不代表平台营收为零。
把它们写成「为什么不建议做」＝ 替读者判了一个我们没能力判的死刑。

三条硬规矩：

1. **标题里不许出现「失败 / 死掉 / 做不成」**，除非有该产品停运的一手证据
   （那种情况归 `graveyard.json`，不归这里）。
2. **正文必须明确写出「它的产品形态没问题」**，并把「数字有问题」和「生意有问题」分开。
3. **不许反推**。定价 × 某个臆想的用户数 ≠ 收入。能算的算，算不出的写「未披露」。

同类红线（沿用 `MEMORY.md`）：
- 聚合站的收入字段是**快照、不是现值**，一律回源后再入库；
- ARR ÷ 12 不是独立 MRR；
- 「回源失败」只能入库 `partial` + `verification_downgraded` 留痕。

## 4. 三张表的分工（别混）

| 表 | 装什么 | 证据口径 | 站点表现 |
|---|---|---|---|
| `data/cases.json` | 274 条推荐位案例 | 一手来源（stripe/official）优先，双轴评分排名 | 主列表 + 排行 |
| `data/graveyard.json` | 22 条**已停运**项目 | 死亡与亏损数字要有一手来源 | 墓碑区（独立栏目） |
| `data/anti_cases.json` | 33 条**可以读、不建议照抄** | `aggregator`；原始媒体未逐条打开 | 独立栏目（见 4.2） |

`graveyard.json` 当初独立的理由写在 `server.build_payload` 的注释里：
「成功案例讲怎么成的，失败案例讲怎么死的，两者的证据要求不同，
混在一张表里会让 case 的入库闸门（content_gate）失去意义。」
反向样本是第三种东西，同理独立。

### 4.1 为什么 33 条没进 `cases.json`

三个具体理由，不是洁癖：

1. **事实层面**：33 条里 20 多条是活得很好的公司（`lovable` 估值 ¥443.52亿）。
   进「案例库」会被读者当成推荐位。
2. **排序层面**：`china_fit` / `solo_fit` / `composite` 是按「值得做」排序的。
   给 33 条打低分 = 在排行榜尾部堆 33 条无信息量条目。
3. **计数层面**：`verify_deploy` 拿 `curated` 计数与线上比对，加进来会连带抬高；
   而 `score_china_fit` 缺表会**静默清空**评分（这是 `MEMORY.md` 里的既有坑），
   33 × 2 张人工表写出来也全是低分，投入产出不对。

### 4.2 上站方式（2026-10-26 落地）

按 4.1 结尾说的那条路做了，没有并进 `cases`：

- `/api/data` 多一个 **`anti` 键**（`{cases, volumes, built_at}`），`stats.anti` 是计数；
- 前端多一个视图 `#anti`（「这些别照着做」），按 `volume` 分成 7 组，
  chips 只放短名（Ⅰ 账单 / Ⅱ 人头 …），全名留在篇头；
- 预渲染**一页** `anti/index.html`（33 条分组内联、可被收录、进 sitemap），
  **不进 `case/`** —— `verify_deploy` 断言「case 目录链接数 = curated 案例数」，
  往那儿塞 33 个页面会让「没少案例」这条唯一判据失效；
- 卡片上必须同时出现两个东西：页面原话（`page_label.value` + 「页面写『月收入』」）
  和真实口径（`caliber`）。33 条里只有 1 条两者一致，这一栏就是内容本身。
- 构建自检加了三道锁：`anti` 的 id 不混进 `cases`、页面缺条目当场报错、
  篇的条数与 `count` 不一致当场报错（否则会出现「Ⅰ 篇 6 条」却只列 5 条的错位）。

## 5. 复跑清单：下一批线索进来，按这个顺序做

1. **抓全页，不只抓卡片。** 卡片上的「💰 月收入」不可信（第 1.2 节），
   必须拿到页面自己的「数据口径」段。参考实现：`tmp/parse_neg_pages.py`。
2. **先定口径，再排序。** 每条先填 `caliber`，`unknown` / `invalid` 的一律不进排序。
3. **过四道筛子，出 T1/T2/T3。** 判据不许临时改；要改就改这份文档并留变更记录。
4. **对 T3 打三类标签**（`structural` / `license` / `caliber`），进 `data/anti_cases.json`。
   登记走 `scripts/build_anti_cases.py` 的 `JUDGE` 表——**表是主体，JSON 是产物**。
5. **T1/T2 走既有漏斗**（collect → triage → verify → score → cases.json），
   两道人工评分表（`score_china_fit.SCORES` / `score_solo_fit.DELIVERY`）必须同时补。
6. **文末自检**：`python scripts/build_anti_cases.py --check` 会拦下
   「三类里有一类为空」「不是月收入却没写口径说明」这种情况。
