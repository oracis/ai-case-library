# 四平台台账一致性机制

> 一句话：**不再「定期对账」，改成「发布即回读 + 机器巡检 + 状态单点写」。**
> 对账是治病，这套是让人不再生病。

---

## 一、为什么会漂（三个根因，都能在 2026-10-19 那次对账里看到证据）

### 根因 1：用「在哪个文件」表达「什么状态」

头条 / 小红书 / B站 各自有两本账：`*_drafts.json` + `*_published.json`。
草稿升格为发布，要在两个文件各写一次，中间失败就永久不一致。

> 证据：头条草稿台账 55 条里，16 条早就该迁走（13 条已发布、3 条幽灵），
> 全靠一次人肉对账才发现。

### 根因 2：台账不存远端 ID，只能靠标题认

| 平台 | 远端 ID | 当时存在哪 |
|---|---|---|
| 公众号 | `appmsgid` | ✅ 字段里（59/60） |
| 小红书 | `note_id` | ✅ 字段里（8/8），草稿侧无 ID（平台无服务端接口） |
| 头条 | `gid` | ❌ 只在 `note` 的**人话文本**里 |
| B站 | `article_id` | ❌ 只在 `note` 的**人话文本**里 |

没有 ID 就只能语义匹配，而标题有**两种口径**（早期 `月收$X：…` / 现在
`产品名：…`），同一篇文章两种标题 ⇒ 必然误判。

> 补齐后（2026-10-19）：头条 21/21、B站 11 条的远端 ID 都已进字段，
> 这两家**不再依赖标题匹配**。仍然没进字段的只有公众号 1 条（`insect-bite-id`）。

> 证据：同一次对账，纯标题匹配把 13 篇老文章判成幽灵，逐个打开正文才发现
> 其中 4 条是真的、其余都是「换过标题」。

### 根因 3：接口返 `code:0` 就落账

头条的 `code:0` 只代表「请求已受理」，不代表落库（删假 gid 也返 `code:0`）。
headless 下 `tt-anti-token` 无效（7050）时照样 `code:0` ⇒ 假成功写进台账。

> 证据：`aeo-engine` / `augora-ai` / `le19emetrou` 三条，台账记着「在草稿箱」，
> 线上草稿箱和已发布列表**都没有**，本地内容包却齐全 —— 永远发不出去。

## 二、目标模型：一条记录一个事实

```
case_id @ platform  →  {
    state:       draft | published | unverified
    remote_id:   gid / note_id / bvid / appmsgid     ← 主键
    verified_at: 最后一次回读证据的时间
    evidence:    这状态是怎么来的（publish_api / health_backfill / …）
}
```

四条规则：

1. **状态是字段，不是位置** ⇒ 迁移是一次原子写，不存在「两个文件各改一半」。
2. **remote_id 是主键** ⇒ 对账退化成两个集合求差，毫秒级、零歧义、不需要标题匹配。
3. **没有 ID 不许写 published** ⇒ 降级成 `unverified`，等回读补证。
   假成功进不了账，也不会挡住重发。
4. **同一条记录只出现一次** ⇒ 草稿台账和已发布台账不会同时有它。
   ⚠ 例外：一个 case 可能在**草稿箱和已发布列表各有一个对象**（对已发布的
   稿子再跑一次存草稿就会出现）。这时两个 ID 并存 —— 状态按 published，
   草稿 ID 存在 `draft_remote_id` 里，谁也不覆盖谁。

| `scripts/test_ledger.py` | 18 项：round-trip 无损、迁移原子、无 ID 降级、平台 ID 字段名、草稿/已发布双 ID 并存 |
| `scripts/test_bili_draft_sync.py` | 8 项：加工过的正文仍能按字认领、撞车不猜、重复跑幂等、已发布不许被拉回草稿 |

### 2026-10-19 实测（跑完这一轮之后的真实数字）

```
头条    草稿 38 / 已发布 21   → ✓ 干净（21 条 gid 全自动回填成功）
小红书  草稿 44 / 已发布  8   → ✓ 干净（8 条 note_id 与线上完全对齐）
B站     草稿 49 / 已发布 11   → ✓ 干净（草稿账当天新建，49 条全部认领）
公众号  草稿 41 / 已发布 19   → 1 条缺 appmsgid（探针未接，见 P2）
```

三处细节值得记：

- **头条 21 条 gid** 全靠巡检自动回填：`note` 里的『旧标题』与线上标题精确
  相等，21/21 全中。**从此头条对账不再需要标题匹配。**
- **B站 7 条漏登**是这次才暴露的：线上 13 篇、台账只有 6 条。以前没人对过
  B站，因为「看起来没出过问题」。这类沉默的漏登，正是人工对账最容易漏掉的
  东西 —— 人只会去查「觉得可疑」的那个平台。
- **13 篇 ≠ 13 条**：B站补登后台账是 **11 条**，因为 `trustmrr` 与
  `uplinked-b-v` 各发了新旧两篇（标题口径不同、正文相同）。一个 case 一条
  记录是统一账本模型的前提，旧篇的标题写进 `note` 的『…』里 —— 巡检的
  ORPHAN 反查认这个别名，不会再把它们当漏登。

### B站草稿账：从「零记录」到 49 条全认领（2026-10-19）

补登完已发布那侧才发现：**B站根本没有草稿账**。线上藏着 49 条草稿，本地
一条记录都没有 —— 「这篇存过草稿没有」只能开浏览器去数。这和已发布那 7 条
漏登是同一种沉默：**没出过事，所以没人查。**

`scripts/bili_draft_sync.py` 一次跑完：49 条全部认领成功（44 条标题精确命中、
5 条正文认领），生成的 `data/bili_drafts.json` 里每条都带 `article_id`。

路上三个坑，每个都值得记住：

1. **有些 case 只有母版、没有 `out/bili` 包**（vid-ai / vectosolve / publbee /
   podawaa / augora-ai）。只扫 `out/bili/<id>/` 会把它们判成「没归属」——
   它们确实在草稿箱里躺着，只是没生成过 B站产物目录。
2. **线上 `summary` 是加工后的一版**：段落标题前多了 `▶`、加粗形状变了。
   只去标点比不动（`—` 这种也叫不出分区别）。判据换成「只留字母数字和汉字」
   才对得上 —— 注意这是**逐字相等**，不是相似度打分。
3. **正文比到第 190 字就分岔**：本地母版和线上草稿箱里那一版确实不是逐字
   相同的（可能改过又没重存）。所以窗口从 200 字逐档收到 120 / 60 字，**任一档唯一命中即可** —— 换锚点，不降门槛。

**发文会不会清草稿**：这次 49 条草稿 × 11 篇已发布，**零交集** —— 发过的
那些草稿确实不在草稿箱里。但别指望它永远如此：对一篇已发布的稿子再跑一次
`publish`（= 存草稿），草稿箱立刻多一条。所以账本从一开始就要能装两个 ID
（`remote_id` 和 `draft_remote_id`），不能靠「现在没有交集」赌未来没有。

## 四、还差什么（按优先级）

### P0 · 发布时就记 ID（最划算的一处改动）

现在 ID 靠事后巡检回填，理想是发布成功那一刻就落账。

| 位置 | 现状 | 改法 |
|---|---|---|
| `toutiao_publish.py:1514` | `mark_published(c["id"])`，而上一行手里就有 `pgcid` | `mark_published(c["id"], remote_id=pgcid)` ⚠ 落地前先拿一篇已知文章验证 `pgcid == gid`（头条这两个 ID 通常相同，但没实测过，别直接信） |
| `xhs_publish.py:1371` | 发布成功后只标 id | 发布页/接口能拿 `note_id`，一并传 |
| `bili_draft_api` 存草稿 | ✅ **已接（2026-10-19）**：`save_via_api` 拿到 `new_aid` 后调 `ledger.set_draft_id` | 用 **`article_id`**（数字 cv 号）⚠ 不是 `bvid`（那是视频的 BV 号），也不是 `id`（list 布局里 `id` 是 **case id**，撞过一次） |
| `wechat_*` | 已有 `appmsgid` | 保持。⚠ 但要知道：**群发/发布后 appmsgid 会变**（草稿 100000546 → 发表后 2247484064）。所以 `wechat_publish.py send` 成功后的记账口径是：`appmsgid` **保留草稿 id 不动**（`refresh`/`fix-cover` 靠它定位草稿），新 id 记到 `published_appmsgid`。`wechat_sync` 的 id 认亲对已发表侧注定 miss，靠标题兜住 —— 这是已知取舍，不是 bug |

配套：`toutiao_publish.mark_published(cid, remote_id="")` 内部改调
`ledger.promote("toutiao", cid, remote_id=...)`，顺手把草稿台账那条删掉
（这一步就是根因 1 的解药）。

### P1 · B站探针接进 `REMOTE_PROBES` —— ✅ 已完成（2026-10-19）

`_remote_bili()` 已注册：`list_drafts(cdp)` → `article_id`、
`list_published_articles(cdp)` → `id`，两侧都 `*_ok=True`。
注意：两个函数都要求 cdp **当前页**在 B站创作中心，先开 target 再调

接上之后第一次跑就抓出 7 条漏登，已按正文核对后补登（台账 6 → 11 条，

## 五、什么时候该跑什么（触发式，没有定时任务）

> 2026-10-19 定调：**这套东西没有排期，全是「该做的时候才做」。**
> 数据就这百十条，又不是天天发；而在线比对要开浏览器、依赖登录态，
> 排期跑只会养出一个脆弱的定时任务。**没有 cron、没有每日每周** ——
> 之前文档里那张「每天一次 / 每周一次」表是过度设计，已删。

| 什么时候 | 跑什么 | 成本 | 为什么 |
|---|---|---|---|
| **每次发车前**（`publish_multi run` 自动带） | 本地账本体检 | 毫秒，不联网 | 别往一本已经坏了的账上继续写。ERROR 拦车，WARN 只提示，`--no-preflight` 可绕 |
| **每次发布成功那一刻** | 记账 + 回读校验（各平台脚本内） | 0 | 发布即落账，别等事后补 |
| 每次往 B站存完草稿 | （自动，`save_via_api` 里已记） | 0 | 不再攒无主草稿 |
| 公众号要把草稿**发表**出去 | `python wechat_publish.py send --case <id>` | ~30s/条（+等扫码） | 扫码前的开编辑器、设开关、两层确认和扫码后的校验落账全自动，**发布和群发两种模式都要管理员/运营者扫码**（物理动作，脚本检测到二维码就停下等，最多 5 分钟） |
| **怀疑漏了 / 要重发前 / 做决定前** | `python ledger_health.py --platform <p> --online` | 20-40s/平台 | 给写入路径当回归测试。历史上 7 条漏登、49 条无主草稿都是**写入路径写错了**，不是漂移 —— 「发布时记一次」治不了这个，因为它只会忠实地把错误也记进账 |
| 小红书要把草稿**发布**出去 | `python xhs_publish.py send-draft --dry` 先看 | ~1min/条 | 走到发布按钮前已实测跑通（开草稿箱→挑最久的→点「编辑」→**图片体检**）；发布按钮 DOM 已知（`button.ce-btn bg-red`），但**抽屉编辑器里没实测到**，`--dry` 会把当前页面红按钮状态打出来，第一次用务必 `--dry`。有裂图默认拦下（CDN 签名会过期） |
| B站攒了一批没归属的草稿 | `python bili_draft_sync.py` → 看报告无误再 `--apply` | 30s | 认领 case。**先看报告，别直接 apply** |
| 台账文件可疑（半截/乱码） | 体检会拦；人工看 `data/*.json` | 0 | 坏文件会被静默读成空账，然后按「没发过」重发一遍 |

**自愈边界照旧**：`--apply` 只修 `DUP` / `PROMOTE` / `BACKFILL` 三类证据唯一、
可逆的；`STALE`（线上没了）、`ORPHAN`（线上漏登）只报告 ——
误删一次比漏修十次贵。

## 六、边界：什么**不**做

1. **不自动删线上内容。** 线上有、本地无（ORPHAN）只报告，人确认后再动。
2. **不靠标题猜。** 补 ID 只认「note 别名精确命中」或「标题完全相等」，
   多候选一律放弃。标题语义匹配只在**诊断**时用，不用于写账。
3. **不在读失败时下结论。** 返回 `None`（没读到）和 `[]`（读到了确实空）
   必须分开；小红书草稿侧本来就读不到，那是平台限制，不是失败。
