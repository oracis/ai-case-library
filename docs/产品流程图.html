① 全景链路

一条主干：自动采集 → 人工挑选 → 人工核实 → 入库 → 成文 → 两路分发。红线以上全是机器，红线以下全是人。

一句话记住这张图：机器负责把世界搬进 inbox；人负责从 inbox 里挑出值得核的、核出可以引用的、写成可以读的。两者之间那条线，就是产品的全部价值。

② 采集层细节

六个源，五种通道形态。唯一的自动化段落，也是唯一允许失败而不影响产品的段落。

摔过的跤：Indie Hackers 没有真分页（?page=2 返回的字节与首页完全相同），所以才需要 sitemap 分片轮换缓存 ih_slugs.json；TrustMRR 全站 startup-sitemap.xml 必须显式 gzip，否则 identity 编码的 1.7 MB 拉不动。

③ 深核 → 判定 → 入库闸门

整套产品的信任机制都在这张图里：AI 只负责打底，决定权与责任都在人，而闸门允许 AI 与脚本请求，但从不放水。

为什么「source_kinds 为空不许入库」是硬规则：2026-09-24 踩出来的——一条没有任何来源的案例如果被标为「已核实」，整个库的可信度就归零。没有来源，就没有资格称核实。

④ 发布流水线 release.py

六步串行，依赖声明有约束力（不是注释）；失败即停，无回滚实现，靠幂等 + 全量覆盖补偿。

auto_deploy 不是发布主路径。它只做「线上和我本地不一样就补一次」的幂等兜底，并不知道你是否改完。generated_at 与 stats.inbox 会先归一化再比，否则每天必然误判为有差异。

⑤ 公众号管线

cases → 正文 → 发布就绪 HTML → 草稿箱。通道是浏览器自动化而不是微信 API——未认证订阅号没有 freepublish 权限。

台账字段：wechat_published.json 记 title / published_at / status(draft|partial|published) / file / appmsgid / refreshed_at / group_sent。注意 status=draft 的实际含义是「草稿管线已完成」，是否已群发要看 group_sent。

⑥ Git / CI 拓扑

机器数据与人工产物分分支。这是「每次 push 都要 rebase」的根治方案。
