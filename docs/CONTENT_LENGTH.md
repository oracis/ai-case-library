# 内容长度手册（分平台字数口径 + 先厚后薄）

> 这份文档把「一篇稿写多长、先写厚还是先写薄」从一次性讨论变成可复用的起草规范。
> 起因：2026-11-22 用户看阿里云已发布文章（`article 1787263`）的截图问「是不是字数太少」。
> 实测该文正文仅 1085 字符 / 547 中文字，与同批介绍稿同口径、并非故障；
> 但技术社区发薄稿有被判「灌水」的风险（腾讯云 Wesnoth 5 篇被拒，理由即「灌水/技术无关内容」）。
> 用户确认把这套口径固化为以后起草的硬规范。
>
> 建立日期：2026-11-22 ｜ 性质：起草规范（非机器闸，理由见文末）

---

## 0. 一句话结论

**分平台定口径 + 把生产顺序反过来：先写厚稿，再裁剪派生薄稿；不给薄稿硬加字数。**

---

## 1. 分平台字数口径

起草目标，不是机器硬闸（理由见 §4）。

| 平台 | 口径 | 目标字数 | 依据 |
|---|---|---|---|
| 掘金 / 知乎 / 博客园 | 深度技术拆解 | 2000–2700 | 现有深度稿 2674 字已被接受 |
| 阿里云 / 腾讯云 | 深度拆解 | 2000+ | 腾讯云拒稿教训：薄稿有被判灌水的风险 |
| CSDN | 技术向、控金额密度 | 1500–2000 | 有金额密度闸，堆数字会被拦 |
| 公众号 | 长文（主阵地） | 2000+ | 「万物解释者」定位 |
| B站简介 / 介绍稿 | 概述 | 1000–1200 | 够用，不必厚 |
| 小红书 | 卡片式 | 500–600 | 图文笔记，短是对的 |

**薄稿不是故障。** 实测同一 case（Mindustry）各平台稿长：

| 口径 | 平台稿 | 字符数 |
|---|---|---|
| 介绍稿 | 阿里云 / CSDN / 腾讯云 / B站二号 | 1085 |
| 介绍稿略长 | 公众号 / B站一号 | 1195 |
| 深度稿 | 掘金 / 知乎 / 博客园 | 2674 |
| 卡片 | 小红书 | 533 |

所以「某平台薄」要先判断是不是**同一口径的平台本来就薄**，不要上来就当成缺稿补写。

---

## 2. 先厚后薄（生产顺序）

1. **新 case 起草直接写深度稿**（2000+）：一次把架构、机制、源码啃透。
2. **介绍稿 / 小红书卡片 / B站简介从深度稿裁剪派生**，不另起炉灶编。
3. 一次深写、多平台复用，事实只核查一遍。

⛔ **不许反过来**——先写薄稿再回头硬加字数。那样只能靠重复观点、堆砌数字凑长度，
结果就是腾讯云那 5 篇被拒的「灌水/技术无关内容」。

---

## 3. 加厚 = 信息增量，不是灌水

撑厚度用**真实技术细节**：

- 架构分层、模块职责（如 C++/WML 分层、数据驱动）
- 关键机制落地（如六边形寻路、AI 插件化接口、锁步同步约束）
- 源码结构、平台适配（如 SDL 可移植性、命令队列 tick 对齐）
- 每条可追溯、带时点/口径，不编造

判据与 `docs/DATA_SCHEMA.md` 的数据口径一致；**不重复同一句话说三遍、不为凑字数编造**。

---

## 4. 边界与常见误解

- **这是文档规范，不做机器硬闸。** 字数下限设成硬闸会误伤素材少的 case——
  强制凑字 = 灌水，与本规范本身矛盾。`scripts/platform_tone.py` 的 `TONE` 表仍是调性单一源，
  本规范是它的「长度维度」补充，两者不冲突。
- **只对**新写稿**生效。** 已发布文章改正文会重进审核（两朵云红线），
  不要拿本规范回头改存量已发布稿。
