# 从静态预渲染迁移到动态生成：迁移评估

> 评估日期：2026-11-20 · 状态：**建议不迁移**（附Conditionally 可行的窄方案）
> 结论一句话：当前 589 条规模下，静态预渲染的成本（每日一次、约 3 分钟、20 个对象）远低于动态化引入的运行时、鉴权、运维与测试重写成本；除非出现「写入后必须秒级可见」或「需要用户态写操作」这类**当前架构根本做不到**的需求，否则不该迁。

## 2. 先厘清动机：动态化到底能解决什么

「为什么不用动态生成」这个问题背后，必须先明确**痛点是什么**。动态化只可能解决下面三类，逐条对号：

| 潜在痛点 | 静态架构现状 | 动态化是否真能解决 |
|---|---|---|
| **A. 写入后不能秒级可见**（改数据要重建+部署，约 3 分钟延迟） | 属实。这是静态站的固有代价 | ✅ 能解决，但代价巨大（见 §4） |
| **B. 需要用户在公开站做写操作**（评论、提交案例、登录后个性化） | 做不到，公开站是只读快照、无后台 | ✅ 能解决，但会引入公网写接口（最大安全风险） |
| **C. 觉得「全量重建 590 页」浪费** | 误解：本地全量重建约 1 分钟，真正昂贵的上传已是增量（20/606） | ❌ 动态化并没有让这件事更省，只是把成本挪到了每次请求 |

**关键判断**：如果动机是 C，那评估结论直接是「不该迁」——因为痛点不成立。如果动机是 A 或 B，才需要往下看。

## 3. 三个候选方案

### 方案一：全量 SSR（公开站改成服务端动态渲染）

把 `server.py` 搬上云，每个页面请求实时查 SQLite / 渲染 HTML，公开站不再产出静态页。

- **要解决**：A + B
- **改造面**：
  - `server.py` 从 `ThreadingHTTPServer` 改为 WSGI/ASGI 入口 + gunicorn/uvicorn，或云函数 HTTP 入口（`server.py:1415` 的绑定逻辑全部重写）
  - SQLite 从本地文件迁到云数据库/持久卷——`case_store.py` 全部写盘入口要改；`data/*.json` 镜像一致性机制（PRD #63）要重做
  - 双端口模型**必须拆**：公开站与后台不能再用「绑 127.0.0.1 + 不同端口」隔离，因为上云后必须监听 `0.0.0.0`
  - 后台写接口要么单独部署到内网、要么公网暴露 + 强鉴权
- **破坏的不变量**：
  - 「公开站连 `/api/login` 都没有，撞库无门」(`server.py:17-19`) → 不复存在
  - 「零 pip 依赖」→ 引入 Web 框架 + DB 驱动
  - 「线上是只读快照，产物不含后台一行代码」(README:766-769) → 不成立
  - 「拷到哪儿都能双击打开」的 `data.js` 离线能力 → 丢失
- **新增风险**：运行时可用性（进程挂了就全站挂）、数据库连接/连接池、密钥管理上云、冷启动、DDoS 与撞库从「本地不存在」变成「头号问题」
- **测试重写**：至少 10 个静态产物/部署测试作废；`verify_deploy` 的 30+ 项断言要重写成 SSR 响应断言

### 方案二：混合式（静态为主 + 少量动态接口）

保留现有静态页做 SEO 和主体阅读，只把「需要实时/写」的功能做成独立动态服务（如单独的评论服务、提交接口），挂在同域名不同路径。

- **要解决**：B（局部）
- **改造面**：新增一个独立小服务 + 反向代理/路径转发；OSS 静态站不动
- **破坏的不变量**：少——静态主体、SEO、离线能力都保留；但「域名直连 OSS、无代理层」这条会被打破，需要引入一层路由
- **风险**：两套部署链、两个故障域；鉴权边界要重新划清
- **适用**：只有当确实出现了「用户要在公开站写东西」的真实需求时才值得

### 方案三：保持静态，但消除「3 分钟延迟」（推荐）

不动架构，只把「重建+部署」从每日定时改为**事件驱动**：本地入库 commit 后由 webhook / GitHub Actions 自动触发 `build_static` + `deploy_incremental` + `verify_deploy`。

- **要解决**：A 的大部分（把 3 分钟人工触发变成自动触发，写入即排队上线）
- **改造面**：新增一个 CI job 或 webhook，复用现有脚本，**不改 `server.py`、不动数据链路、不重写测试**
- **破坏的不变量**：无。双端口、零依赖、只读快照、SEO、离线能力全部保留
- **风险**：仅「CI 凭证保管」一项，且现有 `--env-file .env` 机制可直接沿用
- **残余限制**：仍有约 3 分钟延迟（构建+上传+校验时间），做不到真正秒级

## 4. 成本 / 收益对比

| 维度 | 方案一 全量 SSR | 方案二 混合 | 方案三 静态+事件驱动 |
|---|---|---|---|
| 消除写入延迟 | 秒级 | 不解决 | 降至自动触发（仍约 3 分钟） |
| 支持用户写操作 | ✅ | ✅（局部） | ❌ |
| 运行时故障面 | 全站 | 局部 | 无（静态托管） |
| 鉴权/撞库暴露面 | 公网后台，头号风险 | 局部接口 | 维持现状（无） |
| pip 依赖 | 新增框架+DB 驱动 | 新增小服务 | 无 |
| 数据链路改造 | SQLite 上云 + 镜像重做 | 无 | 无 |
| 测试重写 | ≥10 个 + 30+ 断言 | 少量新增 | 无 |
| SEO / 离线双击 | 需重建等价能力 | 保留 | 保留 |
| 运维负担 | 显著增加 | 中 | 基本不变 |

## 5. 迁移红线（若决定推进，逐条必须先解）

1. **双端口安全模型是刻意设计，不是技术债**：`server.py:13-19` 明确写着「分端口是因为同站 `/admin` 路径挡不住好奇的人试，会响应 401 等于昭告后台存在」。上云改监听 `0.0.0.0` 前，必须先设计好新的隔离（内网后台 / 独立域名 + IP 白名单 / 强鉴权），否则等于把核实和入库接口挂到公网。
2. **SQLite 才是真值，不是 `cases.json`**（PRD #63）：任何迁移方案第一步是确认新写入口仍走 `case_store.save_cases()` 语义，表外字段静默丢弃的老坑不能再踩。
3. **`Manifest.save()` 整本重刷**（PRD #203）与 `db.upsert_post` 空字段回填（PRD #82）等历史坑与存储层无关，但迁移期一旦有人「顺手改数据」极易复发——迁移期间应冻结非必要数据改动。
4. **SEO 判据不能退化成 SPA 空壳**：`verify_deploy` 现在断言 589 页逐个 200 + 正文内联 + sitemap 592 条。改成 SSR 后若首屏不是内联正文，爬虫又读不到内容——等于白迁还丢了 SEO。
5. **测试基线**：99 个测试中 10 个绑静态产物；迁移不是「改完能跑」就算完，必须有等价或更强的独立回读判据。
6. **每日 21:00 兜底任务 `b2e189f7`**：迁移期间不要停用，它是「上线了却没人发现没更新」的唯一自动护栏。

---

## 6. 建议

- **默认结论：不迁移。** 当前痛点（若指"重建浪费"）不成立；若指"3 分钟延迟"，用方案三即可近乎无损解决。
- **仅当出现真实的用户态写需求**（B）时，评估方案二，且后台继续保持独立部署、不公网暴露。
- **仅当出现「秒级可见」硬需求**且无法接受 3 分钟延迟时，才启动方案一，并按 §5 六条红线逐条出具解法，作为迁移的前置条件（不是迁移后再补）。
- 无论走哪条路，`docs/PRD.md` 和本评估应同步更新，避免重演 PRD #46「用户以为已经改成动态渲染」的认知偏差。
