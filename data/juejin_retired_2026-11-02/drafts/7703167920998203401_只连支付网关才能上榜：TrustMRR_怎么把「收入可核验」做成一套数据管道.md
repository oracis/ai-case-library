独立开发者之间最大的信任问题：你说的 MRR 是真的吗？

截图能 P，后台能改，故事能编。TrustMRR 的做法是把「自报」换成「直连」——用户授权只读 API key，平台自己去支付网关拉数据，算出来的收入才是可核验的。

这篇不讲它的生意经，只拆技术：**多支付网关聚合、MRR 口径统一、增量同步、以及「不可信数据源」怎么防**。

## 一、授权模型：只读 key 是这套系统的基础

它能成立的前提，是支付网关提供了**只读**权限的 API 凭据：

- Stripe：Restricted Key，可以只开 `read` 权限到 `charges`、`subscriptions`、`customers`
- LemonSqueezy：API key + 限定 scope
- Paddle：Vendor API key，读交易与订阅

技术上的要点是先明确「最小权限集」：

| 需要的数据 | 对应资源 | 权限 |
| --- | --- | --- |
| 交易金额与时间 | charges / transactions | read |
| 订阅生命周期 | subscriptions | read |
| 退款与拒付 | refunds / disputes | read |
| 客户归属 | customers | read |

**绝不能要写入权限**。这不是礼貌问题，是安全边界：一旦平台保存了可写 key，它就成了所有客户的资金风险点，任何一次数据泄露都是灾难。

## 二、数据模型：三家网关的字段根本不一样

这是这个产品最硬的工程部分——同一件事，三家网关的表示完全不同：

| 概念 | Stripe | LemonSqueezy | Paddle |
| --- | --- | --- | --- |
| 订阅状态 | `active`/`trialing`/`past_due`/`canceled` | `active`/`on_trial`/`paused`/`cancelled` | `active`/`trialing`/`past_due`/`canceled` |
| 计费周期 | `current_period_start/end`（时间戳） | `renews_at`（ISO 字符串） | `current_billing_period`（对象） |
| 金额单位 | 最小货币单位（分） | 分 | 最小单位，含 tax 字段 |
| 年付 | `interval: year` | `variant.interval: yearly` | `billing_cycle.interval` |

正确做法是先定义内部统一模型，再写适配器：

```ts
type NormalizedSubscription = {
  externalId: string;
  gateway: 'stripe' | 'lemonsqueezy' | 'paddle';
  status: 'active' | 'trialing' | 'past_due' | 'canceled';
  amountMinor: number;      // 最小货币单位，统一口径
  currency: string;
  interval: 'month' | 'year';
  currentPeriodEnd: Date;   // 全部转成 UTC Date
};
```

**统一到「最小货币单位 + UTC 时间 + 有限状态枚举」**，是跨网关数据接入的三条铁律。任何保留原始字符串格式的字段，都会在三个月后变成 bug。

## 三、MRR 怎么算才不会自欺

MRR 不是「上月收入」。它的定义是「按当前订阅状态折算的月度经常性收入」，几个必须处理的坑：

1. **年付要摊平**：年付 1200 元 → MRR 100 元/月，不能算成当月 1200
2. **试用期不算收入**：`trialing` 状态要单独剔除或标记
3. **一次性付款不进 MRR**：终身买断、加购、咨询费都属于非经常性
4. **退款要扣**：跨月的退款会同时影响历史与当期口径
5. **时区与残月**：当月未过完时，环比必须剔除残月，否则月度对比无意义

```ts
function toMrr(s: NormalizedSubscription, now: Date): number {
  if (s.status === 'trialing' || s.status === 'canceled') return 0;
  if (s.interval === 'month') return s.amountMinor;
  return Math.round(s.amountMinor / 12);   // 年付摊 12 个月
}
```

年付直接除以 12 是最常见的简化，它会让「年付用户多的月份」看起来 MRR 跳了一下。更严谨的做法是按天摊分，但大多数展示场景用简化值就够了——**前提是展示页要标注口径**。

## 四、同步管道：增量 + 幂等

支付数据会变（退款、续费失败、升级），所以不能只拉一次。

设计原则：

- **按游标增量拉**（网关都提供 `created.gte` 或 `starting_after` 之类的游标）
- **以网关事件 ID 做幂等键**，重复拉不会重复记账
- **落库用 upsert，不用 insert**，避免重放产生重复行
- **定时全量校验**（每天一次，纠偏增量漏掉的）

```sql
create table gateway_event (
  id            text primary key,      -- 网关事件 id，幂等键
  gateway       text not null,
  kind          text not null,
  payload       jsonb not null,
  received_at   timestamptz not null default now()
);
```

**幂等键必须是数据源给的，不能自造**。自造 ID（比如 hash 整条记录）在字段变化时会变成新事件，导致重复计数——这类 bug 往往在跑几个月后才被发现。

## 五、反造假：唯一的可信源是支付网关

这个产品的核心价值主张，技术上对应一个判断：

- 用户能改的东西 = 不可信（包括他自己填的表单、截图、后台数字）
- 用户改不了的东西 = 可信（支付网关的 API 返回）

所以整条链路的设计原则是：**任何展示出来的收入数字，都必须能追溯到一次网关 API 调用的原始响应**。

延伸出来的工程要求：

- 原始响应要留档（至少留关键字段 + 拉取时间），便于事后复核
- 展示页要标「数据同步时间」，否则用户会以为是实时
- 对「异常增长」要有告警（比如单日翻十倍），因为这意味着数据源出问题或者有人在刷

## 六、隐私边界

公开收入数据本身就是敏感信息。这类产品必须做的：

- 只展示聚合后的数字（MRR、订阅数），不展示客户明细
- 授权可撤销，撤销后停止同步并下架
- 数据保留期限要写明，别把历史快照永久留着

这几条不是合规部门的活，是数据模型要提前设计的（比如客户明细压根不落库，只算聚合值）。

## 七、能搬走的设计

- **最小权限 + 只读凭据**，是接第三方数据的默认姿势
- **统一内部模型 + 适配器**，多源接入的不二法门
- **口径（MRR）必须写成代码，不是写在文档里**
- **幂等键用数据源给的**，别自造
- **可信度来自架构，不来自声明**：直连网关才叫可核验
