一个完全不收费、不投广告的国际象棋平台，靠什么撑住全球几百万棋手的实时对局？

答案不在「开源情怀」，在架构选择：它把最贵的部分（实时连接、引擎分析）拆成了可以水平扩展的独立服务，主应用只做业务编排。这套拆分方式，对任何做实时多人产品的团队都有参考价值。

## 一、技术栈

- **后端**：Scala + Play Framework，主仓库 `ornicar/lila`
- **实时通道**：独立的 WebSocket 服务 `lila-ws`，不跟主应用共用进程
- **存储**：MongoDB 存对局与用户，Elasticsearch 做检索
- **引擎分析**：`fishnet` 分布式计算网络，把 Stockfish 任务分发给志愿者的机器
- **前端**：TypeScript + 自研 UI，无重型框架

这套组合的关键特征是「**每个瓶颈单独拆出去**」：棋局消息走 `lila-ws`，搜索走 ES，分析走 fishnet。主应用挂了，正在下的棋还能继续走完。

## 二、为什么 WebSocket 必须独立部署

把 WebSocket 塞进 Web 应用进程，是实时产品最常见的第一刀错误。

原因很直接：HTTP 请求是无状态的短连接，可以随便 fork 多进程负载均衡；WebSocket 是长连接，连接数与内存绑定，且每个连接只属于某一个进程。一旦和业务代码同进程：

- 部署重启 = 所有对局掉线
- 单个慢查询拖住事件循环 = 所有棋局消息延迟
- 无法独立扩容，只能整机扩

Lichess 的做法是把 `lila-ws` 做成纯消息层：它只负责连接管理、消息路由、限流，业务逻辑通过消息回传给主应用。这样两个服务可以按完全不同的节奏扩缩容。

做同类产品的可以直接抄这个边界：

```
客户端 ──WS──> lila-ws（连接/路由/限流）──内部消息──> lila（业务/落库）
                     │
                     └── 广播给对手、观战者
```

## 三、棋局状态怎么同步

棋类对局的特殊之处：**状态是确定性的**。给定初始局面和走法序列，任何人都能重算出当前局面。这带来一个极大的简化——服务端只需要广播「第 N 步走了 e2e4」，不需要广播整个棋盘。

```
服务端 -> 客户端：
  { t: "move", ply: 37, uci: "e2e4", clock: { w: 143000, b: 121000 } }
```

客户端自己维护一份走法历史，收到消息后重放。好处是消息体极小（几十字节），观战者再多也只是多播几份。

代价是客户端必须有可靠的走法引擎（合法性校验、FEN 生成）。Lichess 把这块做成了独立库 `scalachess`，前后端共用同一套规则实现——这是关键决策：**规则只写一遍，就不会出现前后端判定不一致**。

## 四、反作弊与「服务端权威」

在线棋类平台绕不开的问题：谁在算引擎。

架构上的应对是「服务端权威 + 行为留痕」：

- 每一步都记录 **时间戳与思考时长**（毫秒级），这是后续行为分析的基础数据
- 走法合法性全部在服务端复核，客户端只是 UI
- 对局历史全量落库，支持事后重放比对引擎吻合度

这件事的工程含义：**你的日志粒度决定了你能做多强的风控**。如果只存最终棋谱，事后想做「是否与引擎高度吻合」的分析就没数据了。

## 五、把引擎分析外包给用户

`fishnet` 是个值得单独说的设计：普通用户下载一个客户端，就能把自己的 CPU 贡献出来跑 Stockfish 分析任务，换取更快的分析队列优先级。

技术上它解决的是「分析任务是不可预测的突发流量」这个问题——棋手下完一局随手点分析，峰值无法预估。用志愿算力池替代自建集群，成本从固定变成弹性。

对做 AI 类产品的启发：**推理请求如果能容忍延迟（几十秒），就可以做成队列 + 分布式 worker，不必强上在线推理**。

## 六、读代码的入口

如果只想看一件事，建议按这个顺序：

1. `lila-ws` 的连接管理 —— 看长连接服务怎么做到可重启而不丢局
2. `scalachess` 的 `Game` / `Move` —— 看确定性状态重放怎么建模
3. `lila` 的 `Round` 模块 —— 看一局棋的完整生命周期

Scala 的 actor 模型和不可变数据结构在这套代码里用得很彻底，读起来门槛不低，但长期维护成本低。

## 七、门槛与限制

- 本地跑起来需要 JVM + MongoDB + Elasticsearch，依赖不轻
- Scala 3 的隐式与类型体操对不熟悉的人不友好
- 前端不用主流框架，改 UI 需要先适应它的模板系统

## 八、这套架构能搬走什么

- **长连接服务一定要独立部署**，这是实时产品的第一性原则
- **确定性状态 + 走法广播**，比广播全量状态省一个数量级带宽
- **规则库前后端共用**，避免双份实现漂移
- **日志粒度先想清楚**，风控能力上限由它决定
