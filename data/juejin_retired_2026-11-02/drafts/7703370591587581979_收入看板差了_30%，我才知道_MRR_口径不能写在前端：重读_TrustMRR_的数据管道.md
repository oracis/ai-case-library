# 收入看板差了 30%，我才知道 MRR 口径不能写在前端：重读 TrustMRR 的数据管道

> 摘要：去年给一个 SaaS 客户做收入看板。要求很简单：接 Stripe，把 MRR、订阅数、退款画成三张图。

去年给一个 SaaS 客户做收入看板。要求很简单：接 Stripe，把 MRR、订阅数、退款画成三张图。

我当时的判断是这事儿不难——Stripe 的 API 文档写得清楚，拉 `subscriptions` 和 `charges`，存原始 JSON，前端按需计算。一周上线。

上线第二天客户发来一条消息：「我这个月 MRR 应该是 8000 左右，你这个图上写 10400。」

我去查，发现四个错叠在一起：年付被我整笔算进了当月、试用期用户被算成了付费、上个月的一笔退款没扣、还有一个客户因为改了账单地址被重复计了一次收入。四个错的方向不都一样，有的让数字偏高有的偏低，最后凑出来一个「看起来像真的」的 10400。

那天之后我才去认真看 TrustMRR 是怎么做的——一个把「独立开发者的收入可核验」当产品卖的服务。它的做法是把自报换成直连：用户授权只读 API key，平台自己去支付网关拉数据。技术上有几件事我踩过，它做对了。

## 第一版我把原始 JSON 全存下来，前端现算

这是最初的设计，也是后面所有错的源头。

我的想法是「保留原始数据最灵活，以后要什么口径都能算」。听起来没错，但实际后果是：**同一个 MRR 有四处实现**——看板前端算一遍、月度邮件报表算一遍、导出 Excel 算一遍、客户问起来我手动查一遍。四处都不完全一样。

其中一处忘了摊平年付，一处把 `trialing` 算进去了。因为没人定义过「MRR 是什么」，每个地方都按当时的直觉写。

TrustMRR 这种多网关聚合系统的做法是反过来的：先定义内部统一模型，再写适配器，让口径只存在一份代码里。

```ts
type NormalizedSubscription = {
  externalId: string;
  gateway: 'stripe' | 'lemonsqueezy' | 'paddle';
  status: 'active' | 'trialing' | 'past_due' | 'canceled';
  amountMinor: number;      // 最小货币单位，统一口径
  currency: string;
  interval: 'month' | 'year';
  currentPeriodEnd: Date;   // 全部转成 UTC Date
};
```

**统一到「最小货币单位 + UTC 时间 + 有限状态枚举」**，这三条不是洁癖。金额留原始字符串，三个月后就会有人在 `"1,200.00"` 上做加法；时间留各家的格式，跨时区的月度对比永远对不齐。

我后来的改法是：原始 JSON 照样留档（事后复核要用），但入库的同时立刻映射成规范化表，所有计算只读规范化表。四处实现变成一处，剩下三处都调它。

## 年付那 12 倍，我算错了两次

第一次是整笔计入当月：客户年付 1200，那一月 MRR 图表直接冲上天，下个月掉回地板。图表像心电图。

改成除以 12 之后，第二次错来了：**除 12 会让「年付用户集中续费的月份」MRR 跳一下**。因为每笔年付都在它成交的那个月开始被摊成 12 份，如果一批客户都在 3 月成交，3 月到次年 2 月的 MRR 都会带着这 12 个月的份。

更严谨的做法是按天摊分，让每份收入落在它实际覆盖的那一天上。TrustMRR 这类展示型产品大多用简化值（年付 ÷ 12），前提是**展示页要标注口径**——这一点比算法本身重要。客户能接受「这是近似值」，不能接受「这个数字我不知道怎么来的」。

我最后改成了按天摊：日收入 = 年付金额 ÷ 365，累加到当月。多写了三十行代码，换来的是客户不再每个月来问一次为什么数字跳。

顺带把其余几个坑一起处理了。试用期要单独剔除或标记，`trialing` 状态不产生收入；一次性付款（终身买断、加购、咨询费）不进 MRR，它是非经常性的；退款要扣，跨月退款会同时影响历史和当期两个口径；当月没过完时做环比，必须剔除残月，否则「这个月比上个月少」永远成立。

这些规则现在写在一个 `toMrr()` 函数里，有单元测试，有注释说明每条的来源。写在文档里的口径等于没写。

## 我自造的幂等键，让一笔钱记了两遍

那个「改账单地址导致收入重复」的 bug，根因在这儿。

第一版同步是每小时拉一次全量订阅，落库用 `insert`，重复的行靠 `external_id` 去重。我以为这样就幂等了。

问题在于：Stripe 的订阅对象在客户改地址后，`updated` 时间变了，我当时的逻辑是「按 `updated.gte` 增量拉 + insert」，于是同一条订阅被插了第二行。收入乘二。

正确的做法是**用数据源给的事件 ID 做幂等键**，落库用 upsert：

```sql
create table gateway_event (
  id            text primary key,      -- 网关事件 id，幂等键
  gateway       text not null,
  kind          text not null,
  payload       jsonb not null,
  received_at   timestamptz not null default now()
);
```

自造 ID 有个隐蔽的坑：如果你用「hash 整条记录」当键，那么任何字段变化都会变成一个「新事件」——在收入场景里，这不是去重失败，是**凭空多出一笔钱**。这类 bug 往往几个月后才被发现，因为数字一直是「缓慢偏高」，不像故障那么显眼。

我后来的管道是四件事：按游标增量拉（网关都提供 `created.gte` 或 `starting_after`）；以网关事件 ID 为幂等键；落库 upsert；每天跑一次全量校验，纠偏增量漏掉的。最后这条是兜底——增量一定会有漏的时候，区别只在于你有没有发现它的机制。

## 接第三家网关，我才发现字段名全是方言

客户后来又加了 Paddle。我以为加个适配器就行，结果发现同一件事三家的表示完全不同：

| 概念 | Stripe | LemonSqueezy | Paddle |
|---|---|---|---|
| 订阅状态 | `active`/`trialing`/`past_due`/`canceled` | `active`/`on_trial`/`paused`/`cancelled` | `active`/`trialing`/`past_due`/`canceled` |
| 计费周期 | `current_period_start/end`（时间戳） | `renews_at`（ISO 字符串） | `current_billing_period`（对象） |
| 金额单位 | 最小货币单位（分） | 分 | 最小单位，含 tax 字段 |
| 年付 | `interval: year` | `variant.interval: yearly` | `billing_cycle.interval` |

注意 `cancelled` 和 `canceled`——一个字母的差别。我第一版的状态映射里漏了这一条，导致 LemonSqueezy 的取消订阅被判成未知状态，进了「其他」桶，既不算收入也不算流失。数字上看不出来，因为「其他」桶没人看。

这就是为什么必须先有内部模型再有适配器，而不是反过来：**如果你先接三家再想统一，你的模型会长成三家的并集**，字段一大堆，每个都有 `_stripe`、`_paddle` 后缀。

## 只读 key 这条线，我一开始越了

做看板的时候，客户很自然地给了我一把完整的 Stripe key（他也不知道有只读的）。我就用了。

TrustMRR 这类产品的技术前提，是支付网关提供了**只读**权限的凭据：Stripe 的 Restricted Key 可以只开 `read` 到 `charges`、`subscriptions`、`customers`；LemonSqueezy 是 API key 加限定 scope；Paddle 用 Vendor API key 读交易与订阅。

最小权限集大概是这四块：交易金额与时间（charges/transactions）、订阅生命周期（subscriptions）、退款与拒付（refunds/disputes）、客户归属（customers）。

**绝不能要写入权限**。这不是礼貌问题。一旦你的系统保存了可写 key，它就成了所有客户的资金风险点——任何一次数据泄露都不再是「泄露了收入数据」，而是「有人能给你的客户退款、改价格、删订阅」。

我把那把完整 key 换成了 Restricted Key，只开三个 read scope。功能一点没少。

还有一层：**可信度来自架构，不来自声明**。用户能改的东西都不可信（表单、截图、后台数字），改不了的才可信（网关 API 返回）。所以任何一个展示出来的收入数字，都必须能追溯到一次网关调用的原始响应——原始响应要留档（关键字段 + 拉取时间），展示页要标同步时间，异常增长要告警（单日翻十倍通常不是好消息，要么数据源坏了，要么有人在刷）。

## 我最后没做的部分

**没做实时同步**。一开始我想上 webhook，收到事件就更新。后来放弃了：收入看板不是交易系统，延迟一小时没有任何业务影响，而 webhook 要处理重放、乱序、失败重试，成本远高于收益。我改成每小时拉一次，展示页写「数据同步于 X 点」，客户的信任度反而比「实时」更高——因为数字是可解释的。

**没做多币种换算**。客户有欧元订阅，我本来想统一折成美元。做了一半停了：汇率来源、取哪一天的汇率、历史快照要不要重算，每个都是坑。最后按原币展示，只把「同币种 MRR」汇总，跨币种给个「约」字和汇率日期。把不确定的东西标出来，比假装算准了强。

**没做客户明细展示**。公开收入数据本身就敏感，这家产品的做法是只展示聚合值（MRR、订阅数），不展示客户明细，授权可撤销、撤销后停止同步并下架，数据保留期限写明。最彻底的一条是客户明细压根不落库，只算聚合值——这不是合规部门的活，是数据模型要提前设计的东西。我照抄了这条，省了后面一堆麻烦。

## 搬走的是五句话

最小权限加只读凭据，是接任何第三方数据的默认姿势，不是可选项。统一内部模型加适配器，多源接入没有第二条路。口径必须写成代码，写在文档里的等于没写。幂等键必须用数据源给的，自造的键会凭空生出钱来。可信度来自架构，不来自声明——直连网关才叫可核验。

数据来源：产品公开页面与支付网关官方文档（2026-10 快照）。TrustMRR 的产品逻辑是「只连支付网关才能上榜」，技术实现就是我上面拆的这条管道。
