我把 WebSocket 塞进业务进程，上线三天掉了两次线：重读 Lichess 的架构

万物解释者
2026-11-02 0 阅读1分钟

去年给一个项目加实时对战功能，我的第一反应是找现成的参照物。Lichess 是最合适的那个：不收费、不投广告，全球几百万棋手在上面下棋，代码还全开源。我当时的想法很朴素——照着它的模块划分抄一遍，总不会错到哪去。

结果第一版上线三天，掉了两次线。回头再读它的代码，才发现我抄了目录结构，没抄到它真正的边界。

第一版：WebSocket 和业务代码住在同一个进程里

我最初的部署是这样的：一个应用进程，HTTP 接口和 WebSocket 都在里面，棋局逻辑也写在同一套代码里，共用同一个事件循环。

上线第一天的表现就已经不对了。发一次版，所有正在对局的人一起掉线——因为重启进程等于掐断所有长连接。第二天更难看：有人在后台导出一份历史对局，MongoDB 慢查询把事件循环占了几秒，那几秒里所有棋局消息全堵住，前端看起来就是"对手不动了"。

这两件事其实是同一个原因：长连接和业务请求的伸缩维度不一样。HTTP 请求是无状态的，短、可丢弃、随便 fork 几个进程做负载均衡都行；WebSocket 是有状态的，一个连接只属于某一个进程，连接数和内存绑死。把它们放进同一个进程，就等于强迫两者用同一套扩容策略——只能整机扩，而且互相拖累。

Lichess 的处理方式是独立出一个 lila-ws 服务。它不是"把 WebSocket 抽成一个模块"，而是抽成一个只有连接管理、消息路由、限流的纯消息层，业务逻辑一律通过内部消息回传给主应用 lila。两个服务可以按完全不同的节奏扩缩容，主应用发版重启的时候，连接层不用跟着死。

客户端 ──WS──> lila-ws（连接 / 路由 / 限流）──内部消息──> lila（业务 / 落库）
                     │
                     └── 广播给对手、观战者

我把连接层拆出去之后，第一次做到了"发版不影响进行中的对局"。这一步没有任何技术难度，纯粹是边界划错了。

广播整盘棋是我犯的第二个错

拆完连接层，新的瓶颈立刻暴露：带宽。

我一开始的同步方式是每步棋广播一次完整的棋盘状态（FEN 串加双方计时）。单人对局看不出问题，一场有百来号观战者的对局，流量直接顶到出口上限。

后来看 Lichess 的消息格式，它是这样的：

{ t: "move", ply: 37, uci: "e2e4", clock: { w: 143000, b: 121000 } }

只广播"第 37 步走了 e2e4"。没了。因为棋类是确定性游戏——给定初始局面和走法序列，任何人（包括浏览器）都能自己重算出当前局面。客户端维护一份走法历史，收到消息后本地重放即可。消息体从几百字节降到几十字节，观战者再多也只是多播几份同样的小包。

这个设计有个前提：客户端必须有一份可靠的走法引擎，能做合法性校验和 FEN 生成。Lichess 的做法是把这块做成独立库 scalachess，前端和后端共用同一套实现。

我认为这才是它最值得抄的一个决定。规则只写一遍，就不会出现"客户端认为这步能走、服务端认为不能"的漂移。我在自己项目里图省事，前后端各写了一份走法校验，结果上线两周内被抓出三次不一致——一次是吃过路兵，一次是王车易位的条件判断，还有一次是三次重复局面。这类 bug 极其难查，因为两边都"看起来是对的"。

反作弊的瓶颈根本不在算法

在线棋类平台绕不开一个问题：谁在用引擎算。

我一开始以为这是个检测算法问题，去研究什么吻合度模型。看了 Lichess 的落地方式才明白，它首先是个数据采集问题——服务端对每一步都记录时间戳和思考时长，精确到毫秒，并且走法合法性全部在服务端复核，客户端只当 UI 用。

没有这些数据，事后再强的模型也没东西可跑。如果只存最终棋谱，你连"这步棋想了 80 毫秒"都不知道，谈何判断是不是引擎给的。

所以真正的工程结论是：日志粒度决定了风控能力的上限，而这个决定必须在写第一行落库代码的时候就做,后面补不回来。我后来给每步棋加了耗时字段，代价是历史对局全部没有这个数据，等于只有新对局可分析。

算力不够的时候，可以不买机器

fishnet 是我看完最意外的设计。它让普通用户下载一个客户端，把自己的 CPU 贡献出来跑 Stockfish 分析任务，换取更快的分析队列优先级。

它解决的问题很具体：棋手下完一局随手点"分析"，这是典型的不可预测突发流量，峰值可能是均值的十几倍。自建集群意味着按峰值买机器，绝大部分时间是闲置的。志愿者算力池把固定成本变成了弹性成本,代价是排队时间不可控。

这条思路可以推广：推理请求只要能容忍几十秒延迟，就该做成队列加分布式 worker，而不是硬上在线推理。我在另一个项目里做图片处理，原来按峰值配了四台机器，改成队列之后两台机器足够，用户多等三秒基本无感。

照抄的时候我放弃了什么

Lichess 是 Scala 写的，Play Framework、actor 模型、大量不可变数据结构。我读完的感受是：这套东西长期维护成本确实低，但读代码的门槛相当高，尤其 Scala 3 的隐式和类型体操部分，我看了两遍也没完全吃透。

所以我没有搬语言，只搬了三个边界：

一是连接层独立成服务，跟业务进程分开部署、分开扩容；二是状态同步只传增量，规则实现前后端共用同一份；三是日志粒度在建模阶段就定下来，别等出事再补。

其余的部分——MongoDB 存对局、Elasticsearch 做检索、前端不用重型框架——这些是它的历史选择，搬到新项目里未必合适。我最后还是用了关系型数据库，因为我的查询模式简单得多，没必要为了"和大厂一样"去扛一套分布式检索。

读完这套代码最大的收获不是某个具体实现，而是它把每个瓶颈都单独拆出去的那种克制：主应用只做业务编排，贵的部分（长连接、搜索、分析）各自独立。想清楚哪一部分会先撑不住，比抄对目录结构重要得多。

源码在 ornicar/lila、ornicar/lila-ws、lichess-org/scalachess 三个仓库，许可证以各自仓库为准。
