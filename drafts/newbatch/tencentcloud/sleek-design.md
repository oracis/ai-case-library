# 生成一整套风格一致的界面：设计 token、中间表示与多目标导出

Sleek.design 是一个 AI 移动应用设计工具：用自然语言描述 App 创意，它生成整套风格一致的 iOS/Android 界面，可编辑、可导出到 Figma、HTML、React，也能通过接口接入 Claude Code、Cursor 这类编码 agent。

同类产品很多，容易被当成又一个「AI 生成 UI」的壳。但从工程角度看，这类工具真正的难题只有三个，而且都不是「生成得好看」：**一套界面之间怎么保持一致**、**生成结果怎么落到可编辑的结构上**、**同一份设计怎么导出成三种完全不同语义的目标**。

据创始人在 Indie Hackers 的自述（2026 年 1 月），产品上线约一个月做到每月 1 万美元 MRR，零付费营销；官网当前口径是 6 万以上 app 开发者使用。创始人 Mattia Pomelli 与两位朋友远程合伙（意大利），此前做过四个设计工具都没起量，这次用 3 周搭出第一个版本。

> 数据时点 ｜ 2026-01（创始人自述）｜收入口径：月经常性收入（MRR），创始人个人披露

## 一、单屏好看容易，一套界面一致很难

生成一个漂亮的登录页，现在的模型几乎都能做到。生成 12 个屏幕、彼此之间像同一个产品，难度完全不在一个层级。

一致性由四个可见维度构成：

- **色彩**：主色、辅助色、语义色（成功/警告/错误）、背景层级；
- **字体**：字号阶梯、字重、行高；
- **间距**：一套固定的间距刻度（4/8/12/16/24…），页面之间必须复用同一套；
- **形状**：圆角半径、阴影层级、边框粗细。

模型单独生成每一屏时，这四项会在屏与屏之间漂移：第二屏用了 14 号字，第五屏用了 15 号；圆角在三个地方是 8、两个地方是 12。人工看单屏看不出来，但把 12 屏并排放在一起，立刻能感觉「不像一个产品」。

解决办法不是让提示词更严格，而是**先确定 token，再生成**：

1. 从用户的一句话描述里推出一个设计方向（色系、风格关键词、圆角倾向）；
2. 把这个方向固化成一份 token 表（颜色变量、字号阶梯、间距刻度、圆角/阴影档位）；
3. 每个屏幕的生成只允许使用 token 表里的值。

这就把「一致性」从模型的自觉变成了**结构上的强制**。任何生成结果里出现 token 之外的值，都是可检测的错误。

## 二、自然语言之后，必须落到结构上

第二步是中间表示。如果模型直接输出一段 HTML，产品就只能做「看」和「下载」，做不了「可编辑」。

要支持编辑，生成结果必须是一棵组件树：每个节点有类型（容器/文本/图片/按钮）、有属性、有子节点。用户点一下某个按钮，工具要知道「这是组件树里的第几个节点」，才谈得上改它的文案或颜色。

这条链路的形态通常是：

**自然语言 → 组件树（JSON）→ 渲染器 → 屏幕**

组件树这一层是整个产品的核心资产。它的好处在三个地方体现：

- **编辑**：改动落到具体节点，不需要重新生成整屏；
- **换肤**：改一份 token 表，所有屏幕的配色/圆角同时变；
- **校验**：可以写规则检查「这个按钮的可点区域是否小于 44 点」「这段文字对比度是否达标」，这些检查在纯图片或纯 HTML 上做不到。

代价是组件树必须提前定义好一套词汇表：哪些组件类型允许存在、每个类型允许哪些属性。词汇表太窄，生成结果表达不了复杂布局；太宽，渲染器和导出器都要跟着爆炸。这个取舍基本决定了产品的天花板。

## 三、多目标导出：Figma、HTML、React 是三种语义

「导出到 Figma / HTML / React」听起来是三个格式转换器，实际是三种完全不同的东西：

- **Figma** 是**设计态**：它关心图层、约束、自动布局（auto layout）、组件实例。导出时要把组件树翻译成 Figma 的节点体系，并尽量用 auto layout 而不是绝对定位——否则设计师拿到手完全改不动。
- **HTML/CSS** 是**呈现态**：它关心盒模型、flex/grid、响应式断点、字体加载。这里最容易犯的错是把所有东西都写成绝对定位，页面看起来对，但改一个字号就全乱。
- **React** 是**工程态**：它关心组件拆分、props、状态、可复用性。一段能跑的 JSX 不等于一份能维护的代码——把 12 个屏幕各自导成一个巨型组件，前端开发者会直接删掉重写。

同一个中间表示导出三种目标，必然有信息损耗。真正决定产品价值的不是「能不能导出」，而是**导出物在目标环境里能不能继续被改**。设计师打开的 Figma 文件如果全是绝对定位的矩形，这个导出等于没做。

这也是这类工具的分水岭：把它当「生成图片」的产品，用户拿走截图就走了；把它当「生成可维护结构」的产品，用户会长期留在里面改。

## 四、credits 分档本质是成本控制

定价是每月 29、69、99 美元（团队档按人计），按 AI credits 分档。免费层只允许一次生成。

这套设计的工程含义比商业含义更直接：**生成一次界面的成本远高于一次文本对话**。一次完整的 App 设计要生成十几屏，每屏可能涉及多轮修正，背后是几十次模型调用。如果不限额，一个免费用户就能产生可观的账单。

三个设计细节值得注意：

1. **免费层只给一次**。它同时完成了两件事：把滥用成本压到接近零，以及筛出真正的付费意愿——只想试试的人用完就走，不需要做复杂的反滥用系统。
2. **按 credits 而不是按「次数」**。按次数计价会让用户把「生成一屏」和「重做整套 12 屏」看成同一件事，而实际成本差十倍。credits 让消耗与成本对齐。
3. **档位差值设计得大**（29 到 69 到 99）。中间档的存在意义往往不是让人买，而是让高档看起来合理。

对做同类产品的人来说，这里最该抄的不是价格，是「**免费额度必须与单次成本挂钩**」这个原则。任何生成成本高于文本的产品，无条件免费试用都是在给账单做慈善。

## 五、把设计工具做成 agent 的一个工具

这个产品比较特别的一点是：它通过接口把自己接进了 Claude Code、Cursor 这类编码 agent，成为 agent 可以调用的一个能力。

这个方向值得单独说，因为它改变了产品的定位：从「一个你要打开的工具」变成「写代码过程中的一个步骤」。

工程上这要求三件事：

- **能力要原子化**。agent 不会「打开你的界面设计一下」，它只会调用明确的功能：根据描述生成一套屏幕、把某个屏幕改成深色、导出 React 代码。每个功能必须是确定性的输入输出。
- **返回要可被机器消费**。给人类看的是截图，给 agent 看的必须是结构化描述（组件树、token 表、文件路径）。返回一张 PNG 对 agent 毫无用处。
- **失败要能解释**。agent 拿到「失败了」不知道怎么办，需要的是「哪一步失败、缺什么参数、可以怎么重试」。

这个转变对产品的要求比做 UI 高得多：UI 可以模糊，接口不能。但从增长角度看，这是当下最有效的一条分发路径——当开发者在写代码时顺手调用了你的工具，获客成本接近零。

## 六、3 周做出第一个版本，因为前面有四个失败品

创始人此前做过四个设计工具，都没起量。第五个 3 周就出了 v1。这个速度不是因为他变快了，而是因为**前四个已经把最难的部分做完了**：组件树的结构、渲染器、导出器、token 体系，这些是可以跨产品复用的底层。

这也是独立开发者最容易被误解的地方。外界看到的是「3 周做出一个产品」，实际是「3 周加上前面几年的积累」。可复制的做法是：**每次做新产品时，把与业务无关的部分（渲染、导出、支付、鉴权）沉淀成可复用的层**，下一个产品的启动成本会指数级下降。

不可复制的部分是运气与时点——这类工具正处在平台红利期，早一年做没人要，晚一年做已经拥挤。
