# 校验 API 的三级级联：延迟预算、结果缓存与计量幂等

一个 API 做三件事：判断一个电话号码是不是真的、一个邮箱能不能送达、一个 IP 值不值得信任。按调用量计费，卖的不是数据列表，是「调用那一刻的判定」。

这类系统看起来简单——查表而已。真正做起来，难点全在工程侧：怎么在客户同步调用的链路里把 P99 压住、怎么让三档校验的成本可控、怎么在「不落库」的约束下做到足够高的命中率，以及按调用量计费时怎么定义一次「调用」。

## 一、为什么必须分级，而不能一把梭

最朴素的做法是每次都跑完整校验：查号段、做 MX 查询、SMTP 握手、拉 IP 画像。问题是这些动作的成本差了两三个数量级。

- 语法与规范化：纯本地计算，微秒到毫秒级。手机号转 E.164、邮箱做 RFC 5322 结构检查与域名 IDN 归一、IP 判断公网/私网/保留段。
- 存在性查询：有网络往返。邮箱要先查 MX 记录再决定是否握手；号码要查号段归属与在网状态。这一档的耗时由 DNS 和运营商侧决定，通常几十到几百毫秒。
- 风险画像：最贵。IP 要叠加代理识别、机房段、历史行为统计，往往要读多份数据源。

把三档串成一条固定流水线，等于给所有调用都付最贵的成本。合理的做法是按级联触发：第一档挡掉明显脏数据，第二档只在需要时跑，第三档由调用方显式点名要。

代价是接口语义变复杂。一次调用到底跑了几档、降级时返回什么，必须写进契约，否则客户没法在业务里正确使用。

## 二、延迟预算决定架构，不是准确率决定架构

这类 API 的调用点几乎都在关键路径上：注册、登录、下单、线索入库。客户在这些位置调一个外部接口，能容忍的时间窗口非常窄。行业里常见的做法是给整条链路留 200 到 500 毫秒，校验这一段分到 100 毫秒左右就已经很紧。

于是一个反直觉的结论：架构首先被延迟预算约束，而不是被准确率约束。具体体现在几处：

**超时必须可预期。** 给每一档设独立预算，而不是给整个请求一个总超时。SMTP 握手慢的时候，不该拖着语法校验一起超时。

**降级要有明确语义。** 超时返回「未能判定」还是返回「疑似无效」，是完全不同的业务后果。前者客户可以放行后异步复核，后者会直接拦掉真实用户。这类 API 必须把「不知道」当成一个正式结果返回，而不是伪装成「否」。

**缓存是成本杠杆也是延迟杠杆。** 同一个号码会被多个客户反复查，跨客户的短期结果缓存能把命中率拉起来。但这里有个必须守住的边界：缓存的是「校验结论」，不是「采集到的原始数据」，且 TTL 要短到不足以构成一份可被反查的号码库。

## 三、不落库不是洁癖，是架构约束

手机号和邮箱属于个人信息，国内做这类服务绕不开《个人信息保护法》这条线。可行的路径只有一条：做不落库的实时校验——请求进来、算完、返回、不留原始值。

这个约束会反过来改变系统设计：

- 日志不能记原始号码和邮箱，只能记哈希或请求元信息；排障只能靠 request_id 回捞，靠样本复现问题。
- 缓存键要用加盐哈希，且不能反解；跨客户共享缓存时，还要防止用缓存命中与否去推断某个号码是否存在。
- 计费与统计全部走聚合计数，不保留明细——这也顺带解决了「按调用量计费」的数据基础问题。

很多团队是先做完系统再补合规，最后被迫重构存储层。把「不落库」当成第一天就定下的约束，反而少走一遍。

## 四、按调用量计费，先得定义「一次调用」

计费单位是调用次数，那计费系统就成了核心链路的一部分。几个必须明确的语义：

**重试怎么算。** 客户网络抖动重发同一个请求，算一次还是两次。工程上的通行做法是要求带幂等键（比如客户侧生成的 request_id），服务端在短窗口内去重返回同一结果，只计一次。

**超时怎么算。** 服务端已经开始跑，客户侧先超时断开，这次算不算。偏向客户的做法是不计费，但要有防止被刷的限流。

**部分成功怎么算。** 一次请求查了三档，第三档数据源超时，返回了前两档结论。这属于一次已完成的调用，应当计费，但要在响应里把未完成的档位标出来。

这些语义不定清楚，账单迟早会变成客服工单。更麻烦的是计量链路的可用性：计量服务挂了不能让校验也挂，通常要做成本地缓冲 + 异步对账，接受短时间的计数延迟。

## 五、产品线扩张时，接口形状比单个能力更重要

从单一校验扩到多类校验，最常见的失败是每加一种能力就加一套参数、一套错误码、一套超时语义。客户集成成本随能力数量线性上涨，最后没人愿意接第三种。

可维护的做法是先把请求形状统一：一个鉴权 key、一套错误码、一致的分档语义、统一的批量接口。能力差异放在「校验类型」这个字段上，不在接口形态上。

批量接口尤其值得提前设计。单条校验的客户往往最终会变成批量场景（导入一万条线索时，没人愿意发一万个请求），批量接口的并发上限、部分失败返回、结果顺序保证，都是后期很难补的。

## 六、真正的壁垒在反馈闭环

这类工具的功能列表很好抄：谁都能写正则、能查 MX、能调公开的 IP 库。难抄的是准确率——而准确率来自样本反馈。

什么样的邮箱是「格式正确但实际废弃」、什么样的号码是「在网但已停机」、哪些 IP 段是「新上的机房还没进任何公开库」，这些判断只能靠客户标记的误判样本一点点修。客户越大，反馈样本越多，准确率越高，迁移成本也就越高。

这也是这类生意复购稳的原因：客户换供应商要改代码、要重测准确率、要承担一段时间的误判上升。迁移成本天然高于普通 SaaS。
