# 借别人的编辑器交付：AI 生成演示文稿的插件架构、结构化输出与排版兜底

MagicSlides 是一个「把主题或文档变成 PPT」的工具：输入一个主题、一段文档甚至一个链接，AI 生成大纲和每页文案，再通过 Google Slides / PowerPoint 的插件直接导出成可以继续编辑的演示文稿。

它值得做工程拆解，不是因为它技术多深，而是因为它把三个工程问题摆得很清楚：**自研编辑器还是借别人的**、**怎么让模型输出可以直接落页的结构化数据**、**文本长度不可控时排版怎么兜底**。这三件事跟产品规模无关，做任何「生成内容到既有载体」的系统都会遇到。

## 一、借编辑器交付不是偷懒，是架构决策

做演示文稿生成，最常见的错误路线是一上来就自研在线编辑器：渲染、撤销重做、协作、导出兼容性，每一项都是几个月的工程。MagicSlides 的选择是把交付面完全架在 Google Slides 和 PowerPoint 上——用户装一个插件，生成结果直接出现在用户自己的演示文稿里，后续编辑、批注、协作全部复用既有生态。

这个决策的收益是结构性的：

- **交付质量下限由平台兜底**。Google Slides 的排版引擎是现成的，生成的每一页都是真实可编辑的形状与文本框，不是截图或私有格式，用户不会遇到「导出来是乱的」这种致命体验。
- **工程预算全部压到生成质量**。编辑器省下来的工时，可以全部投到大纲结构、文案质量、配图策略上，而这恰恰是这类产品唯一真正的竞争点。
- **信任借自平台**。企业用户对「装一个来历不明的编辑器」的戒备远高于「在 Google Workspace 里装一个插件」。

代价也要认：插件受宿主 API 的能力边界约束。Google Slides API 的批量更新接口只能创建形状、文本框、表格这些基础对象，无法直接复用网页端的智能排版，所以「怎么把内容放进页面」的排版责任，全部落在了插件自己的代码里——这就引出了第三个问题。

## 二、从输入到可落页的结构：生成必须是 schema 约束下的输出

「AI 做 PPT」如果理解为「让模型自由发挥写一堆文字再渲染」，产物必然是不可用的。MagicSlides 这类工具真正的工作流是把生成任务拆成两层约束：

1. **大纲层**：先让模型产出页级结构——每页一个标题、三到五条要点、可选的备注。这一层的输出用固定 schema 收口（页数上限、字段齐全性校验），不合格就重试，而不是把半成品往下传。
2. **内容层**：每页的要点按字数预算生成。演示文稿每页能放的文字量是物理有限的，提示词里直接给长度约束，比生成完再裁剪稳定得多。

输入形态也值得说：主题、文档、链接、视频转写，四种输入对应完全不同的预处理。文档要抽取层级结构（标题层级就是天然的章节划分），链接要做正文提取并处理反爬，视频转写要先分段再归纳。**输入形态越多，预处理矩阵越复杂**，这是功能列表上看不出来、实现时才知道的成本。

## 三、排版兜底：文本长度不可控是常态

LLM 的输出长度有随机性，而幻灯片的版面是刚性的——文本框就那么大，超了就是溢出。工程上能做的兜底是一个分级策略：

- **生成时约束**：提示词里按要点给字数预算，从源头减少超长；
- **插入时检测**：用字符数估算 + 字体度量估算文本高度，超过文本框容量就触发降级；
- **降级路径**：先缩字号（有下限，比如不低于 14pt，再小就不可读了），再减条目（合并语义相近的要点），最后才允许溢出并由用户手动处理。

另一层是**母版与主题映射**。生成的页面要套用户的品牌色和字体，正确做法不是逐个覆盖样式，而是让内容对象引用宿主的布局（layout）——标题占位符放标题、双栏布局放对比内容——这样用户换主题时整份文稿仍然跟着走。逐对象硬编码样式是这类插件最常见的返工原因。

## 四、配图：生成、检索还是占位

演示文稿的配图是个三选一：AI 生图、图库检索、留占位框。MagicSlides 的选择（公开形态可见）偏检索与占位，这在工程上是合理的：AI 生图按次计费，用户为一页 PPT 付一张图的成本不划算；图库检索有版权边界要处理；留占位框把选择权还给用户，成本最低、投诉最少。

**给「够用就好」的功能留人工兜底，比全自动但偶尔离谱更省客服成本**——这是配图链路给出的通用结论。

## 五、这类产品的成本落在哪

不在算力，在**兼容面**。Google Slides 和 PowerPoint 是两套 API、两种扩展机制（Apps Script 生态 vs Office Add-in 体系）、两套排版行为。同一个「在第 3 页插一个两栏对比」的操作，两边的设计路径完全不同。双平台维护意味着每个排版功能都要做两遍，且 PowerPoint 的桌面版与网页版渲染还有差异。

商业结果可以给一个参照：截至 2026-09-20（TrustMRR 快照，Stripe API 直读口径），MagicSlides 的 MRR 约 11,332 美元、累计收入约 71.5 万美元、活跃订阅 825 个——2023 年 1 月上线，一个人借两个成熟编辑器交付，撑起一门订阅生意。数字是快照不是现值，别拿累计数年化。

一个反直觉的结论：这类「生成到既有载体」的产品，核心竞争力不在模型，在**对宿主平台 API 的熟悉程度和排版兜底的完备性**。模型能力大家都在同一起跑线上，而「插进 Slides 不溢出、不破坏母版」这种脏活，恰恰是门槛所在。
