# CheckVibe：给 AI 生成的应用做安全扫描，工程上要拆解的六个问题

用 AI 快速生成（vibe-coded）的应用有个共同点：从想法到能跑的页面只需要很短时间，但依赖清单、环境变量、鉴权边界、后台接口往往是一路补出来的。功能能演示，不代表暴露面被认真收过一遍。给这类应用做自动安全扫描，值得拆的不是「用了什么模型」，而是下面六个工程问题——它们跟产品做多大无关，任何扫描系统都会遇到。

## 一、先定「扫什么」：URL、仓库，还是部署产物

三种输入形态得到的是三份完全不同的证据。

- **一个线上 URL**：只能看到对外暴露的部分，看不到构建配置和依赖树，但能看到真实的运行时行为（响应头、错误页、重定向链）。
- **一个源码仓库**：能读依赖清单、路由定义、配置文件，却看不到部署时注入的环境变量，也看不到网关层加的防护。
- **部署产物或镜像**：介于两者之间，能拿到实际打包进去的依赖版本，但仍不等于线上行为。

很多误判来自把三种口径混在一张报告里：仓库里没有的漏洞，线上网关可能已经挡了；线上看不到的硬编码，仓库里其实还留着。所以报告第一件事不是列问题，而是写清楚这次扫的是哪个面、哪些结论不能从这个面推出。

## 二、暴露面枚举：别把发现阶段做成压力测试

黑盒扫描的第一道活是把路径和接口找出来。常见来源有站点地图、静态资源里引用的路由、前端打包文件里的路由表、框架默认的错误页与调试端点。AI 生成的项目因为常复用同一批脚手架，路由形态会有规律，但这只能当提示，不能当假设——真正需要的是「发现了什么」而不是「猜应该有什么」。

这一阶段有两个容易翻车的点：

1. **并发与限速**。扫描器对目标站是外部流量，默认必须限速、设总请求上限、对连续 5xx 立即退避。否则一轮扫描自己就把站点打挂了，报告还没生成就先制造了一次故障。
2. **递归边界**。遇到分页、日历、无限滚动、带随机参数的链接，不做归一化就会无限展开。比较稳的做法是对 URL 做归一化后按「路径模板」去重，同一模板只探有限个实例。

## 三、误报控制：安全扫描产品真正的分水岭

「收到一个可疑响应」和「存在一个可利用漏洞」之间隔着很远。返回了堆栈信息不等于能执行代码，某个依赖版本在库里不等于该版本的代码路径可达，页面里出现一段像密钥的字符串也不等于它有效。

要把误报压下来，报告里每条结论至少得带齐四样东西：

- **触发条件**：具体请求方法、路径、参数；
- **证据片段**：请求与响应里能支撑判断的那几行，而不是整页 HTML；
- **复现步骤**：用户自己能照着再跑一遍；
- **判定等级**：确认 / 疑似 / 信息项，明确分开。

对付费产品来说，误报的代价通常比漏报更高：用户按报告改了两轮没修好，第三次就不会再打开。因此「宁可少报一条，不可多报一条不该报的」在报告层是合理的默认策略，而不是能力不足的遮掩。

## 四、授权与动作边界：扫描器不能替用户做决定

自动扫描天然带着合规问题，工程上必须硬编码边界，不能靠使用者自觉。

- **归属验证**：只允许扫用户能证明归属的目标，常见做法是 DNS 文本记录、指定路径放校验文件、或用同域名邮箱确认。没验证通过就不发任何探测请求。
- **动作白名单**：默认只做 GET / HEAD 这类无副作用请求；任何写操作、表单提交、文件上传都必须在单独授权下才允许，并且要能整类关掉。
- **遇到登录墙**：停在墙外，不猜口令、不复用会话、不尝试绕过。报告里如实写「认证后的区域未覆盖」，比硬闯过去更有价值。
- **第三方资源**：页面里引用的外部域不在授权范围内，默认不跟进去扫。

这些约束实现上不复杂，难在别为了「覆盖率好看」把它们做成可跳过的开关。

## 五、报告的可复现性与状态机

一份能用的报告，答案不是「有几个高危」，而是「我现在该改哪一行」。因此每条问题都要落到具体位置（文件路径、配置项、接口路径）和具体改法，只给一个漏洞编号或一句「建议升级」帮助有限。

更重要的是把报告做成有状态的对象，而不是每次扫描生成一份新的静态文档：

- 每条发现要有**稳定 ID**（由「目标 + 规则 + 位置」归一化得到，不能用数组下标或时间戳）；
- 复扫时按 ID 对齐，状态在 `open / fixed / regressed / ignored` 之间流转；
- 「修完又出现」要能识别出来，这比单纯统计「本次新增 3 条」有用得多；
- 忽略项要记录理由与操作人，否则下一次复扫同一条又冒出来，团队会反复讨论同一个问题。

顺带一个口径问题：「本次发现问题数」必须由去重后的 ID 产出，不能由扫描器原始命中数产出，否则同一漏洞在十个路径上出现就会被算成十条。

## 六、接进开发流程：增量与全量是两条管线

扫描放到什么时机触发，决定了它的成本结构和能发现什么。

- **PR 触发的增量扫描**：只看改动触及的文件与依赖，要求快、要求结论稳定（同一份代码两次跑出不同结果是灾难）。适合拦硬编码密钥、明显的危险配置。
- **定时全量扫描**：覆盖运行时行为、依赖版本、暴露面变化，允许慢，但要能出差异报告。
- **依赖漏洞与代码漏洞分开**：前者靠依赖清单与版本库比对，后者靠静态分析与动态探测，两者的更新频率、误报来源、修复动作都不一样，塞进一条流水线会让两边的告警都变 noisy。

密钥检测是误报最集中的一档：纯正则会把示例配置、测试夹具、占位符全捞出来；加熵值判定能滤掉一批，但高熵的哈希、构建产物 ID 仍会误中。比较实际的做法是叠加上下文（变量名、文件位置、是否处于示例目录）并给出「疑似」等级，而不是当成确认结论。

## 收尾

这类产品的壁垒不在「一次能扫出多少条」，而在「报告能不能让人直接动手修、修完能不能验证」。发现、去重、授权边界、可复现、状态流转，这五件事做扎实了，扫描结果才从一份吓人的清单变成一条能闭环的工程流程。

（本文只讨论这类系统普遍要处理的工程问题，不描述任何具体产品的内部实现；细节以各项目公开文档为准。）
