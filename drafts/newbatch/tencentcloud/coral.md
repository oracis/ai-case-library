# 把开源 agent 跑进生产：沙箱、凭据代理与长任务状态机

模型和 agent 框架免费之后，「让它在 demo 里跑通」这件事已经没有门槛。真正难的是把它放进一台会被人用、会出错、会被人恶意输入的机器里，然后保证它第二天还在跑。

Coral 的公开描述只有一句话：把开源 agent 框架的部署、托管、权限凭据、集成、模板打包好，让不懂运维的人也能用上。这句话背后是一串具体的工程约束。下面按「跑起来会依次撞到什么」的顺序拆，不讨论 prompt 技巧，只讨论让它不炸的那一层。

## 一、第一件要解决的事是文件系统和网络出口

一个能读文件、能发 HTTP 请求、能执行命令的 agent，本质上是一个远程代码执行入口，只是输入来自自然语言。所以第一层不是「模型怎么调」，而是「它跑在什么里面」。

可选的做法只有三档，取舍很清楚：

- **进程内直接跑**：实现最省事，出一次事就是宿主机的权限。任何面向外部用户的产品都不该这么做。
- **独立进程 + 权限收敛**：用单独的用户跑，限制可写的目录白名单，网络出口走代理并做域名允许列表。成本低，但一个 fork 炸弹或者一个写出宿主机路径的 bug 就穿透了。
- **容器或微虚拟机**：文件系统隔离、网络命名空间隔离、CPU 与内存配额。这是唯一能对「租户 A 的 agent 不许看见租户 B 的东西」给出可验证答案的做法。

选到第三档之后，新的问题马上出现：**容器的生命周期和 agent 的任务生命周期不是一个东西**。一次任务可能跑 20 秒，也可能挂 40 分钟——中间要等人工审批、要等外部 API 回调。容器常驻会烧钱，容器按需销毁会丢状态。所以从第一天起就必须把「执行环境」和「任务状态」分开：容器是无状态的计算单元，任务状态存在外面。

## 二、凭据不能交给 agent 的手里

第二件撞上的事是权限。要让 agent 真的干活，它得能读客户的数据库、能发邮件、能调 GitHub。把这些 token 直接注入环境变量是最常见的做法，也是最容易出事的做法：一次提示注入、一个把环境变量打进日志的错误处理、一次把 `env` 输出贴进对话的调试，凭据就漏了。

比较稳的形态是**凭据代理**，核心是三条：

1. **agent 拿不到明文凭据**。它在需要调某个外部服务时，请求发到本地一个代理端口，由代理去换短期凭证、拼上真实 header、转发出去。agent 侧看到的只是一个内网地址。
2. **权限按任务收敛，不按账号给**。一次任务只需要读某张表，就只发这张表的读权限，且有效期跟着任务走。任务结束即失效，不做「长期有效、以后再说」。
3. **每一次外部调用留审计**。谁在什么任务里、用什么身份、调了什么、返回了什么状态。这条不只是合规需要——排障时它是唯一能把「agent 说它做了」和「它真的做了」分开的证据。

这三条听起来是安全工程，其实是产品差异点：客户敢把生产库交给你，是因为你能说清楚「它最多能做什么、做完留下什么痕迹」，而不是因为你的模型更聪明。

## 三、工具接入的坑在错误语义，不在协议

agent 调工具，协议层已经有比较统一的答案（函数调用、MCP 之类）。真正让人返工的是错误怎么表达。

常见错误是把所有失败都压成一个字符串塞回模型：`Error: request failed`。模型拿到这句话只会做一件事——原样重试。于是超时重试、鉴权失败重试、参数不合法也重试，重试三次之后任务失败，日志里只有三行一样的报错。

可用的做法是给错误分类，且分类要让模型能据此决策：

- **可重试**（限流、5xx、网络抖动）：带退避重试，重试次数上限写死，不交给模型决定。
- **需要换参数**（400、字段校验失败）：把校验信息结构化返回，让模型改参数再来，而不是重试。
- **需要人来处理**（鉴权失效、余额不足、目标不存在）：立刻中断，转人工，别让模型在一个死路上烧 token。
- **有副作用且状态未知**（写请求超时）：这类最危险。必须带幂等键，让重放安全；否则「我不知道上一次到底成没成」会变成重复下单、重复发信。

最后一条是分水岭。工具调用一旦有外部副作用，「重试」就不再是性能问题，而是正确性问题。

## 四、长任务要有状态机，不能靠一次请求撑住

一次 agent 任务经常包含多个步骤：查资料、调三个工具、等审批、再写回。把它做成一个长 HTTP 请求是最省事、也最先崩的做法——网关超时、连接断开、进程重启，任何一个都会让任务变成「不知道做到哪了」。

可行的结构是把任务拆成状态机，每一步都是可重放的小单元：

1. 每一步的输入、输出、工具调用记录都落库，带步号；
2. 进程挂掉后，从最后一个完成步继续，而不是从头再来；
3. 所有有副作用的步都用幂等键去重，保证重放不会造成第二次真实写入；
4. 人工审批作为状态机里的一个显式状态（等待中），而不是「阻塞在某一行代码上」。

这套东西的价值不在优雅，在于**可解释**：客户问「这次为什么失败」，你能给出第几步、哪个工具、返回了什么，而不是一句「agent 出错了」。

## 五、多租户与成本：先限流，再谈优化

托管层的成本结构很容易算错。一个租户跑一次长任务，可能触发几十次模型调用和上百次工具调用，如果并发不做隔离，一个租户的批量任务会把整个池子的配额吃光，其他租户全部超时。

所以顺序应该是：**先做租户级并发与速率限制，再谈单次调用的成本优化**。前者决定「会不会互相拖死」，后者只决定「每单贵一点还是便宜一点」。前者做不好，优化省下来的钱会被重试和超时全部吃掉。

资源预算也要显式：每个任务给一个 token 上限和墙钟时间上限，超了就中止并如实告知，而不是让它无限试。对客户来说，「明确失败」比「跑了四十分钟最后什么都没给」要好得多。

## 六、可观测性：要能回放，不只是能看日志

托管 agent 的排障难点是「同一句话，两次跑出不同结果」。只打日志不够，需要能回放：把一次任务的输入、每一步的模型输出、工具调用参数与返回、最终状态都存成结构化记录，能按任务号重放整条链路。

有了回放，才有三件后续能力：定位是模型问题还是工具问题、把失败样本变成回归用例、在改 prompt 或改工具描述之后验证「这次修复没有把别的任务弄坏」。没有回放，所有改动都是凭感觉。

## 七、为什么这一层能收钱

底层 agent 框架开源、模型按量计费，看起来这一层没有壁垒。但把上面六件事做完，是一家产品公司几个月到一年的活，而且是一件持续要跟着上游改动的活——框架升级、模型换代、客户集成变更，每一次都得重跑一遍。

这跟 WordPress 的故事是同一个形状：软件本身免费，但「让它稳定跑起来、有人管、出事有人接」这件事一直有人付钱。差别在于 agent 这一层多了权限和副作用，出错代价更高，客户的付费意愿也就更强。

Coral 的公开数据可以作为一个横截面参考：TrustMRR 直连显示月订阅收入 3,150 美元、44 个活跃订阅（2026-08-31 快照），获客主要靠创始团队自己办 workshop，一个月十几场。规模不大，但它验证的方向是清楚的——客户买的不是模型，是「不用自己搭这一套」。

## 八、给准备自己做的人的四条判断

1. 先决定隔离档位。选容器/微虚拟机，并且从第一天就把「执行环境」和「任务状态」分开；反过来做，后面一定要重写。
2. 凭据走代理，agent 侧永远拿不到明文。权限按任务发、按任务收，审计先于功能上线。
3. 工具错误必须分类，有副作用的调用必须有幂等键。这两件事不做的系统，第一次生产事故就会教你知道。
4. 先做租户限流和任务预算，再做单次调用优化。顺序反了，优化出来的钱会被超时和重试吃掉。

这套东西没有一项是新技术，全是工程约束的堆叠。它的门槛不在难度，在于愿不愿意认真做这些不性感的部分——而这恰好也是它能收费的原因。
