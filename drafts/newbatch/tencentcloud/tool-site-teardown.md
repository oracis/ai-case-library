# 采集器设计笔记：有界抓取、正则静默失败与跨源求交的假阳性

> 数据时点：2026-11-23 抓取（本机实测，Python 标准库实现，零第三方依赖）

## 一、需求与技术选型的约束

要做的是一个很窄的事情：从外部 AI 工具目录站抓取工具详情，提取月访问量与关键词表，再和本地另一份产品库做对齐分析，判断这份数据能不能支撑选品决策。

约束有四条，直接决定了实现形态：

- 只用 Python 标准库，不引 requests / bs4，便于在任意机器上直接跑。
- 单轮抓取必须有界。站点 robots.txt 写了 `Crawl-delay: 5`，一个详情页五秒，二十个就是一百秒。
- 只读，不写任何远端状态。
- 结果必须可复算：同样的输入、同样的规则，必须得到同样的命中集。

这份笔记记录三个在实现里真正踩到的问题：**抓取层的静默失败、解析层的静默失败、求交层的假阳性**。三者的共同点是都不报错——程序退出码 0，输出看起来正常，但结论是错的。

## 二、抓取层：三个不报错的失败

### 2.1 默认请求头会被拒，但不是每次都拒

不带浏览器请求头，首次请求就会拿到 403。补上一组完整的头（User-Agent、Accept、Accept-Language、Accept-Encoding、Sec-Fetch-Dest/Mode/Site、Upgrade-Insecure-Requests）之后恢复正常。

关键在于：这不是「配置一次就完事」。同一天连续抓了约九十个详情页之后，整个站点重新开始持续 403——包括之前成功过的首页榜单，隔半分钟复查仍然是 403，换任何页面都一样。

结论：403 有两个来源，**请求头特征**和**请求频次**。前者补头解决，后者只能靠控制节奏和单轮上限解决。这也意味着这类采集不能设计成定时任务——定时跑的失败形态是「返回 0 条」，和「今天确实没有新数据」无法区分。

### 2.2 压缩响应不解压会变成乱码，而不是报错

服务端可能返回 gzip。如果不判断魔数直接 decode：

```python
with opener.open(req, timeout=30) as r:
    body = r.read()
if body[:2] == b"\x1f\x8b":          # gzip 魔数 0x1f 0x8b
    body = gzip.decompress(body)
return body.decode("utf-8", "replace")
```

用 `errors="replace"` 时，未解压的二进制会被替换成大量替换字符，程序继续往下跑，正则自然一个都匹配不到，字段全空。**这是第一个「静默失败」**——它伪装成「页面结构变了」。

### 2.3 代理与 TLS 的组合问题

采集器统一绕开环境里的 HTTP 代理（显式构造空 ProxyHandler），否则在系统代理不稳定时会出现「时通时不通」。这一类问题的排查成本比问题本身高，所以在入口处一次性处理掉，不要让它在每次请求里随机出现。

### 2.4 有界不是「少抓点」，是三层约束

「有界」在实现上要落到三个地方，缺一层都会退化成「跑着跑着开始返回空」：

- **单轮详情数上限**（默认 20）。它决定了单次运行的时长上限，也决定了被频次风控的概率。
- **请求间隔下限**（5 秒，跟 robots 一致）。不能因为「想快一点」就压到 1 秒，压了之后前面几十个仍然会成功，直到某次开始连续 403。
- **失败重试有上限**（3 次，指数退避）。遇到 429 要退避，遇到 404 要立刻放弃——把 404 也塞进重试，等于自己放大请求量。

还有一个容易忽略的点：**失败的条目要留下痕迹**。如果重试三次仍失败就静默跳过，最终产物看起来是「这次只抓到 17 条」，和「有 3 条不存在」分不清。

## 三、解析层：正则匹配成功但取到空串

详情页是服务端渲染，可以直接用正则。字段结构大致是：

```
Monthly Visitors:  →  <div>  <span>6.0B</span>
Top Keywords       →  连续三个 <div class="traffic-td">：关键词 / 流量 / CPC
```

两个实践点：

**第一，页面里有框架插入的注释节点。** 真实的 DOM 序列化里会出现 `<!---->` 之类的空占位。如果正则写死成 `</div><div>`，就会整条匹配失败。

```python
m = re.search(r'Monthly Visitors:\s*</div>\s*<div[^>]*>\s*(?:<!---->\s*)?'
              r'<span[^>]*>([^<]+)</span>', page)
visitors = clean(m.group(1)) if m else ""
```

**第二，取到的值是带单位的字符串。** `6.0B`、`1.2M`、`94.5K`。后续要做数值排序或阈值筛选，必须自己做单位换算；直接 `int()` 会抛异常，而用 `try/except` 兜成 0 又会把「解析失败」和「真的没有数据」混成同一种结果——**这是第二个静默失败**。

正确做法是让两者分开：解析失败返回 `None`，没有数据显示为空串，统计时分别计数。

## 四、求交层：假阳性是这次实验最贵的教训

求交的意思是：把目录站抓到的工具，和本地那份带一手收入的产品库按产品对齐。

第一版我写的是宽松规则——先按官网域名匹配，匹配不上再按产品名派生一个 slug 去撞。跑完报出 6 条命中。如果只看统计数，这次实验到这里就「成功」了。

逐条人工核对，**6 条全是假的**。

### 4.1 聚合域名：域名相等 ≠ 产品相同

有 4 个工具在目录站登记的「官网」是应用商店页面和浏览器扩展商店页面，不是自己的域名。

这类域名下挂着成千上万个产品。按域名求交时，一个应用商店域名就把 4 个完全不同的产品映射到了同一条收入记录上。数据层面完全合法——域名确实相等——语义层面彻底错误。

### 4.2 名字派生 slug：用巧合当证据

产品库按 slug 索引，slug 通常由产品名派生，于是「拿名字猜一个 slug 去撞」看起来顺理成章。

实测反例：一个产品的官网是某域名点 live，我拿域名主干去撞库，命中一个名字相似的产品。两者除了名字像，没有任何关系。

跨站命名本来就不一致：同名不同产品、同产品不同名都是常态。名字层面的相等只能用来缩小范围集，不能当作同一性证据。

### 4.3 修法：只认强键，先剔聚合域

```python
AGG = {"apps.apple.com", "play.google.com", "chromewebstore.google.com",
       "chrome.google.com", "github.com", "producthunt.com",
       "apps.microsoft.com", "addons.mozilla.org", ...}

def normalized_host(url):
    h = (urlsplit(url or "").hostname or "").lower()
    return h[4:] if h.startswith("www.") else h

def joined(a, b):
    ha, hb = normalized_host(a["website"]), normalized_host(b["website"])
    if not ha or ha != hb:
        return False
    return ha not in AGG
```

三条规则：只认官网域名完全相等；聚合与平台域名一律不参与；不做任何基于名字的模糊匹配。

## 五、实测结果与解释

严格口径下：

| 数据面 | 抓取 | 成功 | 严格命中 |
|---|---|---|---|
| 热门榜 | 前 60 | 58 | 0 |
| 新品榜 | 前 24 | 22 | 0 |

反向验证同样为 0：从有真实收入的产品里挑 8 个（4 个普通生意、4 个 AI 工具），用域名派生 slug 去请求目录站页面，全部 404。另外该站的站内搜索是前端渲染的，换任何关键词都返回同一批卡片，没有服务端检索可用。

0 命中不是随机波动，有两个结构性解释：

**收录是抽样。** 目录站三点一万条，产品库一万两千条，两边的人群本来就不同——产品库的收入大头是普通生意，不是 AI 工具。

**口径不重叠。** 被拆的案例是完全免费的工具站，变现入口只是给订阅用户提供更好的版本。这类产品在「支付网关一手收入」口径里天然不存在。不是抓取失败，是这个口径不收录它。

## 六、四条可复用结论

1. **跨源匹配只用强键。** 域名相等是强键；名字、slug、标题相等是弱键，弱键只用于缩小范围，不能当证据。
2. **先剔聚合域再算命中率。** 应用商店、代码托管、产品榜单域名下挂着无数产品，参与匹配必然造假。
3. **「匹配成功」必须人工抽检。** 这次 6 条全部抽检才暴露问题；如果直接信统计数，后续所有分析都建立在这 6 条脏数据上。
4. **有界抓取 + 礼貌间隔 + 不进定时任务。** 频次触发的 403 会让「每天跑一次」的设计在若干天后静默失效，而失败形态是返回 0 条，与「没有新数据」无法区分。

这四个坑有一个共同点：**它们都不报错**。所以采集类脚本的验收标准不能是「跑通了」，只能是「抽检过」。
