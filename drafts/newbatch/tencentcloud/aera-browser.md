# 在浏览器里托管长任务：Aera 的调度、连接器复用与推理成本账

Aera 是一款在浏览器里跑自主工作流的 agent：定时抓取、跨站填表、把多个工具串成一条流程，通过 MCP 接外部服务。它值得做工程拆解，不是因为它做得多大，而是因为它把三个工程问题摆得很清楚：**长任务在本地浏览器里怎么可靠地跑完**、**跨站连接器怎么不靠自己维护**、**按订阅收费时推理成本怎么吃掉毛利**。这三件事跟产品做多大无关，做任何"代用户执行"类 agent 都会遇到。

公开口径：MRR 463 美元、6 个活跃订阅、客单价 77.17 美元；近 30 天已验证收入 280 美元、累计收入 4,257 美元，近 30 天利润率 25%（支付网关 API 直读，2026-11-03 同步快照）。

数据时点 ｜ 截至 2026-11-04（TrustMRR 档案 / 官网同步）｜ 口径：MRR

## 一、为什么是浏览器，而不是 API

第一个工程决策不是"用不用大模型"，而是"agent 跑在哪"。纯 API 能做的事，用 API 更稳：接口稳定、数据结构化、没有登录态问题。

但有一类任务恰好卡在 API 的反面——**要登录态、要跨站、要定时**。客户的数据和操作入口都在网页里，逐站去接 API 的成本远高于让 agent 直接在浏览器里复用客户已经登录的会话。Aera 选的是后者：浏览器是唯一同时装着客户数据和操作入口的地方，本地跑 agent 省掉了逐站接 API 的成本。

代价也很明确：浏览器里的 DOM 会变、页面会改版、会话会过期。这类任务的失败是常态，不是异常。所以第一个工程约束是——**长任务必须可恢复**，不能假设每一步都一次成功。

## 二、长任务的调度：失败是常态

"每周固定的重复操作交出去"听起来简单，落到执行层是三件事：

1. **定时触发**：任务按周/按天跑，需要一个不依赖用户开机的调度器；浏览器 agent 的调度器要么常驻后台、要么在用户在线时补跑，两者对"任务是否真的执行了"的语义完全不同。
2. **跨站填表的脆弱性**：填表依赖 DOM 选择器，页面一改版就全废。能做的不是写更聪明的选择器，而是给每步加**字段命中校验**——取不到预期元素就停下并报错，而不是瞎填一通把错误数据提交上去。
3. **失败恢复的边界**：长任务中途失败，重跑要回答"这一步重复执行会怎样"。读操作可以放心重试；**提交类操作不能盲目重试**——第一次可能已经成功，重试就是重复提交。正确做法是先查状态（目标页是否已经出现结果），再决定从哪一步续跑。

一个实用的判据：**凡是替用户点了"提交"的地方，都要能回答"重跑会怎样"**。答不上来的步骤，就不该放进自动重试链。

## 三、MCP：把连接器维护成本外包出去

跨站 agent 最大的隐性成本是连接器——每个外部服务都要维护一个适配层，服务一多就变成主要工作量。

Aera 用 MCP（Model Context Protocol）接外部服务，本质是**复用现成工具链**，不必自己维护每个站的连接器。这对一个小团队是决定性的：MRR 463 美元、6 个订阅的体量，根本养不起一支维护几十个连接器的团队。

工程上的取舍是把"能力边界"划在协议层：agent 只管编排和调度，具体动作交给 MCP 暴露的工具。好处是加一个服务不需要改 agent 本体；坏处是受限于 MCP 生态里有哪些工具——没有现成工具的站点，还是得自己补。

## 四、推理成本账：25% 利润率意味着什么

这是整篇里最值得算的一段，也是很多 agent 产品算不清的一段。

公开口径：客单价 77.17 美元（MRR 463 美元 ÷ 6 订阅），近 30 天利润率 25%。也就是说，每收 100 美元，大约有 75 美元 被成本吃掉——对这类产品，成本的大头是模型推理。

25% 的利润率给出两个结论：

- **跑量不会自动改善利润**。毛利率低的产品，规模只会等比例放大成本。改善要么靠涨价，要么靠降低单任务的推理消耗（更便宜的模型、更短的步骤、更少的重试），而不是靠"多卖几份"。
- **按席位收费是错的定价模型**。这类用户往往只有一个人在用，按席位收费收不上钱；应该按**任务时长或并发数**分档——用量大的客户付更多，正好覆盖他消耗掉的推理成本。

还有一笔账要算清楚：累计收入 4,257 美元 里，有一段来自单月 2,610 美元 的尖峰，之后回落到每月 140 美元–210 美元。看 MRR 时得区分"当前经常性收入"和"被一次性大单抬高的历史峰值"——463 美元 是当期值，4,257 美元 是累计值，两者不能相乘也不能互换。

## 五、这个形态能搬走什么

把 Aera 拆开，能搬走的不是某个功能，是三条判断：

- **从窄任务切**：只做"要登录态、要跨站、要定时"的重复操作，纯 API 能做的事别用浏览器——那里没有你的差异化。
- **先算单任务毛利**：25% 利润率的产品，先把单任务成本算出来再定价，跑量只会放大亏损。
- **连接器能外包就外包**：6 个订阅养不起自建连接器团队，用现成协议（如 MCP）把这块成本转出去。

它同时也说明天花板：一个链接、一个 agent、跨站自动化——位置是真实的，但 6 个订阅、每月一两百美元的体量说明这不是一个大市场。适合学它的成本结构和窄切口，不适合学它的规模预期。
