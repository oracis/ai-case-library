# 公开事件信号管道怎么搭：采集调度、实体归一与时间衰减

有一类系统做的事情很像：盯着公开发生的职业与商业事件——某家公司换了技术负责人、某家企业拿到新一轮融资、某个岗位突然开始大批招聘——发现变化之后自动采取动作。做这类系统的人很快会发现，难点不在"抓得到"，而在"抓到的能不能被下游当成事实用"。

本文只谈工程：从公开事件到可用信号之间，要过哪几道关。以下做法来自对同类系统的观察和通用实践，不涉及任何具体产品的商业细节。

## 一、信号源：公开不等于可消费

换工作、融资、招聘这些信息全都是公开的，但"公开"和"能稳定消费"之间隔着一整层数据工程。

**源的异构性**是最先撞上的。招聘动态散在企业官网的 careers 页、ATS 后台、第三方招聘站；融资公告散在新闻稿、监管披露、行业媒体。每个源的更新频率、结构化程度、反爬策略都不一样。调度层要分频抓取、用条件请求（ETag / Last-Modified）省流量、失败按指数退避重试，并且同一条记录被重复抓到时不能变成两条新数据——采集侧就得有幂等键，通常是「源标识 + 源内主键 + 内容指纹」。

**反爬的边界要提前想清楚**。公开可访问不等于允许高频抓取：遵守 robots、控制并发、给每个源单独配速率预算，比事后被封 IP 再补救便宜得多。

## 二、实体归一：同一家公司有好几张脸

第二条坎是实体消歧。同一家公司在不同源里可能写法不同：有 Inc. 与无 Inc.、改过名、用不同域名、招聘页挂在母公司下。如果「A 公司在融资」和「A Inc. 在招人」不能归并到同一个实体，下游就会把同一件事算成两家公司的。

工程上的常规解法是两级：

1. **blocking**：先用确定性字段把候选集压小（域名、注册名、统一社会信用代码一类的强标识），避免 O(n²) 全量比对；
2. **相似度 + 人工队列**：对候选对跑名称归一化（去后缀、全半角、简繁）加相似度打分，高于阈值自动合并，中间区间进人工复核队列。

关键是把合并做成**可回溯的**：每次合并记录依据和来源，允许拆分。实体归一一旦出错，污染的是整条下游数据，而且很难被发现——它不会报错，只会悄悄把两条记录算成一条。

## 三、观测不是事实：把信号当带衰减的假设

原始观测和事实之间还有一层。一条「某工程师更新了主页头衔」的记录，只是一次观测；直接把它当成「此人正在换工作」的事实往下游送，误报会一路传下去。

比较稳的建模是把每条信号当成**带衰减的假设**：

- 每条信号带来源置信度（官方披露 > 权威媒体 > 单一第三方页面）、观测时间、半衰期；
- 价值随时间衰减，且不同事件类型的衰减速率不同——组织变动的影响窗口以周计，资本事件的决策周期以月计；
- 所以库里要存的是**事件时间戳**，不是只有「最近一次刷新时间」。后者会让一条三个月前的旧信号看起来和昨天的一样新。

## 四、下游动作：副作用必须有预算和闸门

信号被消费之后往往要触发动作。这是整个系统里最不受自己控制的一环，因为动作通常发生在别人的平台上，受平台侧的频率限制和风控模型约束。

三条实践：

- **速率预算按执行者隔离**。每个执行通道维护独立配额池，出现异常（失败率突增、临时限制提示）就自动降速，而不是硬顶上限；
- **副作用要幂等**。同一个事件被两条信号触发时不能执行两次，幂等键取「对象 × 通道」粒度，重复触发记为刷新；
- **留人工闸门**。打分和筛选可以全自动，但真正对外执行的动作先攒队列、人过一眼再放行，等链路稳定再逐级放开。

## 归纳：这条管道的骨架

```
公开事件源 → 采集调度（分频/条件请求/幂等键）
     → 实体归一（blocking + 相似度 + 人工复核）
     → 信号库（置信度 × 观测时间 × 半衰期）
     → 消费与动作（速率预算、幂等、人工闸门）
```

四段里最难的不是抓取，而是**把不确定性显式管起来**：源不可靠就记置信度，事件会过期就记半衰期，实体可能合错就留回溯，动作有副作用就配预算和闸门。做到这些，一套盯公开事件的系统才算能被下游信任。
