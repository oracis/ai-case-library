# 移动端图像分类的置信度表达：端侧推理、时序记录与免责边界

有一类移动端应用做的事很相似：用户拍一张照片，系统给出几种可能、每种可能的把握程度，再附一段处理建议；过几天再拍一张，看它有没有变化。这类系统的难点不在「模型能不能跑起来」，而在**输出天然落在高不确定区间**，偏偏又紧挨着健康决策。本文只谈工程：从一次拍照到一条可负责的回答之间要过哪几道关。以下做法来自对同类系统的观察和通用实践，不涉及任何具体产品的内部实现，也不构成医疗建议。

一句背景，仅用于说明这类窄场景工具确实能长期存在：截至 2026-09-20 的公开快照里，月度经常性收入约 2869 美元、累计收入约 62352 美元、活跃订阅 115 个。前者是当月口径、后者是累计口径，两者不能互相年化；数字是快照、会变，本文不据此推算任何现值。

## 一、推理放在哪：端侧不是一句「离线可用」

第一个决策是推理位置。端侧的好处很直接：照片不出设备、无网也能用、首屏延迟可控、没有按次调用成本。代价同样实在：模型要塞进安装包，内存峰值与发热要压住，老设备上帧率不能塌，换模型往往要跟着发版。

云端反过来：模型随时可换、可以跑更大的网络，但上传健康类图片要先过用户授权，弱网时整个功能不可用，而且每次调用都记在账单上。

比较稳的形态是**端侧常驻 + 云端可选兜底**：小模型在设备上完成首屏判断，只有低置信度样本才询问用户是否上传、由更大的模型复核。这里有几个容易漏掉的工程约束：

- **预处理与训练时严格一致**。输入分辨率、归一化参数、色彩空间、裁剪方式只要差一点，线上分数就会整体漂移，而这种漂移不会报错，只会悄悄把准确率拉低。
- **模型版本和标签表要一起打包**。只换模型文件、没换标签序号，输出就会张冠李戴；标签表必须版本化，并随模型一起灰度、一起回滚。
- **失败要能退化成「判断不了」**。推理超时、内存不足、模型加载失败时，不能拿上一次的缓存结果或默认值硬给一个答案。
- **灰度看的是分档分布，不是平均分**。新模型上线后若「高置信度」占比突然涨一大截，往往不是变准了，而是校准坏了。

## 二、置信度不是取一个最大值

分类模型给的是一组分数，但把最大的那个数直接显示给用户，通常是最糟的做法：未经校准的 0.87 既不等于「87% 把握」，用户也不知道该怎么用它做决定。

更可用的表达是三层：

1. **可能性排序 + 分档**。给出前几种可能，用高／中／低三档代替小数，并明说哪些外观本来就容易互相混淆。用户要的是「接下来该怎么办」，不是一个概率数字。
2. **前置输入质量门**。模糊、过曝、主体占比太小、拍的根本不是目标区域——这些输入下模型仍会给出一个看起来很自信的高分。清晰度、主体检测、曝光检查要在推理之前拦一道，拦住就提示重拍，而不是把噪声送进模型。
3. **分布外拒识**。训练时没见过的类别（完全不同的皮肤状况、异物、截图）不属于任何一类，必须显式留一条「不在适用范围内」的出口。没有这道出口，系统永远会在错误答案里挑一个最像的。

阈值怎么定，取决于答错的后果，而不是模型指标。涉及「要不要就医」的建议，漏报的代价远大于多问一次，所以低置信度一律走保守分支：不自动下结论，只给出「无法判断」与就医提示。

还有一个架构上的分界值得坚持：**模型层只输出可能性，建议层是可审计的规则与文案表**。护理与就医提示不要塞进模型输出里，否则改一句合规文案就得重训或重发模型。每次回答同时记下模型版本、标签表版本、阈值版本与输入质量分——出问题时能还原「当时为什么这么答」，这比事后翻日志猜要可靠得多。

## 三、时序记录：难的是两次照片可比

「记录变化」听起来只是多存几张照片，实际上它把问题从单次推理变成了**跨时间的可比性**。第一次在日光灯下近拍、第二次在窗边远拍，两张照片的像素差异大概率来自拍摄条件，而不是部位本身。

工程上能做的是把采集条件尽量固定下来：取景框与参考轮廓、对焦与曝光锁定、距离和角度提示；时间戳同时存 UTC 与本地时区，跨时区或改系统时间后时间线才不会错序。质量分不达标的观测可以存，但要标记为「不可比」，别让它参与趋势判断。

数据结构上，时间线应该是**不可变观测事件的派生结果**，不是一条被反复覆盖的「当前状态」记录。每次观测存一条：时间戳、原图内容哈希、质量分、模型输出、用户备注。这样用户重拍、删掉某张照片、或者同步中断重来，历史都不会被抹掉或凭空多一个点。

两个连带约束：

- **导入要幂等**。相册重扫、同步重试会把同一张照片送进来两次，用内容哈希去重，重复导入记为刷新而不是新增观测。
- **订阅状态只管新功能，不管已有数据**。健康类照片默认留在设备本地，同步是显式开关；权限变化不能把用户已经存下的记录锁住、隐藏或删除。这是这类产品最容易崩掉信任的地方——功能可以分层，用户自己的历史不该被分层。

## 四、免责边界要落在架构里，不是落在文案里

「这不是诊断」写在页脚就够了？不够。真正决定边界的是系统能不能说出诊断式的话、能不能被追溯。

- **输出措辞可枚举、可校验**：只允许「可能」「建议就医」「无法判断」三类，把「确诊」「排除」「不用管」做成禁用词表，写单测卡住文案模板与模型拼接后的最终文本。
- **建议带适用条件**：不同地区常见虫种与处理路径不同，一套文案全球下发本身就不成立；文案表要带版本、地区与生效时间，别用「一刀切」的静态字符串。
- **隐私按最坏情况设计**：敏感部位照片、未成年人使用、留存期限、注销时的删除链路，要在表结构阶段定好，而不是上线前补一份隐私政策。服务端日志只留结构化判定字段，不落原图。
- **可回溯**：客诉来时能查到「哪天、哪个模型版本、哪条规则、哪句建议」，同时不暴露别人的数据。

## 归纳：这条链路的骨架

```
拍照 → 输入质量门（清晰度 / 主体 / 曝光）
     → 端侧推理（模型版本与标签表版本对齐）
     → 置信度分档与分布外拒识（低分走保守分支）
     → 规则层生成可能性排序与就医提示
     → 不可变观测记录（哈希去重、本地优先）
```

四段里最难的不是把分类模型跑通，而是**在不确定时仍然给出可负责的输出**：模型可能认错就留拒识出口，照片可能不可比就存事件流，建议可能有后果就做规则分离与版本追溯。把不确定性显式管起来，一个很窄的图像工具才算能被用户信任。
