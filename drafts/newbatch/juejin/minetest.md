# Minetest 的 Lua mod 系统怎么撑住沙盒扩展：一个 C++ 引擎的插件边界设计

一个 C++ 写的方块沙盒引擎，把几乎所有游戏逻辑都交给 Lua 脚本——包括物品、节点行为、合成表、甚至新的游戏规则。核心引擎只负责渲染、网络、存储和脚本运行时。

这个边界划在哪里、怎么划，是这份源码最值得看的部分。它解决的问题所有做「平台型产品」的团队都会遇到：**如何让第三方扩展你的产品，而不需要重新编译你的产品。**

## 一、引擎与玩法的分工

- **C++ 侧**（引擎）：地图存储、区块网格、渲染、网络协议、玩家物理、Lua 运行时绑定
- **Lua 侧**（玩法）：节点定义、物品、合成、掉落、生物、GUI、命令

默认游戏「Minetest Game」本身就是一堆 Lua mod，跟第三方 mod 地位完全一样。这是一个重要设计：**官方玩法不享受引擎特权**。如果官方玩法走私有通道，第三方永远会被卡住。

## 二、区块存储：为什么是 16×16×16

地图被切成 `MapBlock`，每边 16 个节点。选这个数字不是随便定的：

- 16³ = 4096 个节点，按每节点 2 字节（类型 + 参数）算约 8KB，一压缩就很小
- 刚好是 16 位坐标能寻址的块内偏移（x/y/z 各 4 bit）
- 渲染、网络同步、磁盘存储、内存缓存全部以块为单位，粒度统一

```cpp
// 简化示意：块内坐标为 4 bit
struct BlockPos { int16_t x, y, z; };   // 世界坐标 → 右移 4 位得多块坐标
struct LocalPos { uint8_t x:4, y:4, z:4; };  // 块内偏移，直接位运算
```

工程上的教训很通用：**网格类系统一定要让「渲染粒度 = 存储粒度 = 同步粒度」**。这三个粒度一旦不一致，就会出现「改一个方块要重传一整片」「存档要跨块拼接」这类连锁麻烦。

## 三、mod 的注册式 API

mod 不改引擎代码，靠的是注册回调：

```lua
core.register_node("mymod:stone_brick", {
    description = "Stone Brick",
    tiles = {"mymod_stone_brick.png"},
    groups = {cracky = 3, stone = 1},
    on_dig = function(pos, node, digger)
        core.remove_node(pos)
    end,
    on_rightclick = function(pos, node, clicker)
        core.chat_send_player(clicker:get_player_name(), "clicked")
    end,
})
```

这套设计的三个要点，做插件系统的人可以直接对照：

1. **注册表而非继承**。引擎维护一张 `name -> definition` 表，行为通过字段挂载，不要求写类。降低接入门槛。
2. **能力分组（groups）**。`cracky = 3` 表示「可被镐挖、硬度 3」，工具只需判断分组，不需要知道具体方块。这是**面向能力而非面向类型**的设计，扩展性远好于硬编码判断。
3. **回调而不是事件总线**。每个节点自己带 `on_dig`/`on_rightclick`，天然并发安全，不需要全局事件分发。

## 四、脚本沙箱的边界在哪

Lua 在引擎里跑在同一进程，这意味着 mod 能做的事情很多，也意味着**一个死循环 mod 能卡死整个服务端**。

引擎的应对是运行时保护：

- `core.register_globalstep` 里的 mod 代码有执行预算，超时会记录并告警
- 地图操作走引擎 API，mod 不能直接改内存里的区块
- 网络包由引擎序列化，mod 只能填内容

但这不是硬隔离（不是进程级沙箱）。对单机游戏够用，对公共服务器就是个风险——这也是为什么很多公共服会自己加 mod 白名单。

**做插件系统必须面对的选择**：同进程（性能好、能力全、但一个坏插件毁全局）vs 独立进程（隔离好、但序列化成本和延迟高）。Minetest 选了前者，因为它要的是方块级高频调用。

## 五、网络协议的设计取向

Minetest 的协议是二进制的、按块增量同步：

- 玩家进入视野时下发整块
- 块内变更只发节点坐标 + 新内容
- 块内容有序列化版本号，客户端可缓存

这跟 HTTP JSON API 的直觉完全不同，但实时沙盒必须这样——玩家每挖一个方块就发一次 JSON，带宽立刻爆掉。

## 六、读代码的入口

1. `src/mapblock.cpp` —— 块的序列化/反序列化，看二进制格式怎么设计
2. `src/script/lua_api/` —— Lua 绑定层，看 `register_node` 之类的 API 怎么落到 C++
3. `builtin/game/` —— 用 Lua 写的默认游戏逻辑，看引擎提供了哪些能力
4. `games/minetest_game/mods/` —— 官方 mod，学写 mod 最好的范本

## 七、编译与门槛

- 依赖 Irrlicht（渲染）、SQLite/LevelDB（地图）、LuaJIT、zlib、OpenAL
- Windows 编译要用 CMake + vcpkg，第一次配环境大概要花掉一个下午
- Lua API 文档散落在 `doc/lua_api.md`，版本间有破坏性变更

## 八、能搬走的设计

- **官方玩法也走插件通道**，保证 API 不被私有需求扭曲
- **按能力分组而不是按类型判断**，扩展点自然生长
- **三个粒度对齐**（渲染/存储/同步），省掉无数边界 bug
- **插件系统先想清楚隔离级别**，别等出事再补
