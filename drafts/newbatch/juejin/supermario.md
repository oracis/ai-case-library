# 在浏览器里复刻 1985 年的超级马里奥：6502 时代的关卡数据怎么搬进 JS

一个用 JavaScript 复刻的超级马里奥兄弟。跑在 canvas 上，手感接近原作。

看起来是「怀旧复刻」，实际上是**一次跨时代的架构移植**：把 NES 那套受硬件限制逼出来的设计（固定点数学、按列滚动、精灵数上限），用现代前端技术重做一遍。做游戏的和做前端的，都能从里面学到东西。

## 一、复刻要解决的四个错位

| 维度 | 1985 年 NES | 现代浏览器 |
| --- | --- | --- |
| 执行模型 | 60Hz 固定帧 + VBlank 同步 | `requestAnimationFrame` 可变帧率 |
| 数学 | 8 位整数 + 亚像素定点 | 双精度浮点 |
| 渲染 | PPU 图块 + 精灵（每行 8 个上限） | Canvas 2D / WebGL，无上限 |
| 内存 | 2KB RAM + 卡带 ROM | 不受限 |

直接照抄原作逻辑会出问题：帧率不固定、浮点累积误差、精灵上限不存在导致画面「太干净」。**复刻的关键不是抄代码，是抄约束。**

## 二、第一条：把帧率钉死

原作所有物理常量都是「每帧移动多少」。如果直接放进 `requestAnimationFrame`，120Hz 屏幕上角色会跑两倍快。

解法是固定步长 + 累积器：

```js
const STEP = 1000 / 60;   // 逻辑固定 60Hz
let acc = 0, last = performance.now();

function loop(now) {
  acc += now - last;
  last = now;

  // 关键：限制最多补 5 帧，防止切标签页回来时一次性跑几千帧
  let guard = 0;
  while (acc >= STEP && guard++ < 5) {
    update(STEP);          // 逻辑只吃固定步长
    acc -= STEP;
  }
  render();                // 渲染可以跑任意帧率
  requestAnimationFrame(loop);
}
```

这条纪律所有游戏都适用：**逻辑与渲染解耦，逻辑永远固定步长**。否则物理在高低帧率设备上表现不一致。

## 三、第二条：定点数学

原作的位置用「像素 + 亚像素」表示：一个 8 位整数存像素，另一个存 1/256 像素。这样加减法不会丢精度。

JS 里用浮点也能跑，但累积误差会让「同一段跳跃在不同帧数下落到不同位置」。复刻里常见的做法是**所有物理量取整到亚像素单位**：

```js
const SUB = 16;                    // 1 像素 = 16 亚像素
player.x += Math.round(vx * SUB);  // 内部全用亚像素整数
const px = player.x / SUB;         // 只在渲染时转成像素
```

好处：跳跃高度可复现、碰撞判定稳定、录像回放能对上。

## 四、第三条：关卡数据怎么编

原作的关卡数据是**紧凑到极致**的：地形按「列」存储，每列一个对象，包含该列的瓦片与「这一列上有什么对象」。

```
列结构（概念上）：
  [瓦片类型1, 瓦片类型2, ..., 对象列表]
对象：
  敌人类型 + y 位置（低 4 位是高 4 位复用）
```

设计要点有两个：

1. **地形与对象共用一列**。因为横版卷轴游戏天然按列生成——角色往右走，新列从右边进来，老列从左边丢弃。
2. **相同列合并成「宏块」**。一片平地就是「重复 N 次某列」，用两个字节表达几十列，压缩率极高。

复刻时如果直接把关卡画成二维数组（每格一个值），文件会大几十倍，且丢失「按列流式加载」的能力。

正确做法是保留列式结构：

```js
// 每列：地形高度 + 对象（可选）
{ tiles: [0, 0, 1, 1], objects: [{ type: 'goomba', y: 11 }] }
```

渲染时只维护一个滑动窗口（视野内约 16 列），左出右进。**这是无限横向关卡的标准实现**，做跑酷游戏的直接能用。

## 五、第四条：碰撞别用像素

原作的角色碰撞盒比精灵小，且贴地判定有「容差」。常见错误是拿精灵图尺寸做碰撞，导致角色「差一像素上不去台阶」。

正确的做法是：

- 碰撞盒定义成固定宽高（比视觉小）
- 水平与垂直分离求解（先水平移动判碰撞，再垂直移动判碰撞）
- 台阶容差（向上 1~2 像素自动抬升）

```js
// 分离轴：先 x 后 y，避免斜向撞墙卡住
moveX(dx); resolveHorizontal();
moveY(dy); resolveVertical();
```

这条在 2D 平台游戏里几乎是铁律：**同时求解 xy 必然出 bug**。

## 六、第五条：原作的「不公平」要保留吗

有意思的取舍：原作的很多手感来自硬件限制（比如跑动加速需要按住 B 键、踩敌人有 1 帧判定窗口）。复刻时全盘现代化，手感就变了；全盘照抄，现代玩家觉得「粘」。

这类项目的价值不在玩法，在**让你看到「限制如何塑造设计」**：8 个精灵/行逼出了闪烁与复用，2KB 内存逼出了列式关卡，20 个瓦片调色板逼出了极简美术风格。

## 七、读代码的入口

1. 主循环与固定步长（`update/render` 分离处）
2. 关卡数据结构（列式还是二维数组，一眼能看出作者水平）
3. 碰撞求解（x/y 是否分离）
4. 精灵图集与瓦片渲染（是否合批）

## 八、门槛

- 纯前端项目，`index.html` 直接打开就能跑，几乎没有环境成本
- 没有构建流程，代码组织偏散，读之前先找入口文件
- 素材版权需要注意：复刻项目通常自带绘制素材或使用自由素材

## 九、能搬走的设计

- **逻辑固定步长 + 渲染自由帧率**，是所有游戏的第一条纪律
- **定点/整数运算**，让物理可复现
- **列式关卡 + 滑动窗口**，无限横版的标准解法
- **碰撞盒小于视觉**，是手感的基础
