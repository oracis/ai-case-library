# 100 万用户只收 576 个订阅：免费对弈平台的实时同步架构与算力账

一个免费的国际象棋对战平台，注册用户 100 万+，付费订阅 576 个，月经常性收入（MRR）7,306 美元，近 30 天流水 19,349 美元，累计收入 69,071 美元。

这个数字组合乍看很别扭：转化率只有 0.06%，凭什么活得下去？答案不在运营技巧，在一笔算得过来的工程账——实时对战类产品的边际成本是长连接和带宽，而这个成本低到 0.06% 的转化就能覆盖。这篇把账算给你看，也把这类平台的实时同步架构拆开。

## 一、它做的是什么

免费国际象棋对战平台，官方口径是「Chess.com but free」，2025 年 3 月上线，作者 Mehdi Ben Haddou。核心玩法免费，收入来自可选增值订阅（576 个）。

近 30 天流水 19,349 美元明显高于 MRR 7,306 美元，差额通常来自年付一次性入账或内购——讲增长只能用 MRR 口径，用流水会失真。

## 二、钱从哪来

档案里定价标为「Free」，也就是说主产品不收钱。收入全部来自增值订阅。

这里的关键不是「免费能赚钱」这种正确的废话，而是：免费产品的成本结构决定了它可以容忍极低的转化率。付费产品获客成本压着定价，免费产品获客成本接近零，只要能覆盖服务器成本，0.06% 的转化就是纯利润。

服务器成本到底多少？下一节算。

## 三、实时对战要解决的四个工程问题

先说清楚：下面的代码是按公开产品形态给出的参考实现，不是官方披露的架构。但对做同类产品的人，这套结构基本是行业共识。

### 3.1 棋局状态：别存「当前局面」，存事件流

新手最容易犯的错是把棋局存成一张不断更新的表——`fen` 字段原地覆盖。这样做的直接后果是：复盘没了、悔棋做不了、争议局面无法回溯。

正确做法是 event sourcing：FEN 只作为当前快照，权威数据是走法序列。

```ts
type Move = { san: string; uci: string; at: number }; // at 用服务端毫秒

type Game = {
  id: string;
  fen: string;        // 当前局面的快照
  moves: Move[];      // 权威历史，重放可复原任意时刻
  white: string;
  black: string;
  clock: { w: number; b: number; lastAt: number; turn: 'w' | 'b' };
};
```

复盘就是 `moves.reduce(apply)`，悔棋就是 pop 最后一个 move 后重算 FEN。存储量也不大：一局 80 步，每步几十字节。

### 3.2 时钟：绝对不能信客户端

所有棋类平台都踩过这个坑——客户端报「我走的时候还剩 3 秒」，服务端照单全收，就等着被改本地时间的人收割。

时钟必须是服务端权威，客户端只做乐观渲染：

```ts
function remaining(g: Game, now: number): number {
  const elapsed = now - g.clock.lastAt;
  return g.clock.turn === 'w' ? g.clock.w - elapsed : g.clock.b - elapsed;
}

// 走子时结算：扣掉本方思考时间，再切边
function applyMove(g: Game, m: Move): Game {
  const left = remaining(g, m.at);
  if (left <= 0) return { ...g, result: 'timeout' };
  const clock = { ...g.clock, [g.clock.turn]: left, lastAt: m.at, turn: g.clock.turn === 'w' ? 'b' : 'w' };
  return { ...g, fen: applyFen(g.fen, m.uci), moves: [...g.moves, m], clock };
}
```

注意 `lastAt` 也是服务端写的——客户端只发「我要走 e2e4」，不发时间戳。

### 3.3 断线重连：全量 sync + 增量补齐

移动端切后台，WebSocket 十有八九被系统杀掉。重连之后如果只补增量，中间丢的消息就永久丢了，棋盘会花。

所以要设计两条通道：

```ts
type ServerMsg =
  | { t: 'move'; seq: number; san: string; fen: string; clock: { w: number; b: number } }
  | { t: 'sync'; seq: number; game: Game }  // 重连时全量下发
  | { t: 'end'; result: 'w' | 'b' | 'draw'; reason: 'checkmate' | 'timeout' | 'resign' };

// 客户端重连带 lastSeq，服务端能补就补，补不了就 sync
```

客户端侧还要做乐观更新 + 回执校正：本地先落子立即渲染，收到 `move` 消息后以服务端 FEN 为准覆盖。否则网络抖一下，用户就看着棋盘停半秒。

### 3.4 走法校验与和棋判定

走法合法性必须在服务端再校验一遍，客户端校验只是体验优化。判「三次重复局面和棋」需要哈希局面：

```ts
// Zobrist 哈希：每一位棋子一个随机数，局面哈希 = 异或
// 关键点：hash 里必须包含「该谁走」和「易位权」，否则不同局面会撞
function posKey(fen: string): string {
  const [board, turn, castling, ep] = fen.split(' ');
  return [board, turn, castling, ep].join('|');  // 简化版，工程上直接比这四段
}
```

踩过的坑：只比棋盘部分，会把「同一棋盘但轮次不同」判成重复局面。半回合计数（`halfmove clock`）也要一起看，五十步和棋靠它。

## 四、算力账：0.06% 转化为什么够

回到最开始的问题。按 100 万注册用户估：

| 项 | 估算 |
| --- | --- |
| 峰值在线率 | 5%（约 5 万在线） |
| 同时对局 | 约 2.5 万局 |
| 长连接数 | 5 万条 WebSocket |
| 单条 move 消息 | 约 200 字节 |
| 单局总流量 | 80 步 × 200B × 2 端 ≈ 32KB |
| 对局状态存储 | 每局 < 10KB，可全部放内存 |

5 万条长连接，Go 或 Node 单实例撑 2~5 万是常见水平，配上状态全内存 + Redis 兜底，8 台 4C8G 的量级足够。按云厂商 50 美元/月一台算，服务器成本 400 美元/月上下，加上 CDN 和数据库，1,000 美元/月以内能打住。

对 7,306 美元的 MRR，服务器成本占比不到 15%。**这就是 0.06% 转化能成立的真正前提：不是用户够多，是每用户成本够低。**

免费产品的算术是「人数 × 极低转化 − 极低成本」，三个因子缺一个就崩。

## 五、能搬走的部分

- **实时互动场景天然适合免费打法**：留存来自「对手在那里」，不需要内容团队持续喂养。
- **成本结构决定定价自由度**：先算清单用户边际成本，再决定能容忍多低的转化率。
- **打订阅制霸主就打价格**：但要找到增值订阅这种非价格收入兜底，否则纯免费就是纯烧钱。
- **选流量在涨的品类**：国际象棋这两年靠直播和短视频复兴，免费增长才有燃料。

## 六、给做同类产品的人

- 棋局、协作、白板这类「双方状态必须一致」的产品，一开始就按事件流设计，别等要复盘了再重构。
- 时间相关的一切都放服务端。客户端时间只用来渲染。
- 长连接产品把「重连」当一等公民做，别当异常处理。
