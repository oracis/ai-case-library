# Next.js SaaS 脚手架的四个集成点：认证、支付 webhook、邮件与 schema 的工程取舍

一个卖 Next.js 脚手架的产品，一次性买断 199 / 249 / 299 美元三档，两年累计收入约 127 万美元，近 30 天约 2,989 美元，买家约 8,348 人，一个人维护。

数字不是重点。重点是它卖的到底是什么：**不是代码，是把「每个 SaaS 都要重写一遍的那部分」提前写好**。这篇拆这类脚手架的四个集成点，以及一次性买断模式对交付与维护的真实影响。

## 一、口径先说清：它天然没有 MRR

一次性买断的产品在按月订阅的榜单上是缺失的——不是没收入，是它的计量单位跟榜单不兼容。

- 累计收入约 127 万美元，近 30 天约 2,989 美元
- 定价 199 / 249 / 299 美元三档（原价更高，长期打折）
- 一人团队，2023 年 9 月上线

引这个数字是为了说明一件事：**收入前置、成本后置**。现金一次性到账，但 issue、依赖升级、上游 breaking change 的义务是无限期的。后面会展开。

产品内部的目录结构与依赖版本没有公开，所以下面谈的是这类脚手架的通用工程做法，不臆测它的源码。

## 二、为什么是 Next.js

卖给同行的脚手架，验收标准不是架构优雅，而是**买家 clone 下来半小时内能跑起来**。在这个约束下，Next.js 几乎是默认答案：

1. 一套路由同时承载页面、API、webhook。Route Handlers 让 `/api/stripe/webhook`、`/api/auth/*` 和业务页面待在同一个部署单元里，省掉「前端 + 后端」两套脚手架的说明成本。
2. Server Component 里直接读 session 和数据库，鉴权逻辑不用在 client 端复刻一遍。
3. 部署适配面广，Vercel / 自建 Node / Docker 都能跑，买家不会被平台锁死。
4. 生态即文档。买家搜「Next.js + Stripe」能搜到大量答案，支持负担直接下降——这对一次性买断产品是生死线。

代价同样清楚：框架大版本迭代快，「开箱可跑」的承诺会被上游 breaking change 反复挑战。

## 三、集成点一：认证，卖的是「别自己写密码」

通用做法是 OAuth（Google / GitHub）+ Magic Link 二选一或并存，**永远不要**在脚手架里自己实现密码哈希和重置流程。

```ts
// 服务端守卫，而不是只在客户端隐藏按钮
export async function requireUser(req: Request) {
  const session = await getSession(req);        // httpOnly cookie
  if (!session?.userId) throw new HttpError(401);
  return session.userId;
}
```

- session 放 httpOnly + SameSite cookie，别塞 localStorage
- 授权判断放服务端（middleware 或每个 handler 入口），客户端只做体验
- OAuth 回调地址、scope、本地开发用哪个 callback URL 必须写进 README——这是买家最高频的踩坑点

## 四、集成点二：支付，真正的工程量在 webhook

Checkout 页面几十行就能接完，坑全在异步回调。三条硬规矩：

```ts
// 验签 → 幂等 → 落库 → 再发货
const event = verifySignature(rawBody, sig, secret);
if (await db.processedEvents.exists(event.id)) return ok();   // 幂等

await db.transaction(async (tx) => {
  await tx.processedEvents.insert(event.id);
  switch (event.type) {
    case 'checkout.session.completed': /* 开通权益 */ break;
    case 'invoice.payment_failed':     /* 降级/提醒 */ break;
  }
});
return ok();   // 先快速返回，重活丢队列
```

- **必须验签**，且要用 raw body，不能被框架的 body parser 吃掉
- **必须幂等**，支付网关会重投；用 `event.id` 去重
- **先落库再发邮件**，顺序反了就会出现「用户收到欢迎邮件但账号没开通」
- 处理超时返回 5xx 让它重试，别吞异常返回 200

对一个卖两百美元的脚手架来说，这段代码的价值远高于 UI——因为买家用它接的是真钱。

## 五、集成点三：邮件，事务性发送外包

注册验证、支付成功、密码重置，全部走第三方 API（Resend / Postmark 之类），模板即代码，跟着仓库走。

- 邮件发送**不要放在 webhook 主链路里同步阻塞**，失败会拖垮支付回调；投队列或 fire-and-forget + 重试
- 所有发送点做幂等键，否则重投的 webhook 会给用户发三封欢迎邮件

## 六、集成点四：schema 越薄，越好卖

买家一定会换库、换 ORM、加字段。所以脚手架的 schema 只应包含四张表级别的抽象：

1. 用户
2. 会话 / 账号绑定
3. 订阅或权益（用有效期，不用布尔值）
4. 已处理事件（幂等表）

附加业务表越少，退货率越低。迁移给成可重放的 migration，而不是一份 `schema.sql` 让用户手动灌。

## 七、一次性买断的真实影响

这是这个案例最值得技术人看的部分：一条收入前置、成本后置的曲线。

- **现金一次性到账，维护义务无限期**。127 万美元是过去时，2,989 美元是现在时；但 issue、依赖升级、上游变更的成本是持续的。
- **版本漂移不可避免**。Next.js 大版本、支付 API 版本、各家 OAuth 策略变更，任何一条都会让「开箱可跑」变成「跑不起来」，而你收不到一分续费。
- **支持成本必须被边界框住**：明确「只保证 X 版本开箱可跑」、给 issue 模板、把常见问题写进文档、把定制开发明确排除在买断范围外。
- **分档定价应该给「支持优先级」定价**，而不是阉割核心功能——功能阉割会制造两类用户和两套文档，维护成本反而翻倍。
- **没有订阅就没有续费压力，也没有持续现金流付维护**。这就是它从占创始人月收入约 40% 掉到约 3.5% 的结构性原因：不是产品坏了，是模型本身没有复利。

结论：脚手架是现金流工具，不是资产。

## 八、落地检查清单

要做一个同类脚手架，按这个顺序自查：

1. 买家 clone 后能否在 30 分钟内跑通登录 + 一次测试支付？不能就别发版
2. webhook 是否验签 + 幂等 + 先落库后发货？
3. 邮件、队列、数据库是否都能一键替换，且有迁移脚本？
4. README 是否覆盖所有第三方后台配置步骤（回调地址、密钥、测试卡号）？
5. 维护边界是否写进商品页（支持哪些框架大版本、什么不包含）？
6. 上架前，你的分发渠道有多少人？这一项权重最高
