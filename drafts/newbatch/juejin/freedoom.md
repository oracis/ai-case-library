# Freedoom 不写引擎，只重画素材：Doom WAD 格式与「自由素材」的兼容性工程

一个奇怪的项目：它不实现游戏引擎，也不做玩法，只提供一套**素材包**——贴图、怪物、音效、关卡，全部自由授权。把它放进任何 Doom 引擎，就能跑出一个完整的 FPS。

引擎本身早就以 GPL 开源了，卡住所有人的是原版素材的版权。Freedoom 做的事，是把「引擎自由、内容不自由」这个缺口补上。

从工程角度看，它是一份极好的**二进制格式与兼容性**教材。

## 一、它到底交付了什么

- 产物：`freedoom1.wad`、`freedoom2.wad`（对应 Doom 与 Doom II 的关卡集）
- 内容：全部贴图、精灵、音效、音乐、关卡地图，自由许可
- 不包含：引擎代码、游戏逻辑

所以它能被 GZDoom、Chocolate Doom、PrBoom+ 等引擎直接加载——**只要引擎兼容原版 WAD 约定**。

这就是关键：它不是「做一个新游戏」，而是「在既有二进制契约上，替换全部内容」。

## 二、WAD 格式：一个 1993 年的容器

WAD 是 Doom 的资源容器，结构极其简单——一个头 + 一张目录 + 一堆数据块（lump）：

```c
typedef struct {
    char    id[4];         // "IWAD"（官方）或 "PWAD"（补丁/自定义）
    int32_t numlumps;      // 数据块数量
    int32_t infotableofs;  // 目录表在文件中的偏移
} wadinfo_t;

typedef struct {
    int32_t filepos;       // 该 lump 在文件中的偏移
    int32_t size;          // 字节数
    char    name[8];       // 8 字节名字，不足补 0
} lumpinfo_t;
```

整个格式就这两个结构。没有版本号、没有校验和、没有压缩（压缩是引擎层做的）。

**lump 的「名字」承担了类型系统的职责**。引擎靠名字和它在目录里的位置判断这是什么：

- `PLAYPAL`：调色板（256 色）
- `S_START` / `S_END`：中间的 lump 全是精灵（sprite）
- `F_START` / `F_END`：中间全是平面贴图（flat）
- `MAP01`…：关卡，后面紧跟 `THINGS`/`LINEDEFS`/`SECTORS` 等子 lump

这种「用标记名字划分命名空间」的做法，等于在一张平表上模拟目录结构。简陋，但极其好解析——**任何语言几十行就能读完一个 WAD**。

## 三、精灵帧的命名规则：把动画写在文件名里

Doom 精灵的命名是「4 字符基名 + 帧字母 + 角度 + 可选帧」：

```
TROOA1  → 基名 TROO（Imp），帧 A（站立），角度 1（正面）
TROOA2A8 → 帧 A，角度 2 到 8（8 方向旋转），且是动画帧
POSSA1  → 基名 POSS（Zombieman），帧 A
```

这意味着：**新增一个敌人不需要改任何代码**，只要按规则命名精灵图，引擎自动识别朝向与动画序列。

这是把「数据即逻辑」推到极致的形态——连状态机都编码在文件名里。代价是可读性差（没人记得住 TROO 是什么怪），收益是零代码扩展。

## 四、兼容性才是真正的难点

做一个「能跑」的素材包不难，难的是**在所有引擎上都跑对**。Freedoom 面对的现实约束：

1. **调色板必须严格 256 色**。所有贴图要量化到 `PLAYPAL` 的索引色，否则颜色全错
2. **flat 贴图必须是 64×64**，纹理尺寸必须是 2 的幂且不超过引擎上限
3. **关卡要满足引擎的几何约束**（sector 必须闭合、不能有非法 linedef 引用）
4. **不同引擎支持不同扩展**（Boom 的传送枪、GZDoom 的 3D floor），素材要用共同子集

第 4 条是兼容性工程的核心：**只使用所有目标引擎都支持的最小特性集**，才能做到「一份素材到处跑」。

这条对做跨平台产品的人很直接：**你以为你在用能力，其实你在用交集**。扩展特性用多了，兼容性立刻塌。

## 五、行为也要能改：DeHackEd

只换素材还不够——原版怪物的数值、武器参数都硬编码在引擎里。Freedoom 用 DeHackEd 补丁（`DEHACKED` lump）改这些：

```
Patch File for DeHackEd v3.0
Thing 1 (Player)
Initial frame = 0
Hit points = 100

Weapon 1 (Fist)
Ammo type = 0
```

引擎读这个 lump 后覆盖内部表。这是 1993 年的「配置覆盖」方案：**不重新编译，靠补丁表改行为**。

## 六、构建流程

素材源文件（PNG、WAV、地图源文件）通过脚本打包成 WAD：

- 图像量化到调色板
- 精灵按规则重命名
- 地图从编辑器格式编译成 Doom 二进制格式
- 最后按目录顺序拼成 WAD

这套流程本身值得看：**二进制产物的可复现构建**（同样的源文件必须打出字节一致的 WAD，否则多人联机会因为校验不一致掉线）。

## 七、读/用什么入口

1. `wadinfo_t` 与 `lumpinfo_t` —— 先写个 30 行的 WAD 目录读取器，整个格式就通了
2. `PLAYPAL` 与 `COLORMAP` —— 理解 256 色调色板与光照衰减表
3. `S_START`/`F_START` 命名空间 —— 理解 lump 的分类约定
4. 用 `deutex` 或 `wadbuild` 解包官方 WAD，对照着看

## 八、门槛

- 素材体量大，仓库克隆慢
- 地图编辑需要专门的 Doom 关卡编辑器（如 Ultimate Doom Builder，只有 Windows）
- 打包脚本依赖 Python + 图像工具链，环境搭建有一定门槛

## 九、能搬走的设计

- **容器格式越简单，存活越久**：两个结构体撑了三十年
- **用命名约定承担类型信息**，能省掉一层 schema
- **兼容性 = 功能交集**，扩展特性用多了就没有「到处能跑」
- **改行为用补丁表，不改二进制**，是老系统可维护的关键
