# 一个体育投注推荐 App 的技术栈：赛程数据、定时推送与订阅付费墙

月经常性收入 337 美元，订阅价 34.99 美元/月，覆盖足球、篮球、网球、美式足球、棒球五个品类，每天推送专家投注建议。

这是一个技术上「薄」但结构完整的订阅制产品：数据接入、内容生产、定时推送、付费墙、订阅生命周期，一个都不少。拆它的价值在于——**当你只有几百美元月收入时，技术栈应该有多轻**。

## 一、这类产品的技术骨架

四个组件，没有第五个：

```
赛程/赔率 API ──> 每日任务（生成建议）──> 推送服务 ──> App
                                    └──> 内容页（付费墙）
                                             │
                                     订阅（Stripe / IAP）
```

没有实时计算，没有推荐算法集群，没有用户行为建模。全部是「定时跑批 + 分发」。

对这种规模的产品，**过度设计比设计不足更致命**。一台小机器 + 一个定时任务就能跑完所有事。

## 二、数据源：体育数据是最大的成本项

体育数据 API 的计费模式跟常规 API 完全不同，需要先看清：

| 类型 | 典型计费 | 特点 |
| --- | --- | --- |
| 赛程/比分 | 按请求数或按赛季套餐 | 请求量可控 |
| 赔率（odds） | **按请求数 + 按博彩公司数** | 极贵，多一家赔率商就翻倍 |
| 历史数据 | 一次性打包 | 便宜，但更新慢 |

关键工程结论：**赔率数据的成本随「赔率商数量 × 轮询频率」线性增长**。想做赔率对比，先算这笔钱。

优化手段（都是真实有效的）：

- 只在赛前窗口拉（比如开赛前 24 小时），不要全量轮询
- 缓存赛程表（一天一变），只对临近赛事拉赔率
- 用 webhook 或推送接口替代轮询（部分厂商支持）

```python
# 只在赛前 T-24h 到 T-30min 之间拉赔率
def should_fetch(match, now):
    delta = match.kickoff - now
    return timedelta(minutes=30) <= delta <= timedelta(hours=24)
```

## 三、内容生产：定时任务的时间窗

每日建议必须**在用户下注前到达**，所以发布窗口是硬的。跨时区是第一个坑：

- 赛事按当地时间开赛，用户可能在任意时区
- 「每天几点推送」不能固定成服务器时区的时间

正确做法是**按赛事开赛时间倒推**，而不是按「每天早八点」：

```
对每个品类、每个开赛日：
  开赛前 6 小时生成建议 → 开赛前 4 小时推送
```

这样推送时间自然随时区与赛程浮动，用户收到的时候总是「还来得及」。

## 四、推送：可靠性比送达量重要

推送走 APNs / FCM，工程上有三条经验：

1. **推送是「尽力而为」通道**，不是可靠消息队列。重要内容（付费用户专享建议）必须同时在 App 内可查，不能只靠推送
2. **推送令牌会失效**（用户卸载、重装、系统清理），要有失效清理任务，否则队列里堆死令牌
3. **高频推送会触发系统限流**，五个品类一次群发等于五次打扰，要合并成一条

```sql
-- 令牌失效要能清理，别只 insert 不 delete
create table push_token (
  token       text primary key,
  user_id     text not null,
  platform    text not null,      -- 'apns' | 'fcm'
  updated_at  timestamptz not null default now(),
  failed_cnt  int not null default 0
);
-- failed_cnt 连续超阈值 → 删除该令牌
```

## 五、付费墙：订阅在 App 内外是两套账

这是这类产品最容易被忽略的工程决策：**在哪收钱，决定抽成比例**。

- App 内订阅走应用商店 IAP，平台抽 15%~30%
- Web 订阅走 Stripe，抽 2.9% + 固定费

同样的 34.99 美元，走 IAP 到手可能只有 24 美元，走 Web 能拿到 33 美元。差距接近 30%。

所以很多订阅类 App 的做法是：**App 内只做登录和内容，引导 Web 完成订阅**（注意各平台对「引导站外支付」的政策不同，需要按当期规则处理）。

技术上要打通的是「两端权益一致」：

```sql
create table entitlement (
  user_id            text primary key,
  source             text not null,       -- 'iap' | 'stripe'
  current_period_end timestamptz not null
);
```

两个来源写同一张权益表，服务端只认 `current_period_end`，不认来源。这样换渠道不影响业务逻辑。

## 六、成本结构：337 美元收入能活吗

按月收入 337 美元倒推：

| 项 | 月成本（估） |
| --- | --- |
| 服务器（1 台小机 + 数据库） | 20~50 美元 |
| 体育数据 API | 50~200 美元（取决于赔率） |
| 推送（APNs/FCM） | 0 |
| 邮件/监控 | 5~15 美元 |

毛利在 200~250 美元区间。这意味着：**这个产品能养活自己，但养不活一个人**。所以它的定位天然是「副业级现金流」，不是主业。

技术上的推论很实用：**收入在千美元级时，任何一个月成本超过 100 美元的第三方服务都要重新审视**。

## 七、这类产品的真实风险

不是技术风险：

- **合规**：投注建议在多数地区受监管，表述边界很窄（不能承诺收益）
- **平台政策**：涉及赌博内容的应用在商店审核更严
- **数据源依赖**：单一 API 涨价或停服，产品直接停摆

工程上能做的是：数据源留一个可替换的适配层，别把某个厂商的字段名写进业务代码。

## 八、能搬走的设计

- **定时跑批 + 分发**，是小体量订阅产品的正确形态，别做实时
- **按事件倒推推送时间**，而不是按固定钟点
- **推送不可靠**，重要内容必须在 App 内可查
- **收钱的渠道决定毛利**，订阅产品先把这笔账算清
- **权益表只认有效期**，不认来源
