# 做一个免费国际象棋对战平台，工程上要过哪几道关

棋类对战看起来是最"简单"的一类产品：规则固定、棋盘固定、没有物理引擎、没有实时渲染压力。但真做起来，难点全在别处——状态归属、断线恢复、时钟可信、匹配效率，以及"免费"这两个字背后的成本结构。

Chessigma 是一个 2025 年 3 月上线的免费国际象棋对战平台，官网口号写得直白：Chess.com but free，公开口径 100 万+ 用户。它的具体实现没有开源，本文不猜它的内部架构；下面讲的是这一类系统必须解决的工程问题，以及能从它公开的形态里看到的部分。

## 一、棋局状态该由谁算

这是第一个必须拍板的决定，而且是架构级的分叉。

**客户端权威**：双方各自跑棋规校验，只把走子动作同步给对方。好处是服务端几乎不耗 CPU，一台机器能挂很多局；坏处是客户端可篡改，改一行 JS 就能走一个非法着法，或者直接宣布自己赢。

**服务端权威**：客户端只发送"意图"（从 e2 到 e4），服务端校验合法性、更新局面、再广播结果。每步都要在服务端跑一次走法生成，但换来的是不可作弊。

棋类产品如果没有排名和积分，客户端权威勉强能用；一旦有 ELO、有天梯、有奖金，就必须服务端权威。伪代码大致是这样：

```text
onMove(gameId, from, to, promo):
    g = load(gameId)
    if not isLegal(g.position, from, to): return reject
    apply(g, from, to, promo)          # 更新局面
    g.history.push({from, to, promo, t: serverNow()})
    broadcast(g.room, g.history.last)  # 只广播增量
    if isGameOver(g): settle(g)
```

关键点是 `isLegal` 必须在服务端跑。国际象棋的走法生成不难写（滑子用射线扫描，马和兵查表，王要处理将军），难的是把它写对——吃过路兵、王车易位、升变、三次重复局面、五十步和棋，这几条漏一条就会在天梯上被反复利用。

## 二、断线重连：一局棋十分钟，连接一定会断

移动端尤其明显：地铁、电梯、切后台、来电。一局 10 分钟的快棋，断线几乎是必然事件，不是异常。

两种常见做法：

1. **全量快照**：重连时服务端把整个 `history` 重放一遍给客户端。简单，但如果一局走了 80 步，每次重连都传 80 条记录。
2. **增量 + 序号**：每条消息带自增 `seq`，客户端重连时报自己最后收到的 `seq`，服务端从 `seq+1` 补发。

实际系统通常两者结合：`seq` 落后太多（比如超过 20 条）就发全量快照，否则补增量。

还有一个坑：**重连期间的超时判定**。多数平台在断线后仍照常走时钟，只给很短的宽限（比如 15 秒）；如果客户端能靠"断线暂停"来逃避时间压力，这个机制在几分钟内就会被玩坏。宽限时间和时钟必须由同一个服务端计时器裁决，不能各自为政。

## 三、时钟：别信客户端的表

棋类产品的时钟和普通倒计时不一样：只在轮到该方走子时走，落子瞬间切换。这里最容易出的错是**用客户端时间做裁决**。

客户端时钟只能用于显示。真正的判定要在服务端做：记录每步的 `serverNow()`，用相邻两步的时间差累减。客户端改系统时间、改浏览器时钟、甚至改 JS 里的 `Date.now`，都影响不到服务端账本。

```text
step n: 白方剩余 -= (now - lastMoveAt)
if 白方剩余 <= 0: 判负，触发 flag fall
```

对免费产品来说，这里还有个细节：**断线超时和超时判负要分开处理**。前者是连接问题，后者是比赛结果，混在一起会让用户觉得"网络一抖就输棋"，体验非常差。

## 四、匹配：池子冷的时候，算法再好也没用

ELO 匹配的教科书做法是按分数区间找人，等待时间越长区间越宽。但免费产品的真实困境是**同时在线人数不够**，尤其在小语种时段和低分段。

几个实际在用的补救手段：

- **区间随时间放宽**：等待 5 秒 ±50 分，15 秒 ±150 分，30 秒不设上限。
- **机器人兜底**：低分段长时间匹配不到就派一个本地引擎驱动的账号上场，棋力按用户分数调。这招能显著降低"匹配失败"的流失，但必须明确标注，不然被识别出来口碑会崩。
- **重连优先**：断线重连的玩家优先回原局，不要当新玩家重新匹配。

顺带说一句配对池的工程细节：匹配服务一定要和棋局服务解耦。匹配是短连接、高频、可水平扩展；棋局是长连接、有状态、需要粘性。塞进一个服务里，扩容时两边互相拖累。

## 五、"免费"的成本结构

棋类对战的消息量小得惊人：一步棋的 UCI 表示是 4~5 个字节（`e2e4`、`e7e8q`），加上序号和时间戳也就几十字节。一局 10 分钟快棋，双方各走 40 步，总流量不到 5 KB。

这意味着**带宽不是瓶颈，连接数才是**。一台 4 核 8G 的机器，用长连接框架撑住几千到上万在线，是完全现实的量级。棋局状态本身也很小：一个局面用 FEN 表示不到 100 字节，一局的历史记录全部存内存也就几十 KB。

所以这类产品的固定成本主要落在三块：长连接的机器、静态资源和 CDN、以及匹配与统计的数据库。没有视频转码、没有图像推理、没有大模型调用——图形界面在客户端跑，服务端只做裁判。

这也是"免费"能成立的前提：用户涨十倍，成本大致涨线性，但不需要为每个用户支付一次推理费用。

## 六、从 Chessigma 的公开形态能看到什么

只看公开信息，能确认的其实不多，但也不是没有：

- **多端策略**：iOS 客户端在架，由 ARCHE LABS LTD 发布，版本 2.0.0，最近更新在 2026-10-05。做对战平台先上移动端是合理的，棋类用户的碎片时间在手机上。
- **能力被包成了可调用的接口**：作者在 GitHub 有一个 `chessigma-mcp` 仓库，把平台能力按 MCP（Model Context Protocol）的形式暴露出来。这个动作说明它的后端不是纯页面驱动，至少有一部分业务能力是可以被程序化调用的。
- **免费是明面上的定价策略**：核心对弈不收费，靠可选增值项支撑。公开数据里付费用户是 576 个这个量级，与"100 万+ 用户"相比约为万分之六——这正是前文说的"连接数成本 + 极低转化率"结构的典型样本。

需要说明的是：以上只是公开形态，不等于它的技术栈。它有没有用服务端权威、怎么处理断线，外部看不到。

## 七、如果你要自己做，先做什么

按投入产出排，我会这样切：

1. **先做单机对 AI**，把棋规校验写对（尤其是特殊走法）。这一步不做完，后面的联机全是在错的基础上叠。
2. **再做房间式对战**，服务端权威 + WebSocket，先不做匹配，手动开房。这一步能验证状态同步和断线重连。
3. **最后做匹配和积分**。匹配依赖在线人数，冷启动阶段做了也是空转。
4. 时钟和超时判定从第一天就放服务端，别等到出问题再改——这类逻辑一改就要动历史数据。

## 小结

棋类对战平台的工程量，不在"实现国际象棋"这件事上，而在**把一整局比赛的状态、时间和结果都裁定在一个可信的地方**。免费只是商业选择，它把压力从"每用户成本"转移到了"连接数与转化率"上，而这两件事的工程解法和收费产品没有区别。
