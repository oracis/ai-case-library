# 一个链接承载卖货页、会员与社群：单页交付面的架构取舍

创作者工具的交付面通常被拆成三块：卖货页、会员中心、内容发布。Stan 把三块压进同一个可分享链接——买家打开链接就能完成交易、进社群、续会员，创作者不用自建站点，也不用单独对接支付渠道。这个取舍对工程的含义比看上去深。

## 链接即交付面：把三种意图压进一份渲染契约

一个链接承载多种意图，路由不能靠路径区分，只能靠**状态**区分：

- 未登录访客 → 商品与档位视图
- 已登录未购买 → 结算入口
- 已购买 → 会员内容与社群入口
- 会员过期 → 续期入口同页呈现

好处是分享出去的 URL 永不失效；代价是同一份页面要按四套权限状态渲染，权限判断必须前置到渲染之前，否则会先吐内容再拦人。

## 支付网关直读：数字从 API 来，不是后台自报

这类平台最容易含糊的一点是规模数据从哪来。公开口径注明由支付侧 API 直连验证：MRR 3,569,654 美元、累计 76,627,685 美元。

技术上意味着取数链路是「平台后台 → 支付商 API → 只读快照」，而不是运营手填。好处是可复核；风险也明确：快照会变，任何转述都得带上时点。

## 会员状态机：宽限期与跨产品授权

周期型交付最容易在边界上出错，必须先定义清楚三个状态：

- **生效中**：可访问全部已购内容
- **宽限期**：扣款失败但未终止，保留访问并提示更新支付方式
- **已终止**：内容降级为只读，社群权限回收

跨产品授权是第二个坑：同一买家买了两个社群，权限要按 (买家, 产品) 二元组授权，而不是按买家整体开关——否则退掉一个会误伤另一个。

## 结算对账：冲正与幂等重放

按交易额分成，对账要处理三件事：

- **退款冲正**：订单退款后对应分成必须冲回，不能只记正向流水
- **拒付（chargeback）**：发生在结算周期之后，得允许回溯调整历史周期
- **回调幂等**：支付回调可能重复投递，处理端按事件 id 去重，重放不产生二次入账

这三条不做，账面上就会出现「已结算但已退款」的幽灵流水，且越滚越大。

## 可迁移的经验

- 交付面能收成一个链接时，收成一个链接：分享成本是产品最贵的摩擦之一
- 规模数据要么来自支付侧 API，要么标注为估算，中间态最危险
- 周期交付系统先定义状态机与授权维度，再谈功能
- 把「冲正」当一等公民，别等对不上再补
