# 从零搭一个 Next.js SaaS 模板：登录态、支付 Webhook、邮件队列、数据库迁移的工程细节与踩坑清单

> 平台：csdn ｜ 案例：ShipFast（shipfast）｜ 状态：待确认（本地稿，未推送、未发布）

做一个 SaaS，前两周的代码几乎永远是同一份：登录、付费、发信、建表。把这部分抽出来做成模板，是很多独立开发者的第一反应。这篇不谈商业模式，只谈**如果真要把这套东西做成能交付给他人的模板，工程上要处理哪些细节**。

## 目录结构：先把边界划出来

模板最怕的是"什么都有，什么都耦合"。建议第一天就按路由组切干净：

- `app/(marketing)/` — 落地页、定价页，无登录态
- `app/(auth)/` — 登录、回调、登出
- `app/(dashboard)/` — 需要登录的业务区
- `app/api/webhook/stripe/route.ts` — 支付回调，永远单独一个入口
- `lib/auth/session.ts` — 会话读取与校验，只有这一处
- `lib/db/schema.ts` — 表结构，唯一真相
- `lib/mail/queue.ts` — 入队，不含发送逻辑

判断标准很简单：**改登录方式时，需要动几个文件？** 超过 3 个就说明边界没切好。

## 登录态：能跑通不等于能用

常见组合是 OAuth（Google / GitHub）+ 邮箱链接。细节：

1. 会话可以放无状态 JWT cookie（`httpOnly`、`secure`、`sameSite=lax`），也可以落 session 表。前者省一次查询，后者能主动踢人，模板里建议做成可替换的两个实现。
2. `middleware.ts` 只做"未登录跳转"这种粗判，**真正的权限校验必须在 server component 或 route handler 里重做一次**。Middleware 拦不住直接打 API 的请求。
3. 邮箱做小写归一化再存，`email` 上建唯一索引；不要假设一个邮箱只对应一个 provider，用户先 GitHub 后 Google 登录是很常见的。
4. 踩坑：Edge Runtime 里拿不到部分 Node API；cookie 塞太多用户信息导致超限；会话没有滑动续期，用户填表单填到一半被踢出去。

## 支付 Webhook：幂等比功能重要

Webhook 是模板里最容易写错、也最难排查的部分。

- **验签必须用原始 body**。先 `await req.text()` 拿到原文再验签，不要先 `req.json()` 再序列化回去，签名会对不上。
- **建一张事件表**，`stripe_event_id` 加唯一索引。收到事件先尝试插入，插入冲突就直接返回 200。这样重复投递天然幂等。
- **不要依赖事件到达顺序**。`checkout.session.completed` 和订阅类事件可能乱序，落库时以 customer id 做 upsert，而不是以"谁先到"为准。
- **永远不要相信前端跳回的成功页**。跳转只是用户体验，开通权限只认 webhook。
- **webhook 里只做落库和入队**，不要在里面同步发邮件、调第三方接口。处理慢了平台会重试，重试又叠加副作用。
- 本地调试用 Stripe CLI 转发事件，注意转发时 header 和原始 body 都要保留。

## 邮件队列：请求链路里不要发信

在 HTTP 请求里同步发信的问题很实在：超时、失败重试导致重复发送、供应商限流直接拖垮接口响应。

推荐 outbox 模式：

1. 业务事务里往 `mail_outbox` 插一行：收件人、模板名、参数 JSON、状态、重试次数、下次重试时间。
2. 用 cron 或定时函数轮询待发送记录，发送成功后置为 sent，失败按指数退避更新 `next_retry_at`，超过上限置 failed。
3. 用一个业务幂等键（例如 `order_paid:123`）建唯一索引，保证同一事件只入队一次。
4. 开发环境把邮件写到本地文件或控制台，别真发出去。

这套东西代码量不大，但它是"模板能不能卖"的分水岭——买家最常问的就是"邮件发不出去怎么办"。

## 数据库迁移：从第一天就当线上对待

- schema 用 Drizzle / Prisma 管理，迁移文件进版本库，本地和线上跑同一条迁移链。
- 加字段走三步：先加可空列 → 回填数据 → 再加约束或删旧列。一次性改表在线上很容易锁表。
- 部署顺序：**先跑迁移，再上代码**（expand-contract）。新代码兼容旧结构，永远比反过来安全。
- 备一个 `seed.ts`，让别人 clone 下来五分钟内有数据可看。
- 不要提供"直接在线上手改表"的教程，那是模板最常见的售后来源。

## 把重复代码产品化的判断标准

不是"这段代码我写了三遍"就该抽象，而是**这段代码我写了三遍，且第三次我几乎没改**。抽象时注意：

- 买家要的是"能删掉的代码"，不是黑盒依赖。能用 20 行看懂的实现，别封装成 3 层。
- 配置集中到一个 `config` 文件：套餐、价格、功能开关、邮件模板映射。散落在 20 个文件里的配置等于不可维护。
- 交付闭环：`.env.example` + README 的五分钟启动步骤 + 一条能跑通的最小链路（登录 → 付费 → 收到邮件 → 数据落库）。少一环，售后就多一轮。

顺带说一个现实：这类一次性买断的模板（ShipFast 的定价是 $199 / $249 / $299 三档）天然没有续费。公开数据显示它累计收入 $1.27M、约 8,348 名用户，但近 30 天约 $2,989，在创始人的月收入占比从约 40% 降到约 3.5%（数据来源：TrustMRR、Steal What Works）。这是买断模式的结构性结果，不是执行问题——做模板的人最好一开始就按"卖完之后进入维护"来规划，而不是按订阅产品的心态。

## 踩坑清单

1. webhook 用解析后的对象验签，签名永远不对。
2. 事件表没唯一索引，重试时重复发信、重复加额度。
3. 在 middleware 里做权限判断，API 被直接调用绕过。
4. 邮件在请求里同步发送，超时后平台重试，用户收到三封。
5. 会话不续期，用户填长表单被登出。
6. 邮箱大小写不一致，同一用户建出两个账号。
7. 迁移文件手动改线上表，新环境起不来。
8. 定价和套餐写死在页面组件里，改价要全局搜。
9. 模板里留了硬编码的密钥占位符，买家直接提交到公开仓库。
10. 没有最小可运行链路，买家第一步就卡在环境变量。

做完上面这些，模板才算"可以交到别人手里"。剩下的部分——定价、分发、口碑——是另一个话题了。
