# 从事件流到触达幂等：一条意向信号管道怎么搭

做线索类工具，力气最容易花在「模型给这条线索打几分」。真正上线后常出问题的却是另外三件事：同一次职业变动被抓了五遍、三个月前的融资事件还在触发外联、以及同一个收件人同时收到两封话术不同的邮件。本文只谈工程骨架：事件采集、可信度衰减、触达幂等、反馈回流四段怎么接，不涉及任何具体产品的内部实现。

一句背景，仅用于说明这类窄场景系统确实能长期运行：截至 2026-09-16 的抓取日快照，公开口径显示月度经常性收入约 42.4 万美元、活跃订阅 3,944 个；该数值来自 2026-08-14 最后一次成功同步的快照，并非实时值，累计额是另一个分列字段，两者不能互相年化，本文也不据此推算任何现值。

## 一、事件采集：先定「什么事算信号」，再定从哪抓

常见做法是先接一批数据源，再想怎么用；结果就是采集层堆满爬虫适配器，下游拿到的是一堆彼此冲突的字段。更稳的顺序是反过来：

- **把信号定义成不可变事件**：`event_type / subject_id / observed_at / source / payload_hash`，而不是一条会被覆盖的「当前状态」记录。一个人换了工作、一家公司发了融资公告，都是独立事件，允许同一主体有多条。
- **去重按内容哈希，不按 URL 或标题**：同一篇公告被多个站点转载、标题改一个标点，都该算同一事件。聚合站给的徽标只是站点级声明，不等于每个字段都来自一手来源。
- **保留抓取时点与原文指针**：`observed_at`（事件发生）和 `fetched_at`（我们抓到）必须分开存，否则回溯时无法区分「刚发生」和「刚抓到」，衰减计算会整体错位。
- **缺字段显式留空**：没有时间戳、没有主体标识的记录进隔离区，别让下游拿默认值补出一个看起来可信的信号。

## 二、打分与衰减：把信号当成会过期的假设

一个事件本身没有「意向分」，分是我们对「它还值不值得打扰」的估计。这里最忌讳把分数存成一个永不变化的字段：

- **分数 = 基线权重 × 时间衰减 × 适用条件**。融资、招人、换岗三类事件的半衰期完全不同，用同一条曲线会让最旧的事件一直排在队首。
- **阈值取决于打扰成本，不取决于模型指标**。多问一次的成本远低于把人惹烦，所以低分段默认不进外联队列，只留在观察池。
- **模型版本、标签表版本、阈值版本要一起落库**。只换模型不换版本，事后无法还原「当时为什么给它打了高分」，客诉来了只能靠猜。
- **分布外要留出口**：明显不属于任何已定义事件类型的记录，应该显式判「不适用」，而不是在错误类别里挑一个最像的。

## 三、触达幂等：同一线索只能被同一个理由碰一次

发送层是最容易把前面所有努力毁掉的一段。重试、补偿任务、多人同时操作都会让同一条事件被反复消费：

- **幂等键用 `(subject_id, event_type, payload_hash, playbook_version)`**，而不是用线索 ID。同一个人半年后再次换岗是新事件，理应允许再触达；同一次事件被两个 worker 捡到则必须收敛成一次。
- **频控放在队列入口，不是发送函数里**：跨渠道（邮件、站内、社交）共享一个计数器，否则「每个渠道都只发一次」合起来仍是三封。
- **发送状态机要能区分「已排队 / 已发送 / 已回复 / 已退订」**，退订是终态且优先级最高，任何补偿任务都不能把它改回可发送。
- **模板与文案可回放**：保存渲染时的模板版本与变量快照，回复率异常时才能判断是文案变了还是信号质量变了。

## 四、反馈回流：让回复去修正打分，而不是堆更多渠道

把「有没有回复」接回打分，才算闭环；但接错方式会很快把模型带偏：

- **反馈分正负且带延迟窗口**：发出后 24 小时内无回复不是负样本，只是未观测；退订与明确拒绝才是强负样本。
- **按事件类型分别统计，不做全局平均**：某类事件量大但回复差，全局均值会掩盖它，队列还是被它占满。
- **回流只改权重与阈值版本，不改写原始事件**：原始记录保持只读，模型迭代才不会把历史擦掉，也方便做离线回放对照。
- **人工复核留痕**：运营改过的判定要单独记一层，别和模型输出混在同一列，否则分不清是数据变了还是人改了。

## 归纳：这条链路的骨架

```
事件源 → 归一化与内容哈希去重 → 打分（含衰减与适用条件）
      → 幂等键与跨渠道频控 → 渠道发送 → 回复/退订回流
      → 权重与阈值版本更新
```

四段里最容易被跳过的是衰减和幂等：它们不产生看得见的新功能，却直接决定这套系统会不会把一次性事件用成长期骚扰。把「信号会过期」和「同一理由只发一次」写进数据结构，比事后在发送层加补丁稳得多。
