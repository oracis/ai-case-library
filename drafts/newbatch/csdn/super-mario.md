# 用 Backbone 游戏引擎复刻超级马力欧兄弟：Sprite、Engine 与关卡数据怎么分层

《超级马力欧兄弟》1985 年在 FC 上发售，是横版卷轴平台游戏的原型：跑、跳、踩敌人、顶砖块、吃蘑菇变大。想理解这类游戏在代码里长什么样，读一个开源复刻项目比读教程有效得多。

这里读的是 martindrapeau/backbone-game-engine（MIT，JavaScript，两百多 star）。它不是完整复刻，而是用一套通用游戏引擎实现了一个马力欧关卡——重点在引擎抽象，不在关卡数量。

## 这个仓库到底是什么

要先把预期放对：仓库里是引擎 + 一份关卡数据，不是可以直接下载来玩的游戏包。跑起来要靠浏览器打开它的 demo 页，或者本地起一个静态服务。原版图片和音效属于任天堂，仓库一般不带——这也是所有经典游戏重实现项目的共同处境。

## 横版平台游戏要解决的四件事

不管用什么语言写，这类游戏的骨架都是四块：

1. **帧循环**：每帧按固定顺序更新输入、物理、碰撞、渲染。
2. **物理与碰撞**：重力、落地判定、与砖块/敌人的 AABB 碰撞。
3. **镜头**：角色走到屏幕中间就推动视口，背景按视差速度分层滚动。
4. **实体管理**：砖块、敌人、道具、角色都是"活着的对象"，有各自的状态机。

马力欧的特殊性在于跳跃手感：起跳高度随按键时长变化、下落比上升快、水平速度有加速过程。这三条不加，玩起来就是"不像马力欧"。

## 核心抽象：Sprite 与 Engine

仓库的 `src/core.js` 定义了两个基础类，这也是整个引擎的骨架：

- **Sprite（精灵）**：一个可绘制、可移动、有状态的实体。它持有位置、尺寸、当前动画帧、碰撞盒，并负责自己的 `update`（每帧逻辑）和 `draw`（绘制）。
- **Engine（引擎）**：持有精灵集合、运行帧循环、做统一的碰撞检测与镜头跟随，并管理输入状态。

这个划分的价值在于：游戏逻辑写在各个 Sprite 子类里，公共的循环、碰撞、镜头只写一次。加一种敌人就是加一个 Sprite 子类，不用改 Engine。

`src/world.js` 承担关卡层的事情：哪些地块是实心的、哪块砖能顶出蘑菇、管道从哪进、终点旗杆在哪。`src/character.js` 和 `src/hero.js` 则是角色层的实现——一个是通用角色行为（移动、受重力、被踩会死），一个是马力欧特有的（吃蘑菇变大、变大会顶碎砖、受伤变小）。

## 精灵动画与碰撞盒

横版游戏里，"看起来对"和"碰撞对"经常是两回事。

马力欧的站立、跑动、跳跃、变大后的每一种形态，都是一组帧图。动画播放只要按时间切帧，但**碰撞盒通常要独立于图像尺寸**：变大的马力欧贴图更高，如果碰撞盒跟着贴图走，就会出现"贴着天花板卡住"或者"明明没碰到却判死"。

常见的做法是给每个精灵定义一到两个矩形碰撞盒（受击盒、攻击/踩踏盒），和绘制用的贴图尺寸解耦。踩敌人时判定的是脚底那一条窄带，不是整个身体。

另一个细节是**碰撞后的位置修正**：检测到与地面相交后，不能只把速度归零，还要把精灵"推"到刚好贴合地面的位置，否则下一帧又检测到相交，角色会抖。

## 关卡数据为什么要独立

如果每个砖块都手写在代码里，改一关就要改代码、重新测。所以关卡通常是外部数据（JSON 或二维数组），引擎读数据生成实体。

仓库里 `super-mario-bros` 目录放的就是这类游戏特定数据——引擎不认识"砖块"和"蘑菇"，是数据告诉它"这里放一个砖块精灵"。

这个分层的直接好处：换关卡不用碰引擎，做关卡编辑器也只需要产出同格式的数据。

## 上手成本

- **运行**：纯前端，静态托管即可；不用打包工具，但需要能起本地 HTTP 服务（直接 file:// 打开有时会被资源加载策略拦）。
- **依赖**：项目比较老，依赖的 Backbone 是 2010 年代的 MV* 框架，和现在的 React/Vue 思路不同——它只做模型与事件，不做视图渲染，所以更适合拿来学结构而不是学主流前端。
- **改造**：想加新关卡就改数据；想加新敌人就加 Sprite 子类；想换操作手感就调跳跃参数。这三条正好对应三处分层边界。

## 小结

读这个项目最值得带走的一件事是分层边界：**引擎管"怎么跑"（循环、碰撞、镜头），精灵管"是什么"（行为、动画），数据管"放在哪"（关卡）**。三者的边界一旦模糊，加一个敌人就会牵动半个项目——这和用什么框架无关。
