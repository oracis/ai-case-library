# 跨站数据求交的假阳性陷阱：一次 80 样本的实测与修法

> 数据时点：2026-11-23 抓取（本机实测，Python 标准库实现）

## 背景：一个看起来很简单的需求

我需要判断一个外部 AI 工具目录站的数据，能不能用来做选品分析。这个站点收录约三点一万个工具，每个工具详情页公开了月访问量、流量来源结构和一张带搜索量与 CPC 的关键词表。

我手上还有另一份数据：一份「有支付网关一手收入」的产品库，一万两千多个条目，收入从支付网关直读。

直觉上的方案很自然：两边按产品对齐，就同时有了「估算流量」和「真实收入」，可以互相校验。真正做下来才发现，**这个对齐是整个实验里最容易出错的一步，而且错的方式非常隐蔽**。

## 一、采集层：三个必须处理的现实约束

用 Python 标准库实现，不引第三方依赖。落地时撞到三个约束，都属于「不处理就会静默出错」的类型。

**1. 默认 UA 直接 403。** 不带完整浏览器请求头的请求会被拒。补上 User-Agent、Accept、Accept-Language、Accept-Encoding 与 Sec-Fetch-* 一组头之后才通。注意要处理 gzip——响应体可能是压缩的，不判断魔数直接 decode 会得到一坨乱码而不是报错，属于典型的静默失败。

```python
with opener.open(req, timeout=30) as r:
    body = r.read()
if body[:2] == b"\x1f\x8b":        # gzip 魔数
    body = gzip.decompress(body)
return body.decode("utf-8", "replace")
```

**2. robots 有 Crawl-delay。** 站点 robots.txt 明确写了 `Crawl-delay: 5`，所以请求间隔按五秒走，不做并发。对应的代价是单轮必须设上限——一个详情页五秒，二十个就是一百秒，这决定了采集器只能按需跑，不能定时跑。

**3. 403 是频次触发的。** 这点值得单说：我以为带上完整请求头就一劳永逸，结果同一天连续抓了大约九十个详情页之后，整个站点开始持续 403——包括之前成功过的首页榜单，隔半分钟复查仍是 403，换页面也没用。所以「请求头齐全」只解决前几十个请求，之后是频次风控。这一点决定了这类采集在设计上就不能进定时任务。

## 二、解析层：正则会「成功」地返回空

详情页是服务端渲染的，可以直接用正则取。但要注意「匹配成功但取到空串」这种情况，它比报错更难排查。

月访问量长这样：`Monthly Visitors:` 后面跟一个嵌套的 div 和 span，值本身是 `6.0B`、`1.2M` 这类带单位的字符串。关键词表是连续三个 `traffic-td` 的 div，分别是关键词、流量、CPC。

```python
m = re.search(r'Monthly Visitors:\s*</div>\s*<div[^>]*>\s*(?:<!---->\s*)?'
              r'<span[^>]*>([^<]+)</span>', page)
visitors = clean(m.group(1)) if m else ""
```

两个实践点：

- 页面里可能混着框架插入的注释节点（`<!---->`），正则里要留可选的空节点，否则整条匹配失败、字段变空但程序不报错。
- 解析出来的流量是**字符串**（`6.0B`），后续要做数值比较必须自己写单位换算，别指望 `int()`。

## 三、求交层：假阳性都出在这里

先说结论：我第一版写了宽松匹配，报出 6 条「命中」；逐条核对后 **6 条全假**。而且假得很像真的——有产品名、有官网、有收入数字，看上去就是同一家公司。

### 陷阱一：聚合域名

有 4 个工具在目录站登记的「官网」不是自己的域名，而是应用商店和浏览器扩展商店的页面。

这类域名下挂着成千上万个产品。按域名求交时，`apps.apple.com` 这一个域名就把 4 个完全不同的产品映射到了同一条收入记录上。数据层面完全合法（域名确实相等），语义层面彻底错误。

### 陷阱二：按名字猜 slug

产品库的条目按 slug 索引，slug 通常由产品名派生。看起来很自然地可以「拿名字猜一个 slug 去撞」。

实测反例：一个产品的官网是某域名点 live，我拿域名主干去撞库，撞上一个名字相似的产品。两者除了名字像，没有任何关系。跨站命名本来就不一致——同名不同产品、同产品不同名都是常态，靠名字对齐等于用巧合做证据。

### 修法：只认强键

```python
AGG = {"apps.apple.com", "play.google.com", "chromewebstore.google.com",
       "chrome.google.com", "github.com", "producthunt.com",
       "apps.microsoft.com", "addons.mozilla.org", ...}

def normalized_host(url):
    h = (urlsplit(url or "").hostname or "").lower()
    return h[4:] if h.startswith("www.") else h

def joined(a, b):
    ha, hb = normalized_host(a["website"]), normalized_host(b["website"])
    if not ha or ha != hb:
        return False
    return ha not in AGG          # 聚合域名一律不参与
```

规则三条：只认官网域名完全相等；聚合/平台域名直接排除；不做任何基于名字的模糊匹配。

## 四、实测结果

严格口径下重跑：

| 数据面 | 抓取 | 成功 | 严格命中 |
|---|---|---|---|
| 热门榜 | 前 60 | 58 | 0 |
| 新品榜 | 前 24 | 22 | 0 |

不死心，又做了反向验证：从有真实收入的产品里挑 8 个，反过来去目录站找页面。4 个是普通生意，4 个是 AI 工具，用域名派生 slug 请求，全部 404。

补一个阻断性发现：该站的站内搜索是前端渲染的，换任何关键词都返回同一批卡片，没有可用的服务端检索。所以「拿已知产品反查流量页」这条路也不成立。

## 五、0 命中的两点工程解释

不是随机波动，是两个可以解释的结构性原因。

**收录是抽样。** 目录站三点一万个条目，对应的是一个远大于此的工具总量；产品库一万两千条，收入大头是普通生意而非 AI 工具。两个抽样人群的交集本来就稀薄。

**口径不重叠。** 被拆的那个案例是完全免费的工具站，变现入口只是给订阅用户提供「更好的版本」。这类产品在「支付网关一手收入」口径里天然不存在——不是数据没抓到，是这个口径不收录它。

## 六、可复用的四条结论

1. **跨源匹配只用强键。** 域名相等是强键；名字、slug、标题相等都是弱键，弱键只能用来缩小范围，不能当证据。
2. **先去掉聚合域再看命中率。** 应用商店、代码托管、产品榜单这类域名下面挂着无数产品，参与匹配必然造假。
3. **「匹配成功」要人工抽检。** 我这次的 6 条全部抽检才暴露问题；如果直接信统计数，后面所有分析都建立在这 6 条脏数据上。
4. **有界 + 礼貌间隔 + 不进定时任务。** 频次触发的 403 会让「每天跑一次」这种设计在第七天开始静默失效，而失败形态是「返回 0 条」，看起来像「今天没新数据」。
