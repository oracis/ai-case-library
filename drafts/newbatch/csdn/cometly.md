# 用AI对话直接回答归因问题不拼仪表盘

## 先说清楚它是什么

Cometly 是给 B2B SaaS 团队做的营销归因工具。它把 Google Ads、Meta、LinkedIn 等投放渠道的数据接到一处，然后允许你用自然语言提问——「上季度哪个渠道的获客成本最低」「这批线索里哪些真正变成了客户」——直接返回结论，而不是丢给你一张要自己读的仪表盘。

公开资料里的数字是：月经常性收入 20.2 万美元，最近 30 天进账 26.9 万美元（截至 2026-10-10 的快照，从 Stripe 支付记录直读）。先提醒一句：这是快照，不是现值；下文凡是涉及数字的地方都带时点和口径，别拿它当今天的实时值。

## 它真正卖掉的不是报表

仪表盘这个东西十几年前就有了。客户真正的痛点不是「看不到数据」，而是数据散在七八个平台、字段口径对不上、每周要花一天手工拼表，拼完还不确定哪个数字是对的。

Cometly 把这件事整个接过去。它卖的是「不用看报表」——你问一个问题，它给一个能直接拿去做预算决策的答案。这个位置很特别：投放规模到了某个量级之后，归因混乱才开始造成真实损失，小团队不会为它掏钱，而已经投了几年流的公司痛了很久。需求不需要教育，掏钱是止损，不是试错。

## 数据层先做扎实，AI 只放最上面一层

这是这篇稿子最值得抄的部分。它的结构可以拆成三层。

**接入层**负责把各渠道的原始数据拉进来。Google Ads、Meta、LinkedIn 各自的字段命名、时间粒度、货币单位都不一样，接入层要做的第一件事是映射成统一 schema。这一步没有捷径：渠道 API 一改版，字段就漂移，得有持续的校验和告警。

**归因层**处理「这笔成交该算到谁头上」。触点归属规则、归因窗口、重复点击去重、跨设备身份合并，都在这里定。这一层是脏活，但它决定了上层所有结论的可信度。

**查询层**才是那层「AI 对话」。自然语言进来，先被约束成结构化的指标查询，再由服务端执行，最后把结果解释成一句话。关键点是：口径固化在服务端，不让模型自己拼查询条件。同一指标在服务端只有一个定义，无论用户怎么问，答案都一致。

归因数据如果不准，对话式查询只是把错误答案讲得更流畅——这不是修辞，是产品设计的硬约束。所以顺序不能反：先把数据层做扎实，AI 放最后一层。

## 对话式查询工程上的四个坎

第一，**自然语言到指标的映射必须有界**。让模型自由生成查询语句看似灵活，实际会把「获客成本」和「单次点击成本」混为一谈。做法是把可用指标、维度、时间范围列成受控词表，模型只做槽位填充，不做自由发挥。

第二，**回答要能回溯到明细**。客户敢不敢拿这个答案去调整预算，取决于他能不能点进去看是哪几条记录支撑了这个结论。只能给出一句话、不能下钻的系统，在 B2B 场景里活不下来。

第三，**多租户下的数据隔离**。同一套查询层服务成百上千个客户，权限边界必须在服务端做，不能靠前端传参。

第四，**异常值的解释**。一次性的大额入账、退款、汇率变动都会污染趋势，查询层要能识别并标注，而不是把它们当成正常波动讲给客户听。

## 数字对账里最值得抄的一课

公开口径里有两个不能省的数字：最近 30 天 MRR 增速是 **-4.9%**，而同期进账增速是 **+35.4%**。两者背离，原因是一次性入账和退款。所以判断趋势只能用 MRR 口径，不能用当期进账——把 +35.4% 当成「增长强劲」讲，就是典型的误读。

另一个坑在计费单位。官网标示的席位单价与实测客户数对不上：按标示价反推需要 1,347 席，而实际只有 288 个付费客户，差 4.68 倍。合理的解释是计费单位实际不是「席」，而是按页面浏览量分层。别拿官网标价乘客户数去猜它的真实客单——这是最容易被写进案例稿、又最经不起推敲的一类推算。

历史峰值到最近完整月，留存 93%。这说明它不是一波流，而是一个长期横盘的盘子。对想抄的人来说，这个信号比「高增长」更有价值。

## 六条失败模式

1. **渠道 API 变更导致字段漂移**：没有持续校验，归因结果会在无人察觉的情况下错掉。
2. **归因窗口设置不当**：把品牌词流量算成付费流量，结论看起来很漂亮，实际是自我欺骗。
3. **一次性入账污染趋势**：不区分经常性项和一次性项，趋势判断必然失真。
4. **对话层绕过服务端口径**：同一指标两种答案，客户信任一次就崩。
5. **实施依赖人工**：9 人团队里有客户成功和实施角色，这个交付结构一个人做不了。要抄的是切入位置，不是交付方式。
6. **大客户定制把数据层压成项目制**：每家都要改一遍映射，产品就退化成外包。

## 能搬走的与不能搬的

能搬走的：数据层先行、口径固化在服务端、对话层做薄、回答可下钻、趋势只用 MRR 口径。这几条跟团队规模无关，一个人也能做。

不能搬的：它的客户成功和实施体系。9 人团队含两位创始人和一位 CTO，主体是 Comet LLC——这是公司样本，不是一个人怎么做的样本。照抄交付结构会把自己拖垮。

## 国内视角

国内投放数据在几个相对封闭的超级 App 生态里，跨渠道归因的数据获取难度比海外高一个量级。能做的切法不是先搭一个大而全的归因平台，而是先打通单一生态内的投放与成交数据，把口径做对，再谈跨渠道。

## 一句话结论

营销归因不是小工具生意，但它需要的团队交付决定了这不是一个人的赛道。一个人能抄的是数据层和口径设计，不是它的客户成功体系。
