# 跨数据源对齐：如何判断一份第三方流量数据能不能用

> 数据时点：2026-11-23 抓取（本机实测）

## 问题的真实形态

做选品分析时，最容易被忽略的一步不是「怎么抓到数据」，而是「这份数据能回答什么问题、不能回答什么问题」。

我遇到的具体场景是：一份第三方 AI 工具目录站的数据，公开了每个工具的月访问量、流量来源结构和关键词表；另一份是本地产品库，收入从支付网关直读。直觉方案是两边按产品对齐，一份数据提供流量、一份提供收入，互相校验。

做完之后我的结论是：**这两份数据不该被对齐使用**，因为它们服务的不是同一个人群。下面记录判断过程——这套方法比结论本身更可复用。

## 一、先明确每份数据的口径

任何跨源分析的第一步都该是做这张表，而不是先写采集器。

| | 目录站 | 收入型产品库 |
|---|---|---|
| 收录对象 | AI 工具，含大量免费产品 | 有支付网关流水的小生意 |
| 数字来源 | 第三方估算的流量 | 支付网关直读的流水 |
| 更新方式 | 周期性重算估算 | 跟随真实交易 |
| 能回答 | 这方向热不热、量级多大 | 这产品到底收到多少钱 |
| 不能回答 | 它到底赚多少 | 它值不值得做 |

这张表一旦列出来，很多「为什么对不上」的疑问会自己消失。比如被拆解的那个案例是完全免费的工具站，它的变现入口只是给订阅用户提供更好的版本——这类产品在「支付网关流水」口径里天然不存在。不是数据没抓到，是这个口径根本不收录它。

## 二、采集层：把「不报错」当作失败

采集器的实现只有几百行，但踩到的坑都属于「程序正常退出、结论是错的」这一类。

**请求头不足会 403，请求频次过高也会 403。**前者补一组完整浏览器头就能解；后者我在同一天连续抓了约九十个详情页后撞上——整个站点（含此前成功过的首页榜单）开始持续 403，隔半分钟复查仍是 403，换页面无效。这说明频率风控是独立的一层。

**压缩响应不解压会变成乱码，而不是异常。**响应体可能是 gzip，判断魔数后再解压：

```python
with opener.open(req, timeout=30) as r:
    body = r.read()
if body[:2] == b"\x1f\x8b":          # gzip 魔数
    body = gzip.decompress(body)
return body.decode("utf-8", "replace")
```

用 `errors="replace"` 时，未解压数据会被替换成一堆替换字符，解码不报错、正则匹配不到、字段全空——看起来像「站点改版了」，实际是自己没解压。

**解析必须区分「没有数据」和「解析失败」。**详情页的月访问量是 `6.0B` 这种带单位字符串，关键词表是三列 div。如果解析函数用 `try/except` 一律兜成 0，就会把「这个工具还没有流量数据」和「我的正则失效了」混成同一种结果。正确做法是让两者分别返回：解析失败返回 `None`，确实没数据返回空串，统计时分开计数。

## 三、对齐层：三处造假，一处修法

求交的键，我第一版写得很宽松：先按官网域名匹配，匹配不上再按产品名派生 slug 去撞。跑完报出 6 条命中。

逐条核对，**6 条全假**。它们的共同点是看上去极其合理：有产品名、有官网、有收入数字。

**造假点一：聚合域名。**有 4 个工具登记的「官网」是应用商店页和浏览器扩展商店页。这类域名下挂着成千上万个产品，按域名求交时会把 4 个完全不同的产品映射到同一条收入记录上。域名确实相等，但产品不是同一个。

**造假点二：名字派生 slug。**一个产品的官网是某域名点 live，我拿域名主干去撞库，命中一个名字相似的产品。两者除了名字像没有任何关系。跨站命名本来就不一致，靠名字对齐等于用巧合做证据。

**修法：只认强键。**

```python
AGG = {"apps.apple.com", "play.google.com", "chromewebstore.google.com",
       "chrome.google.com", "github.com", "producthunt.com", ...}

def normalized_host(url):
    h = (urlsplit(url or "").hostname or "").lower()
    return h[4:] if h.startswith("www.") else h

def joined(a, b):
    ha, hb = normalized_host(a["website"]), normalized_host(b["website"])
    if not ha or ha != hb:
        return False
    return ha not in AGG          # 聚合/平台域名一律不参与
```

三条：只认官网域名完全相等；聚合与平台域名直接排除；不做基于名字的模糊匹配。

## 四、实测：严格口径下的命中率

| 数据面 | 抓取 | 成功 | 严格命中 |
|---|---|---|---|
| 热门榜 | 前 60 | 58 | 0 |
| 新品榜 | 前 24 | 22 | 0 |

反向验证同样为 0：从有真实收入的产品里挑 8 个（4 个普通生意、4 个 AI 工具），用域名派生 slug 请求目录站页面，全部 404。该站站内搜索是前端渲染，换任何关键词返回同一批卡片，没有服务端检索可反查。

反向验证这一步值得单独说，因为它的目的是**排除「我的匹配规则太严」这个解释**。严格口径 0 命中之后，有两种可能：一是两边真的没有交集，二是我的键选错了。所以换一个方向再试一次——从 A 侧取样本，用最宽松的方式派生键，去 B 侧找。两个方向都空，才能把「规则太严」这个可能性排掉。

顺带发现两边的人群分布也不匹配：目录站热门榜前 60 里 20 个是大型厂商产品，其余多数月访问在千万级以上，唯一够「个人可做」量级的只有九万四千五；而新品榜虽然全是独立开发者产品，22 条里有 16 条还没有流量数据——工具刚上线，第三方估算还没积累。

一个要估算、一个要流水，中间还隔着「有数据的是巨头、有个体量的还没数据」的时滞。这就是 0 命中的完整解释。

## 五、判断一份第三方数据能不能用：四个检查点

1. **口径能不能说清。**说不清「这个数字是谁算的、用什么方法算的、什么时候算的」，就不要拿它做定量结论。
2. **强键存不存在。**有强键（如官网域名）才能跨源对齐；只有弱键（如产品名）时，只能用来缩小范围，不能出结论。
3. **命中能不能抽检。**这次 6 条假阳性全靠人工逐条核对才暴露。任何「自动匹配出 N 条」的结果，验收标准都必须是抽检，不是条数。
4. **失败形态是什么。**如果失败时返回的是空集合，那它和「真的没有」无法区分，必须额外埋计数（解析失败多少、请求失败多少），否则出了问题也看不出来。

## 六、抽检该怎么做

这次唯一的「验收动作」是抽检，而且它救了我。做法很简单，值得固化成流程：

- **全量看命中数，随机抽 5~10 条看语义。**不要看程序认为的「匹配度」，直接打开两边的页面，确认是不是同一个产品。
- **专门抽「最像真的」那几条。**假阳性通常出现在有完整官网、有明确产品名、看起来最规整的条目上，随机抽反而容易漏。我的 6 条假阳性全部集中在「有独立官网但指向应用商店」这一类。
- **对不上时，先怀疑键，再怀疑数据。**0 命中要能区分「真的没有交集」和「我的规则写错了」。办法是做一次反向验证：从另一侧取样，用最宽松的方式派生键去这一侧找，两边都空才能下结论。

最后补一条采集侧的工程约束：这类站点按频次风控，所以采集设计必须是有界的、带礼貌间隔的、按需触发的。凡是设计成「每天定时跑一轮」的方案，早晚会遇到「连续几天返回 0 条但没人发现」的情况——因为 0 条本身不是错误信号。
