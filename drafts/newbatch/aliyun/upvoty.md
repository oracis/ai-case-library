# 公开看板的多租户边界：缓存键、检索索引与投票洪峰

Upvoty 这类产品，表面看是一个「用户投票板」：用户提交想法，别人点票，团队把高票的排进路线图，状态公开可见。官网自述有 2,000 多个团队在用（未区分付费与免费）。

换个角度，从资源与弹性的账本看这个形态：它的数据量很小，但**读写路径极其分散**——一个公开页面同时要读主表、读票数、读检索索引、读内部状态投影，还要在状态变化时给几百人发通知。这类系统的事故几乎都不是「撑不住」，而是**串了**。

这里不谈定价策略，只谈负载形状会怎么反过来约束架构。

## 一、负载长什么样

把它的访问拆开，有四段形状完全不同：

- **公开看板的读洪峰**。一个客户把投票链接转发到群里，几分钟内几千次打开。特点是读多写少、页面几乎一样、必须匿名可访问。
- **投票的写尖峰**。同一时刻几百人点票，落在同一批条目上。写入量不大，但对**幂等和去重**的要求极高——重复计票比少计票更难修。
- **检索与归并的离线批**。提交一条反馈时要做疑似重复检索，这是一次读扩散；运营确认合并时又要重算票数。这段是间歇性的，且不能拖慢前台。
- **通知的扇出**。一个需求上线，要通知所有投过票的人。几个人到几百人不等，扇出倍率不可预测，而且是外部依赖（邮件网关）驱动的。

规划容量的常见错误是把这四段当成一个服务：为公开读洪峰备的缓存，被写尖峰的一致性要求拖累；为扇出准备的长连接，在没通知的日子里全空转。

## 二、资源与成本的取舍

按这个形状，几件事必须在架构层定下来：

1. **公开看板做成可缓存的只读投影**。页面是匿名的、内容相对稳定，适合在 CDN 或边缘缓存住，设一个较短的 TTL 就够了。真正的写入全部回到源头系统，看板只读。**最忌讳的是允许运营在看板上拖卡片再反向写回内部系统**——两套状态机双向同步，迟早循环覆盖。
2. **票数按两种口径分开存**：投过票的组织数、投过票的人数。合并时要能重算，所以每张票必须带 `(租户, 用户, 条目)` 的幂等键。合并后不能简单相加——同一个人投过两条被合并的条目，只能算一票。这决定了合并是一条**可重放的日志**，而不是一次 UPDATE。
3. **归并检索走独立索引，且带租户命名空间**。提交时的疑似重复检索是一次读扩散，不能压在主库上。但如果索引是全局的、只靠上层拼租户条件，一定会出事——典型事故是缓存键漏了租户前缀，A 客户的反馈列表被塞进一个全局 key，B 客户打开看板读到别人的内容。同类的风险还出现在全文索引、向量空间、导出的临时文件、以及日志里的正文片段。稳的做法是把租户标识做成所有查询的强制参数，在存储层就拒绝不带租户条件的读取。
4. **通知扇出要独立成队列，并且幂等**。邮件网关会超时重投，任务会重试，同一条状态变更必须带事件 id 去重，否则用户收到两遍「已上线」。还要按用户聚合事件：一个人关注了五个需求，一天内不该收到五封邮件。这一层的成本不在算力，在外部网关的配额和退信率。
5. **删除要跨层穿透**。用户要求删除自己提交的反馈时，要同时清掉主表、检索索引、向量片段、通知队列里的待发内容，以及合并链上的引用。只删主表是最常见的实现，也是最容易被合规问住的一种。

可观测性上值得盯的不是请求量，而是三个数：**状态变更到通知发出的滞后天数**（一涨说明闭环断了，看板上还看不出来）、**合并错误的回滚次数**（归并质量）、**同一用户重复投票的拦截率**（幂等键是否有效）。

## 三、公开数字的时点

这个案例没有可以安全引用的财务数字，唯一的规模口径是官网自述的「2,000 多个团队在用」，未区分付费与免费，也没有第三方核验。

> 数据时点 ｜ 官网自述规模（2026 年可查的产品页）｜ 口径：使用团队数，未区分付费与免费，无第三方核验

各类第三方汇编里关于该产品收入的估算与创始人自述口径不同、时点不同，本文不引用任何金额，也不做换算。对资源规划来说，团队数这个口径其实比收入更有用——它直接对应租户数量、索引分片和通知扇出的基数。

## 四、判断与适用边界

这套形态成立的前提：

- **公开与私有必须先分清**。不少企业客户要求自己的私有反馈板：只有本组织成员可见、走单点登录、管理员看全员提交。这时候「公开缓存」就不能是全局的，缓存键、索引命名空间、导出文件路径都要按租户切分。先把这条边界定死，再谈性能优化。
- **投票洪峰靠限流与排队消化，不靠拒绝**。速率限制和异常聚类能挡住脚本刷票，但真实客户集中投票的形态和刷票非常像。误伤的代价远高于漏放——一个被误判的客户会同时失去投票权和反馈意愿。所以规则宁可事后人工复核，也不要在写入路径上直接拒绝。
- **内部状态与公开状态必须单向**。内部研发状态通常有十几种（待评审、待排期、开发中、联调、待发布、灰度、已上线、回滚、暂缓），公开只保留四五个。映射要尽量单调：内部从「开发中」退回「待联调」时，公开状态不该来回跳。看板反复变化比更新慢更伤信任。「已排期」等价于对外承诺，必须带明确的进入条件与撤回策略。
- **权重规则不要公开**。把「付费客户一票算三票」写在明面上，等于邀请大家博弈权重，运营也很难解释某个高票需求为何没排上。把权重留在内部排序参考里、公开只展示原始票数与组织数，比做一套精巧的加权算法更可控。

至于长尾落地页，那部分可以工程化（模板渲染加结构化快照批量生成），但它同时也是最容易复制的一层：模板能被照搬，收录排名会随搜索规则波动。真正决定客户留存的，是前面那些不显眼的东西——归并准不准、票数可不可信、状态变没变、通知到没到。

结论：负载形状决定成本结构，成本结构再决定哪些设计能长期扛住。Upvoty 的团队数是快照，引用带时点。
