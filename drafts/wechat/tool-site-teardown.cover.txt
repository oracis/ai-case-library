三、为什么是这套（对齐 docs/MULTIPLATFORM.md 封面口径）
================================================================

1. 两行结构：短判断 + 一句边界。封面只承担「点进来」的活，不承担科普。
   正文标题 25 字上封面会被压到 30px 以下，所以封面上行单独压到 11 字。

2. 数字的取舍：封面口径禁的是「会过期的快照」（金额、订阅数、留存、倍数）。
   「80 个样本 / 0 命中」是这次实验的固定结果，不会随时间漂移，所以可以上封面。
   如果仍然希望封面零数字，直接用备选 A「估算撑不起拆站法」。

3. 第二行用「能/不能」而不是形容词：可验证、不吹、和正文结论同构。

4. 摘要钩子前置：转发卡片大约只能显示 2 行（约 54 字），
   所以「80 个样本，0 条对上」放在最前 12 字，截断也不丢信息。

5. 全篇无 $ 、无 ** 加粗、无金额，避开 KaTeX 与金额密度两道闸；
   publish_guard.scan_content('wechat', 摘要) 返回空。

   python scripts/md2wechat.py drafts/wechat/tool-site-teardown.md
   产物：out/wechat/公众号-tool-site-teardown.html

   python scripts/wechat_cover_render.py \
     --name "80 个样本，0 命中" \
     --desc "第三方估算能当选题，不能当证据" \

③ 连后台存草稿（管理员扫码；publish 会自己重绘封面，②的 PNG 只是预览/兜底）
   python scripts/wechat_publish.py publish \
     --file "out/wechat/公众号-tool-site-teardown.html" \
     --title "我拿 80 个 AI 工具去验那篇拆站文，一条都没对上" \
     --desc "80 个样本，0 条对上。那篇很火的拆站文流程干净，可每一步都建立在估算上；拿它去和支付网关的一手收入求交，我才看清这类数据该摆在哪。" \
     --cover-name "80 个样本，0 命中" \
     --cover-desc "第三方估算能当选题，不能当证据" \
     --cover-kicker "DATA CHECK" \
     --tag "实测 · 2026-11" \
     --slug tool-site-teardown \
     --dry

注意：
  · --file 要的是「公众号-*.html」，不是 .md；本稿不在 cases.json，build 不认它。
  · --dry 会打印计划但不打开浏览器；去掉 --dry 才真连（需要已登录的 Chrome CDP）。
  · 干跑实测输出：标题 27 字 / 摘要 67 字 / 正文 3199 字，全部在上限内。
